# Packaging

The NuGet packages, the native runtime packages and their add-ons, and versioning. Moved here from CLAUDE.md, which keeps the short version.

## Packages

- **Packaging**: `Emgu.LiteRT`, `Emgu.TF.Lite` (csproj, `AssemblyName`, nuget `PackageId` and C# namespace all `Emgu.TF.Lite` — they briefly diverged, with the folder and then the csproj/AssemblyName/PackageId each renamed to `Emgu.LiteRT.Tflite` and later moved back) and `Emgu.LiteRT.Util` each produce their own nuget package (`IsPackable=True`/`GeneratePackageOnBuild=True` in their CMake-generated `Directory.Build.props`) — they used to ship bundled into a single `Emgu.LiteRT` package (via `PrivateAssets="all"` ProjectReferences plus an `IncludeReferencedProjectsInPackage` target), but were split so each can be installed independently.
- `Emgu.TF.Lite` and `Emgu.LiteRT` both `ProjectReference` `Emgu.LiteRT.Util.csproj` with no `PrivateAssets` (their `UnmanagedObject`-derived types need it to compile), which NuGet turns into a normal package dependency on `Emgu.LiteRT.Util` when packing since the referenced project is itself packable; `Emgu.LiteRT` has no reference to `Emgu.TF.Lite` at all, since its code never used it — that was only ever packaging-bundling, not a real dependency.
- Every package ID except `Emgu.TF.Lite`'s, `Emgu.TF.Lite.ImageIO`'s and `Emgu.TF.Lite.runtime.windows`'s (each a literal string, not derived from the `Emgu.LiteRT` root) comes from `EMGU_LITERT_NUGET_ID` (`Emgu.LiteRT`) in the top-level `CMakeLists.txt` — `Emgu.LiteRT.Util`, `Emgu.LiteRT.Tflite.Models`, `Emgu.LiteRT.runtime.{macos,windows,ubuntu,debian-*,maui.*}` — and their underlying projects mostly keep `Emgu.TF.Lite.*` names or namespaces too (e.g. `Emgu.TF.Lite.Models/NetStandard/Emgu.TF.Lite.Models.csproj`), same as `Emgu.TF.Lite/NetStandard/Emgu.TF.Lite.csproj` itself (no longer an exception now that its csproj/AssemblyName/PackageId moved back off `Emgu.LiteRT.Tflite`).
- Projects that use `Emgu.TF.Lite`/`Emgu.LiteRT.Util` types (`Emgu.TF.Lite.Models`, the MAUI runtime projects) now `ProjectReference` all three with no `PrivateAssets`, so their own packages correctly depend on all three.
- **Linux package ids carry the distro version, as Emgu CV's do** (since 2026-11-05): `Emgu.LiteRT.runtime.ubuntu-<version>-<arch>` / `Emgu.LiteRT.LM.runtime.ubuntu-<version>-<arch>` (e.g. `ubuntu-26.04-x64`; before, `ubuntu.24.04-x64` style, hard-coded to that when packaged off Ubuntu) and `Emgu.LiteRT.runtime.debian-<release>-<arch>` / `Emgu.LiteRT.LM.runtime.debian-<release>-arm64` (e.g. `debian-trixie-arm64`; before, `debian-arm64`). The old ids get no further versions. The folders inside the packages don't change (`runtimes/ubuntu-x64/native`, `runtimes/linux-arm64/native`). The version comes from `ubuntu_version.txt` / `debian_version.txt`, which `platforms/ubuntu/*/bazel_build_tflite` and `platforms/debian/*/{bazel,cmake}_build_tflite` write next to the libraries (from `/etc/os-release`), so another machine can package them; without it, CMake asks `lsb_release` when it runs on that distro, else leaves the version out with a warning (`EMGU_READ_DISTRO_VERSION` in the top-level `CMakeLists.txt`). Ubuntu is one package named after the architecture it holds (x64 when both folders exist).
- **Each Linux package ships `build/<id>.props` with `<UseRidGraph>true</UseRidGraph>`** (`cmake/UseRidGraph.props.in`, as Emgu CV's packages do): since .NET 8 the SDK and the host only know portable RIDs, so without the full RID graph a portable app ignores `runtimes/ubuntu-x64/native`, and `DllImport("liblitert-lm")` etc. fail. Until 2026-11-05 the base Ubuntu package also packed its files into `runtimes/runtimes/ubuntu-*/native` (doubled since 2022), which NuGet doesn't treat as native assets.
- `Emgu.LiteRT.LM.Server` (2026-11-05, TODO item 29): its own package (`EMGU_LITERT_LM_SERVER_NUGET_ID`, `netstandard2.0;net8.0`, props/README from `cmake/Emgu.LiteRT.LM.Server.*.in`), depending only on `Microsoft.Extensions.AI.Abstractions` - no LiteRT, so any app can serve any `IChatClient`; `Emgu.LiteRT.LM.Maui.OpenAI` references it for the Mac's serving feature.
- `Emgu.TF.Lite/Toolbox.cs`'s tfliteextern image helpers (`Pixel32ToPixelFloat` etc.) are in `Emgu.TF.Lite.Toolbox`, not `Emgu.LiteRT.Util.Toolbox` — a partial class can't span the two assemblies.

## LiteRT-LM native libraries

- `liblitert-lm` (+ `libGemmaModelConstraintProvider`) is packaged, when present, in `Emgu.LiteRT.runtime.macos` (top-level `CMakeLists.txt`), `Emgu.LiteRT.Runtime/Mac`'s `.projitems`, the MAUI Android runtime (`arm64-v8a`/`x86_64`), and - on Windows, where it's built separately by `bazel_build_litert.ps1` rather than bundled with `libLiteRt.dll`/`tfliteextern.dll` - its own `Emgu.LiteRT.LM.runtime.windows` nuget package (depending on `Emgu.LiteRT.runtime.windows` for `libLiteRt.dll`), built only when `lib/runtimes/win-x64/native/liblitert-lm.dll` exists (`HAVE_WINDOWS_LITERT_LM`).
- `libomniextern` (Emgu's C API over LiteRT-LM's OmniEngine: speech recognition, Emgu.LiteRT.LM's `SpeechToTextEngine`; `libasrextern` before LiteRT-LM v0.19.0) goes next to `liblitert-lm` wherever that is packaged, each guarded on its own file existing: `Emgu.LiteRT.runtime.macos` and `Emgu.LiteRT.Runtime/Mac`'s `.projitems` (`libomniextern.dylib`), `Emgu.LiteRT.LM.runtime.maui.android` (`libomniextern.so`, arm64-v8a/x86_64), `Emgu.LiteRT.LM.runtime.maui.ios` (`omniextern.xcframework`), `Emgu.LiteRT.LM.runtime.maui.macos` (Mac Catalyst, the macOS dylib), `Emgu.LiteRT.LM.runtime.windows`, `Emgu.LiteRT.LM.runtime.ubuntu-*` (excluded from the base Ubuntu package's `*.so` glob) and `Emgu.LiteRT.LM.runtime.debian-<release>-arm64` (likewise excluded from the base Debian package; with `liblitert-lm.so`, and with the two prebuilts only from a `LITERT_LM_PREBUILTS=1` build, each file guarded on existing - the default Debian build has none, see `docs/native-builds.md`). Parakeet's weights it runs are CC-BY-4.0 (downloaded by the app, not packaged).
- On macOS (and Mac Catalyst) `liblitert-lm.dylib` also needs `libwebgpu_dawn.dylib` since LiteRT-LM v0.19.0 (Google's prebuilt Dawn, 15 MB, a load dependency of its WebGPU sampler): packaged next to it in the same places as `libGemmaModelConstraintProvider.dylib`. So does `liblitert-lm.so` on Linux (`libwebgpu_dawn.so`, shipped in `Emgu.LiteRT.LM.runtime.ubuntu` and left out of `Emgu.LiteRT.runtime.ubuntu`). Android and iOS don't link it. On Windows `liblitert-lm.dll` only delay-loads `webgpu_dawn.dll` (LiteRT-LM's prebuilt, 13 MB), for GPU sampling: it loads and runs on the CPU without it, so `Emgu.LiteRT.LM.runtime.windows` leaves it out and only the optional `Emgu.LiteRT.GPU.runtime.windows` ships it (before 2026-11-03 both did, so an app with both packages got two copies of it). `bazel_build_litert.ps1` still copies it next to the library, for local runs and the GPU bundle.

## The LiteRT-LM add-ons for iOS and Mac Catalyst

- Like Android's LM natives, they ship in a separate add-on rather than the base `Emgu.LiteRT.runtime.maui.ios`: `Emgu.LiteRT.Runtime/Maui/LM/iOS/Emgu.LiteRT.LM.runtime.maui.ios.csproj` (an iOS binding project with nothing to bind, `NoBindingEmbedding`, depending on the base iOS runtime; package `Emgu.LiteRT.LM.runtime.maui.ios`, props/README from `cmake/Emgu.LiteRT.LM.runtime.maui.ios.*.in`) embeds the xcframeworks - since 2026-11-04 also `LiteRtMetalAccelerator.xcframework`, LiteRT's GPU accelerator for iOS (Google's prebuilt, 8 MB; unlike macOS's Metal add-on it isn't a package of its own yet) (`NativeReference Kind=Framework`, when present; the package carries them in its `.resources.zip`), and the `Emgu.LiteRT.LM.runtime.maui` aggregator gets an ios TargetFramework and a PackageReference to it only when `lib/ios/LiteRtLm.xcframework` exists (`EMGU_LITERT_LM_MAUI_IOS_TFM`), so hosts that never built it don't try to restore it.
- **Mac Catalyst** has no LiteRT-LM build (Bazel has no Catalyst platform, and LiteRT-LM's prebuilt Gemma library only exists for macOS/iOS/Android), but dyld lets a Catalyst process load (not link) a macOS dylib, so the add-on `Emgu.LiteRT.Runtime/Maui/LM/Mac/Emgu.LiteRT.LM.runtime.maui.macos.csproj` (a plain maccatalyst library, package `Emgu.LiteRT.LM.runtime.maui.macos`, depending on the base `Emgu.LiteRT.runtime.maui.macos`) ships the macOS arm64 `liblitert-lm.dylib` plus `libGemmaModelConstraintProvider.dylib`/`libLiteRt.dylib` from `lib/runtimes/osx/native/` as `None` items copied to output/publish (so a referencing app puts them in `Contents/MonoBundle`) and packed under `runtimes/maccatalyst-arm64/native`; `Emgu.LiteRT.LM`'s `LiteRtLmLibrary` is `liblitert-lm` on Catalyst (which also defines `__IOS__`).
- The static Catalyst `tfliteextern` and the TFLite inside those dylibs never share a binary.
- The aggregator's maccatalyst TFM/PackageReference is likewise only generated when `lib/runtimes/osx/native/liblitert-lm.dylib` exists (`EMGU_LITERT_LM_MAUI_MACCATALYST_TFM`).
- Apple Silicon only, like `liblitert-lm.dylib`.
- Verified: the Catalyst demo ran Qwen3 multi-turn while its static `tfe*` API kept working in the same process, and `Emgu.LiteRT.LM`'s iOS `DllImport("__Internal")` resolves against the linked framework - verified in an iOS 27 simulator: the MAUI demo downloaded and ran Qwen3, streaming and multi-turn.

## Versioning

- There is no `tensorflow/` submodule — it was removed once the Windows CMake path was proven to work without it (LiteRT downloads the TF source it needs itself). The overall package version (`CPACK_PACKAGE_VERSION_*` in the top-level `CMakeLists.txt`, and `litertextern/tfliteextern/CMakeLists.txt`'s own version) is read from `litert/litert/version.bzl` (`LITERT_EXPERIMENTAL_VERSION`) via `cmake/modules/LitertVersion.cmake`, plus the git commit count. Exception: the TFLite-versioned packages (`Emgu.TF.Lite`, `Emgu.LiteRT.Tflite.Models`, `Emgu.TF.Lite.runtime.windows`) use the TFLite version, i.e. TensorFlow's `TF_VERSION` (`EMGU_TFLITE_PACKAGE_VERSION` = `<TF_VERSION>.<commit count>`, e.g. 2.22.0.N). Every native build writes a `tflite_version.txt` next to its libraries (the Bazel scripts from `$(bazel info output_base)/external/org_tensorflow/tensorflow/tf_version.bzl`, the CMake build from the TensorFlow it downloads), the same way as `tflite_with_xnnpack.txt`; the top-level `CMakeLists.txt` reads all of them under `lib/` (highest wins, with a warning if they differ - e.g. a CMake-built 2.21.0 next to Bazel-built 2.22.0) and falls back to the LiteRT version when there are none. The root `Directory.Build.props` (from `cmake/Directory.Build.props.in`, imported at the end of each project's own props) only sets `Version` when the project hasn't, so the Tflite projects' version isn't overridden. The MAUI runtime's `PackageReference` to `Emgu.TF.Lite.runtime.windows` uses that version too; `ProjectReference`s to the Tflite projects pick it up automatically.

## GPU accelerator packages (OpenCL, Metal)

- **Android, OpenCL.** LiteRT's OpenCL accelerator `libLiteRtOpenClAccelerator.so` is a LiteRT-LM prebuilt
  (`prebuilt/android_{arm64,x86_64}`; self-contained, using only Android system libraries). `bazel_build_tflite_android`
  copies it to `lib/android/<abi>/`, and the optional `Emgu.LiteRT.OpenCL.runtime.maui.android` package embeds it
  (`Emgu.LiteRT.Runtime/Maui/OpenCL/Android/`; props and README from `cmake/Emgu.LiteRT.OpenCL.runtime.maui.android.*.in`;
  `EMGU_LITERT_OPENCL_MAUI_ANDROID_NUGET_ID`). It has arm64-v8a and x86_64 only and depends on
  `Emgu.LiteRT.runtime.maui.android`; nothing depends on it. It is a LiteRT plugin, so `CompiledModel` can use it with
  `HwAccelerators.Gpu` too, though only LiteRT-LM was tested. The demo references it.
- **Duplicate native libraries in the Android add-ons.** When an add-on is packed, .NET for Android unpacks the referenced
  base project's `.aar` (`obj/.../lp/<n>/jl/jni/`) and adds its `libLiteRt.so` and `libtfliteextern.so` to the add-on's
  `EmbeddedNativeLibrary` items (with `%(OriginalFile)` set), which put another copy of them for every ABI into the add-on's
  `.aar`. So both add-ons - this one and `Emgu.LiteRT.LM.runtime.maui.android` - have an
  `EmguExcludeReferencedNativeLibraries` target (before `_CreateAarCache`) that removes the items with `%(OriginalFile)`; the
  base package they depend on provides them. Verified: the OpenCL package went from 16 to 4.1 MB, the LM package from 37 to
  26 MB, and an Android app referencing only the two add-on packages gets one copy of each library.
- **Mac Catalyst, Metal.** LiteRT's Metal accelerator `libLiteRtMetalAccelerator.dylib` is a LiteRT-LM prebuilt
  (`prebuilt/macos_arm64`; arm64, macOS 14+, using only system frameworks). `bazel_build_tflite_macos darwin_arm64` copies it
  to `lib/runtimes/osx/native/`, and the optional `Emgu.LiteRT.Metal.runtime.maui.macos` package puts it in
  `Contents/MonoBundle` (`Emgu.LiteRT.Runtime/Maui/Metal/Mac/`; `EMGU_LITERT_METAL_MAUI_MACOS_NUGET_ID`; props and README from
  `cmake/Emgu.LiteRT.Metal.runtime.maui.macos.*.in`). It depends on `Emgu.LiteRT.LM.runtime.maui.macos`, the only package with
  a Catalyst `libLiteRt.dylib`, which loads the plugin by name from its own folder - verified in the test runner and in the
  Catalyst app.
- **Plain macOS .NET apps, Metal.** The same plugin ships in the optional `Emgu.LiteRT.Metal.runtime.macos` package
  (`cmake/Emgu.LiteRT.Metal.runtime.macos.Package.{nuspec,README.md}.in`, generated into
  `platforms/nuget/Emgu.LiteRT.Metal.runtime.macos/` and packed by its `CMakeLists.txt` like `Emgu.LiteRT.runtime.macos`, only
  when `lib/runtimes/osx/native/libLiteRtMetalAccelerator.dylib` exists - `HAVE_MACOS_LITERT_METAL`; it goes in
  `runtimes/osx/native` and depends on `Emgu.LiteRT.runtime.macos`). `Emgu.LiteRT.Runtime/Mac`'s `.projitems` copies the
  plugin to in-repo projects' output when it exists.
- **Finding the plugin on macOS.** libLiteRt dlopens its plugins by bare file name, which on macOS only finds them on the
  library search path or in the current folder: a console app using these packages couldn't load the plugin unless it was
  started from `runtimes/osx/native`. So `Emgu.LiteRT.Util.AcceleratorPlugins.Load()` (`Emgu.LiteRT.Util/AcceleratorPlugins.cs`,
  once per process) dlopens `libLiteRtMetalAccelerator.dylib` by full path from the app folder or
  `runtimes/{osx,osx-arm64,maccatalyst-arm64}/native` on macOS and Mac Catalyst, and LiteRT's later dlopen then returns the
  loaded library. `Emgu.LiteRT`'s `Environment` calls it before `LiteRtCreateEnvironment` (LiteRT registers its accelerators
  when the environment is created), and `Emgu.LiteRT.LM`'s `Engine` before creating an engine with a "gpu" backend. Verified
  with a console app started from `/`, both a portable build (`runtimes/osx/native`) and an `-r osx-arm64` build.
