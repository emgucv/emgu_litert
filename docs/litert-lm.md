# LiteRT-LM in .NET

`Emgu.LiteRT.LM` (LiteRT-LM's C API), `Emgu.LiteRT.LM.Models` (ready-to-use language and embedding models) and `Emgu.LiteRT.LM.Extensions.AI` (`IChatClient`): facts about LiteRT-LM, model quirks and the bugs worked around. Moved here from CLAUDE.md, which keeps the short version.

## Emgu.LiteRT.LM

- `Emgu.LiteRT.LM/` (own `Emgu.LiteRT.LM.dll` and nuget package `Emgu.LiteRT.LM`, namespace `Emgu.LiteRT.LM`, depending on `Emgu.LiteRT.Util` only) wraps LiteRT-LM's C API (`LiteRT-LM/c/*.h`, the `litert_lm_*` functions exported by `liblitert-lm`) the same way, via `DllImport("liblitert-lm")` (`__Internal` on iOS): `EngineSettings`/`Engine` (load a `.litertlm` model; tokenize, start/stop tokens), `SessionConfig`/`SamplerParams`/`Session` (`GenerateContent`, `RunPrefill`/`RunDecode`, scoring, checkpoints), `InputData`, `Responses`, `ConversationConfig`/`ThinkingConfig`/`ConversationOptionalArgs`/`Conversation` (JSON messages in LiteRT-LM's format; `Conversation.CreateTextMessage` builds one), `LoadedFile` (model capabilities: thinking, tools, modalities, sampler defaults, context length, signature lengths, backends, NPU/SoC, model type, embedding size) and `BenchmarkInfo` (with `MaxNumTokens`), `SpeculativeDecodingConfig` (`EngineSettings.SpeculativeDecoding` / `SessionConfig.SpeculativeDecoding`: Off, On, Adaptive), `Session.Clone`, `EngineSettings.FromFileDescriptor` and `SingleThreadedExecution` (with `Conversation.WaitUntilDone`), plus the embedding engine (`EmbeddingEngine.cs`: `EmbeddingEngineSettings` - model, backends, threads, cache folder, min/max input length, activation type - audio threads, vision tokens per image, NPU dispatch folders - `EmbeddingOptions` - `Normalize`, `InsertSpecialTokens`, `InputOverflowStrategy`, `OutputSize`, `VisionTokensPerImage` - and `EmbeddingEngine` with `ComputeEmbedding(text | InputData[])`, `ComputeEmbeddings(texts | InputData[][])` as one batch, and `CosineSimilarity`; it loads GPU plugins like `Engine`); and `LiteRtLmExperimental` (c/experimental.h: `IsDebuggerEnabled`, `UpdateGpuEnableMetalResidencySet`, `GetDebugCaptureDir`). Every function of the v0.19.0 C API is wrapped.
- Notes: strings cross as null-terminated UTF-8 `byte[]` / `PtrToStringUtf8` (not `LPStr`, which is ANSI on Windows); since C API 1.0.0 (LiteRT-LM v0.19.0, `LiteRtLmInvoke.ApiVersion`; older libraries aren't supported) every function that can fail returns a `LiteRtLmStatusCode`, results come back through `out` parameters, and counts and indexes are `size_t` (`UIntPtr`). As Emgu CV does, nothing is thrown from native code: `LiteRtLmInvoke.CheckError` runs right after each call and throws `LiteRtLmException` with `Status`, `FunctionName` and `ErrorMessage` (from `litert_lm_get_last_error_message`, thread-local, so read on the calling thread); `CheckFound` turns the `NotFound` of a value a model file doesn't define into false / null. The stream callback runs on LiteRT-LM's thread and never throws. Stop tokens (`token_unions_get_token_at`) are borrowed, not deleted; `render_*_to_string` results belong to the conversation until the next render. The config objects have no getters, so their properties cache the last value set; every setter and the stream functions copy their arguments.
- Streaming (`Session.GenerateContentStreamAsync`/`RunDecodeAsync`, `Conversation.SendMessageStreamAsync`, whose chunks are partial JSON messages) goes through `StreamOperation`: one static `LiteRtLmStreamCallback` delegate, a `GCHandle` as `callback_data`, a `TaskCompletionSource` with `RunContinuationsAsynchronously` (user code never resumes on LiteRT-LM's thread), no exception ever unwinding into native frames, native cancel issued from a thread-pool thread (cancelling from inside a callback could deadlock on LiteRT-LM's execution-manager locks), and the task completing only on the final chunk, so the session is idle once it completes (an `onChunk` exception cancels and then faults the task).
- LiteRT-LM doesn't support reusing a session/conversation after `Cancel`.

## Embeddings: EmbeddingModel, EmbeddingGemma 2 and DocumentIndex

- `Emgu.LiteRT.LM.Models`' `EmbeddingModel` (download + load like `LanguageModel`; `Embed`, `EmbedQuery`/`EmbedDocuments` with the model's prompt prefixes, normalized) and `EmbeddingGemma2` (`litert-community/embeddinggemma-2-text-270m-litert-lm`'s `embeddinggemma-2-text-270m.litertlm`, 165 MB, Apache 2.0, 768 values or 512/256/128, EmbeddingGemma's `task: search result | query: ` / `title: none | text: ` prefixes) wrap it; `TestEmbeddingGemma2`: on an M1's CPU it loads in ~6 s, embeds a query in ~66 ms, the batch equals single embeddings, and each of 5 questions finds the document that answers it (cosine ~0.8 vs <0.72 for the rest; the prefixes made no difference on this small set).
- Images and audio: `EmbeddingModel.SupportsImages`/`SupportsAudio` gate `EmbedImage`/`EmbedImageFile`/`EmbedImages` (batch) and `EmbedAudio`/`EmbedAudioFile` (optionally with a text, sent as a second input of the same request), and `CreateEngineSettings` passes `EmbeddingModel.VisionBackend`/`AudioBackend` (default "cpu", also with a "gpu" main backend; null disables, like `Gemma4`'s) for such models; `EmbeddingGemma2TextVision` (`litert-community/embeddinggemma-2-text-vision-440m-litert-lm`'s `embeddinggemma-2-text-vision-440m.litertlm`, 388 MB, text + images) and `EmbeddingGemma2Multimodal` (`embeddinggemma-2-740m-litert-lm`'s `embeddinggemma-2-740m.litertlm`, 485 MB, text + images + audio) derive from `EmbeddingGemma2` (same prefixes; images and texts share one space, so `EmbedQuery` finds images).
- `TestEmbeddingGemma2TextVision`/`TestEmbeddingGemma2Multimodal` on the M1's CPU: a text query picks the right one of 4 images (apple, Grace Hopper, tulips, surfers; 4/4, the same scores from both models - they share the vision encoder), ~1 s per image (the vision encoder loads lazily on the first one), batch equal to single; the 740M model matches LiteRT-LM's `have_a_wonderful_day.wav` to "Have a wonderful day!" (0.85 vs <0.59), in 150 ms; warm loads 0.2 s.
- On a Pixel Fold's CPU (740M model, temporary self-test in the demo): the same results and scores (5/5 text, 4/4 images, audio 0.847), warm load 2.1 s, ~400 ms per text query, ~5.7 s per image (vision encoder load 10 s), audio 3.7 s, RSS 0.9 GB.
- The GPU: before LiteRT-LM v0.19.0 it crashed the process on Android (OpenCL) and macOS (Metal) while `LiteRtCreateCompiledModel` compiled the text or vision encoder. EmbeddingGemma 2's weights are external buffers, which the GPU plugin binds through `weight_loader::WeightLoader` in `libLiteRt`; LiteRT commit `dd3db3123` (2026-10-08) changed that interface, and v0.18.0's prebuilt plugins were built after it while our `libLiteRt` was built before. v0.19.0's LiteRT (`dcb657e8`) has the change, and `EmbeddingModel.Init` no longer refuses "gpu" (2026-11-01; `EnableWindowsWebGpu` is obsolete and does nothing).
  - Mac (M1, Metal): `TestEmbeddingGemma2MultimodalGpuMatchesCpu` / `TestEmbeddingGemma2TextVisionGpuMatchesCpu` (now run wherever a GPU plugin is next to `libLiteRt`, like `TestLiteRtMobilenetGpu`): text cosine to the CPU's 0.9977-0.9989, image 0.9971, audio 0.9928; the apple picture still matches "a red apple" best and the spoken sentence its text (0.925); 730 ms against 2.4 s on the CPU for 3 texts, an image and the audio; the first GPU load 17.9 s (compiling its programs), then 1.7 s.
  - Galaxy S10 (Adreno 640, OpenCL; the demo with a temporary self-test): text cosines 0.9975-0.9987, 3 texts in 439 ms against 2,375 ms on the CPU, load 16.7 s. Pixel Fold (Mali-G710, OpenCL): 0.9995-0.9997, 511 ms against 1,552 ms, load 22.3 s.
  - Images and audio on the S10's GPU (2026-11-01, the 740M model, the demo with a temporary self-test): image cosines to the CPU's 0.9896-0.9983 (the tulips lowest), queries 0.9981-0.9991, audio 0.9982; 4/4 queries still find their picture, the audio matches its text (0.871). Load 4.7 s (warm), the first image 1.5 s (vision encoder), 4 images in 6.2 s against 29.0 s on the CPU, 4 queries and the audio in 1.3 s against 7.5 s; a 20 s video's `VideoMomentIndex` (10 windows) in 15.8 s against 72.5 s, finding the shuttle scene. With Gemma 4 E2B on the GPU as well: PSS 4.1 GB, 1.1 GB available, no kill.
  - The demo offers the GPU search models on Windows (`WINDOWS_WEBGPU`), Mac Catalyst and Android since 2026-11-01 (not iOS, untried there).
- `DocumentIndex` (`Emgu.LiteRT.LM.Models/DocumentIndex.cs`, no PDF dependency) is the retrieval part of document questions: `AddText(text, location)` splits text into passages (`SplitText`: at most `MaxPassageLength` 700 characters at paragraph/sentence ends - not after abbreviations such as "e.g."; a short line without closing punctuation before a capitalised line, or a list marker, starts a paragraph, since PDF text lacks empty lines; whole sentences of up to `PassageOverlap` 120 characters repeated; over-long runs cut at spaces), `AddImage(bytes, mediaType, location, isPage)`, `Build(embeddingModel, progress, cancellationToken)` (passages in batches of 8, then images one at a time; needs `SupportsImages` if images were added) and `Search(model, query)` (every passage and image with its cosine similarity, best first).
- Tested by `TestDocumentSplitText` (no model) and `TestDocumentIndex` (4 pages and 2 photos, each question finds its page and "flowers" the tulips).
- `VideoMomentIndex` (`Emgu.LiteRT.LM.Models/VideoMomentIndex.cs`) finds the moments of a video a text describes, the way Google AI Edge Gallery's Video Moment Finder does (`Android/.../customtasks/videomomentfinder`).
  - **Indexing:** `Split` cuts the video into `WindowMs` 2000 windows, with `OverlapMs` 0 and steps of at least a second. Each window has `FramesPerWindow` 2 frame times, spread from its start to its end inclusive. `BuildAsync(model, durationMs, frameAt, audioBetween)` takes each frame (and the window's 16 kHz sound) from the app's callbacks. It embeds a whole window as one `Embed(InputData[], 0, VisionTokensPerFrame 70)` request.
  - **The request layout:** with sound it is the model's timed one: `"00:00" <audio> "00:00" <frame> "00:01" <audio> ...`. The sound is split into one slice per frame (`SplitAudio`) and sent as WAV. Frames alone go without times.
  - **When the sound is left out:** if `EstimateTokens` would go over `MaxInputTokens` 1024. If the first window's audio fails, the whole video is indexed frames only, so its windows stay in one embedding space (`WithAudio`).
  - **Search:** `Search(model, query, topK 5)` embeds the query (`EmbedQuery`). `Rank` keeps the best `topK` windows, merges any within 0.5 s of each other into `VideoMoment`s and lists the best first. `Save`/`Load` keep an index.
  - **Tested by** `UnitTestVideoMoments` (no model) and `TestVideoMomentIndex`: a 20 s video of five 4 s test-picture scenes, with "have a wonderful day" spoken over the last.
    - On the M1's CPU, 10 windows take 10.0 s frames only and 10.6 s with sound, and each query's best moment covers its scene.
    - With sound, "someone saying have a wonderful day" ranks the spoken window first (0.750, against 0.640 frames only).
    - A window's last frame is the next scene's first, so the window before a scene partly matches it ("a dog": 00:02-00:06 with LiteRT-LM v0.18.0). With v0.19.0 that window and the scene's own nearly tie (00:02-00:04 0.727, 00:06-00:08 0.723), so the test now searches with the feature's `topK` 5 instead of 2 ("a dog": 00:02-00:08).
  - **Sparse windows** (2026-10-30): `StrideMs` sets how far apart windows start (0: `WindowMs` - `OverlapMs`), e.g. a 2 s window of one frame every 10 s, and `MaxWindows` keeps only the first windows; file version 2 saves both (version 1 files still load). `Emgu.LiteRT.LM.Chat`'s `VideoLibraryIndex` ("Search my videos") indexes a device's videos this way, about a minute of work per minute of video on a Galaxy S10 instead of 7.5.

## Speech recognition: OmniEngine, omniextern, Parakeet-TDT-0.6B-v3 and Qwen3-ASR-0.6B

- LiteRT-LM runs speech recognition models in its experimental "Omni" engine (`omni/`: `OmniEngine`, `OmniRegistry`, and in `omni/speech2text` a log-mel preprocessor, CTC/TDT/LM decoders and text mergers; `omni/asr` and its `AsrEngine` before v0.19.0), which has no C API. `litertextern/omniextern` is ours (called `asrextern` before v0.19.0): a small C API (`omniextern_*`) over it, built as its own library (`libomniextern`, staged into the LiteRT-LM workspace like `tfliteextern` and built with `--define=litert_runtime_link_mode=dynamic`, so it links against our `libLiteRt`; see `docs/native-builds.md`).
  - `omniextern_engine_create(model_name, model_path, tokenizer_path, backend, threads, overlap, text_merger, &engine)` calls `OmniEngine::Create(model_name, settings, &Speech2TextSessionConfig)`: the model is one a linked `alwayslink` target registered (`//omni/speech2text:parakeet_tdt` and, since 2026-11-02, `:qwen3_asr`), loaded from its local `.litertlm`, which holds the tokenizer (since v0.19.0 the speech models load only from `.litertlm`; `tokenizer_path` is ignored). The overlap and the merger (`TEXT_MERGER_TYPE_LEVENSHTEIN` / `_TIMESTAMP`) are set from the arguments; LiteRT-LM's defaults are 0.75 and the timestamp merger.
  - A session reads a `PushInputSource` (LiteRT-LM's): `push_audio` pushes `AudioInput`s, `end_audio` `EndOfInput`; the session cuts them into the model's 5 s windows itself, and resamples (`AudioInputMetadata`, 16 kHz from us). `omniextern_session_process` returns the next window's confirmed text and the guess after it; `NotFound` (no whole window yet) is "need audio", and after the end of the audio it `Flush`es every stage for the rest of the text.
  - Every function catches C++ exceptions and returns a status code with a thread-local message (`omniextern_get_last_error_message`), like LiteRT-LM's C API.
- `Emgu.LiteRT.LM`'s `SpeechToTextEngine` / `SpeechToTextSession` / `SpeechToTextResult` (`SpeechRecognition.cs`, `OmniInvoke`, `DllImport("libomniextern")`, `@rpath/omniextern.framework/omniextern` on iOS; `AsrEngine` etc. before) wrap it, throwing `LiteRtLmException` with the status; `PushAudio` may come from another thread than `Process`. `Emgu.LiteRT.LM.Models`' `SpeechToTextModel` downloads the file and `TranscribeAsync(samples, sampleRate, partial)` resamples to 16 kHz, pushes the audio and joins the windows' confirmed texts; `CreateSession()` is for live audio; `OverlapRatio` (default 0.4) and `TextMerger` are set before `Init`. `ParakeetTdt06BV3` is NVIDIA's Parakeet-TDT-0.6B-v3: `parakeet_tdt_0.6b_v3_5s_i8_stateful.litertlm` (614.6 MB, litert-community, the model and its tokenizer; `ObsoleteFileNames` lists the `.tflite` and `tokenizer.json` used before v0.19.0, which the demo deletes). Its compiled-model cache is named after the model, not the file (`parakeet-tdt-0.6b-v3_<id>_<size>.xnnpack_cache`, 601 MB; `RegisteredName`), so `StorageModel.Speech` takes cache names. 25 European languages, detected by the model, with punctuation and capitals. Its weights are **CC-BY-4.0**: an app using them must credit NVIDIA.
- CPU only: `Init` refuses "gpu" (the model card measured the mobile GPU slower for its decoding loop; v0.19.0 runs Parakeet's encoder on the GPU and its decoder on the CPU - not tried).
- **The text merger.** On a 34 s English `say` sample LiteRT-LM v0.18.0's timestamp merger repeated a phrase at one seam ("sign up for a library card, and look at the for a library card, and learn"), so `ParakeetTdt06BV3` uses the Levenshtein merger; each window's text starts with a capital ("morning, Clearing by the afternoon"), so `SpeechToTextModel.Append` lowercases a piece's first word inside a sentence unless it looks like a name ("I", inner capitals, or a capitalized word next: "City Library"). A one-word name at a seam is lowercased ("paris is next").
- **The Levenshtein merger dropped text (LiteRT-LM v0.18.0; fixed in v0.19.0).** It took the first matching word of a whole-length alignment as where two windows overlapped, so a word that happened to match ("did", "the") became the anchor and the 2-3 s between were dropped: 22.8% of a clean 56 s synthetic meeting's words in one session, 45.6% of a Pixel Fold's recording of it from across a room, and most of the 15.2% wrong on noisy turns. LiteRT-LM's `b34761f3` and `b2f2d9d9` stitch at the longest run of matching words instead. Measured on the Mac with the same recordings (2026-11-01, one session per recording; the time for the Mac idle):

  | Merger, overlap | Clean turns | Noisy turns | Whole meeting (56 s) | Fold recording (100 s) | Time for the clean turns (57 s) |
  |---|---|---|---|---|---|
  | v0.18.0, Levenshtein 0.4 | 0% | 15.2% | 22.8% | 45.6% | 3.1 s |
  | Levenshtein 0.4 (the default) | 0% | 1.3% | 1.9% | 11.4% | 4.0 s |
  | Levenshtein 0.75 | 0% | 1.3% | 0% | 7.6% | 5.0 s |
  | timestamp 0.4 | 0% | 1.3% | 1.9% | 10.8% | |
  | timestamp 0.75 (LiteRT-LM's defaults) | 3.8% | 5.1% | 29.1% | 39.9% | |

  - With noise Parakeet now gets fewer words wrong than Apple's recognizer (5.7%) and Google's (4.4%) on the same turns. 0.75 is a little more accurate on long recordings at 1.25-2x the time (phones are 4-5x slower), so the default stays 0.4.
  - Measured before the fix and not taken: overlap 0.6 (fewer drops, but still some), cutting long audio into 15-28 s sessions at its pauses, and noise removal (CMGAN took the noisy turns to 2.5% but the Fold recording to 76.6%, DTLN 5.7% and 22-28%).

- **Qwen3-ASR-0.6B** (2026-11-02, `Qwen3Asr06B`, registered as `qwen3-asr-0.6b`): Alibaba Qwen's model (Apache-2.0), 30 languages from its model card (Chinese, English, Cantonese, Arabic, German, French, Spanish, Portuguese, Indonesian, Italian, Korean, Russian, Thai, Vietnamese, Japanese, Turkish, Hindi, Malay, Dutch, Swedish, Danish, Finnish, Polish, Czech, Filipino, Persian, Greek, Hungarian, Macedonian, Romanian) plus Chinese dialects, detected itself. litert-community's `qwen3_asr_0.6b_5s_i8.litertlm` (960 MB, pinned at revision `80384dfb`; the repository also has `.tflite` files and per-SoC NPU builds, not used). ## Text to image: OmniEngine, omniextern, Bonsai Image and FLUX.2-klein

- The same `libomniextern` registers LiteRT-LM's two text-to-image models (`//omni/text2image:bonsai_flux2` and `:flux2_klein`, alwayslink, since 2026-11-01). `omniextern_image_engine_create(model_name, model_path, backend, threads, size, cache_dir, &engine)` calls `OmniEngine::Create(model_name, settings, &Text2ImageSessionConfig)`; `omniextern_image_generate(engine, prompt, steps, seed, &rgb, &width, &height, &channels)` makes a session on a `PushInputSource`, pushes an `ImageGenInputMetadata` (steps, seed) and the `TextInput`, and copies the `ImageOutput` (RGB888) into a buffer freed with `omniextern_free_buffer`. Same status codes and thread-local messages as the speech functions.
- What LiteRT-LM's text2image does (v0.19.0): the picture's size comes from the session config when the stages are built (a prompt's own width/height is ignored), and both `.litertlm` files hold 256 x 256 graphs only (512 fails building the stages); steps and seed are per picture, seed 0 meaning its fixed 42; there's no progress and no way to stop a picture (`OmniSession` has no cancel; one `ProcessNext()` draws it); the GPU stages are forced to FP32 (`force_fp32_on_gpu`, FLUX.2's denoiser degrades in FP16); the caches are named after the graphs (`flux2_dit_...`), the same for both models, hence the `cache_dir` argument.
- `Emgu.LiteRT.LM`'s `TextToImageEngine` (`TextToImage.cs`, imports in `OmniInvoke`) and `TextToImageResult`; `Emgu.LiteRT.LM.Models`' `TextToImageModel` (`Download`, `Init(backend, threads)`, `GenerateAsync(prompt, seed, steps, cancellationToken)` one at a time, `CacheFolder`), `BonsaiImage4B` and `Flux2Klein4B` (256 x 256), and `BonsaiImage4B512` (Emgu's 512 x 512 repackaging, its own cache folder since it has the same registered name). Measurements and model notes: `Emgu.LiteRT.Models/MODELS.md` ("Bonsai Image and FLUX.2-klein"). Tests: `UnitTestTextToImage.cs` (model-free argument checks; `TEST_MODELS` for drawing with each model, the same seed giving the same bytes, cancellation, a size that isn't a multiple of 16).

## Text to speech: OmniEngine, omniextern and Kokoro 82M

- `libomniextern` registers LiteRT-LM's Kokoro (`//omni/text2speech:kokoro`, alwayslink, since 2026-11-01). `omniextern_tts_engine_create(model_name, model_path, backend, threads, language, voice, cache_dir, &engine)` doesn't go through `OmniEngine` (which hides its factory): it calls `OmniRegistry::Get().CreateSessionFactory` with a `Text2SpeechSessionConfig` and keeps the factory, a `TtsSessionFactory` - so `omniextern_tts_engine_get_voices` / `_get_languages` / `_get_default_voice` can ask it - and makes a session once to check the voice (a voice of another language is `INVALID_ARGUMENT`: "Voice 'bf_emma' (language: en-gb) conflicts with requested language 'en-US'"). `omniextern_tts_synthesize(engine, text, &pcm, &count, &sample_rate)` makes a session per call on a `PushInputSource`, pushes the `TextInput`, `Finish()`es, collects every `AudioOutput` `ProcessNext` gives and what `Flush` still holds (24 kHz mono floats, `omniextern_free_buffer`). The language and voice are fixed per engine; a new engine loads in well under a second once the caches are written.
- **Every acoustic run costs about the same:** Kokoro's acoustic model and vocoder have fixed-size frames (about 124 phonemes, 10 s of speech), so "Hello." costs as much as a long sentence (M1 Metal: 0.74 s for 1.35 s of audio, 0.50 s for 3.67 s; Galaxy S10: about 2.2 s for either). LiteRT-LM's default text chunking cuts at every sentence and clause end (`TextChunkConfig`'s delimiters), a run each; `omniextern` sets the delimiters to line breaks only, and the chat packs sentences into pieces of about 120 characters (`VoiceEngines.SpeechPieces`: the first sentence alone so speech starts sooner, then the next ones together) - three short sentences in one call took 0.49 s on the M1 against 1.40 s one by one. Kokoro still splits a text too long for one run by itself.
- Two files with the same weights (`litert-community/Kokoro-82M`, pinned revision): `kokoro_int8_gpu_fp16.litertlm` (the vocoder's INT8 weights on the GPU; on the CPU its audio is noisier - about 30% more energy above 8 kHz than the CPU file's on the M1) and `kokoro_int8_fp16.litertlm` (dequantized for clean CPU audio, about twice the memory). On an M1, 12.8 s of English: the GPU file on Metal 1.7 s (RTF 0.13, 0.33 GB peak), on the CPU 3.5 s (RTF 0.27, 0.50 GB), the CPU file on the CPU 9.4 s (RTF 0.73, 0.94 GB). All 9 languages and dialects about 0.5 s a sentence on Metal; 54 voices (Kokoro's convention: the first letter is the language, the second f/m).
- `Emgu.LiteRT.LM`'s `TextToSpeechEngine` (`TextToSpeech.cs`, imports in `OmniInvoke`); `Emgu.LiteRT.LM.Models`' `TextToSpeechModel` (`Download`, `Init(backend, threads, language, voice)`, `SetVoiceAsync`, `SynthesizeAsync` one at a time, `GetVoices`/`Languages`/`GetDefaultVoice`, `CacheFolder`) and `Kokoro82M(gpuFile)` (`VoiceLanguage`, `DescribeVoice`). Tests: `UnitTestTextToSpeech.cs` (each language, the voices, a voice of another language, packing, and Parakeet hearing what Kokoro says - "Have a wonderful day. The library opens at 9 tomorrow morning." word for word). The chat's use (`ChatVoice`, Settings > Voice) and the Galaxy S10's numbers (about 2.2 s a run on its GPU whatever the length; three sentences said in 15.6 s for 12.8 s of speech): `Emgu.LiteRT.Example/Maui/FEATURES.md`, "Voice". `libomniextern` grew by about 1 MB with Kokoro (macOS 21.8 to 23.0 MB, Android arm64 18.5 to 19.4 MB).

## Emgu.LiteRT.LM.Extensions.AI: IChatClient

- `Emgu.LiteRT.LM.Extensions.AI/` (own `Emgu.LiteRT.LM.Extensions.AI.dll` and nuget package, namespace `Emgu.LiteRT.LM.Extensions.AI`, netstandard2.0 + net8.0 + ios/maccatalyst - net8.0 because the netstandard2.0 build gets `IAsyncEnumerable` from `Microsoft.Bcl.AsyncInterfaces`, which isn't deployed on runtimes that have it built in, so a net10 app failed to load it; depends on `Emgu.LiteRT.LM.Models`, `Emgu.LiteRT.LM` and `Microsoft.Extensions.AI.Abstractions`, so the other LiteRT-LM packages don't depend on Microsoft.Extensions.AI) implements Microsoft.Extensions.AI's `IChatClient` over a `LanguageModel` (`LiteRtLmChatClient`, `model.AsIChatClient()`), so the models work with `ChatClientBuilder.UseFunctionInvocation()` tool calling and Microsoft Agent Framework (`ChatClientAgent`).
- Text, `DataContent` images/audio, `TextReasoningContent` (thinking via `ChatOptions.Reasoning`: effort None = off), `FunctionCallContent`/`FunctionResultContent`, `ChatOptions.Instructions`/system messages, `MaxOutputTokens`.
- `IChatClient` is stateless, so the client keeps one LiteRT-LM conversation open (with a key per message it contains, and a settings key of system message/tools/thinking/max tokens) and, when a request only adds one message to it, sends just that; otherwise it rebuilds the conversation seeded with all but the last message (always, for models without `SupportsMultiTurnConversation`).
- Verified that tool rounds and agent sessions reuse it.
- **`SendMessage`/`SendMessageStream` take one JSON object since v0.19.0** (`conversation.cc`: "Message must be a JSON object"); v0.18.0 also took an array of messages (`message.is_array()`), which the client used to append a media tool result - its acknowledgement and the image turn (`ExpandToolMedia`) - in one call, keeping the conversation's cache. A conversation's *history* (`ConversationConfig` messages) can still be an array. So when a request adds more than one message, the client now rebuilds the conversation with all but the last as its history and sends the last alone: a camera capture re-reads the conversation (`GemmaDescribesImageReturnedByCameraTool` no longer expects the same conversation object after the second capture). Not reported upstream yet. Sending the two messages one after the other would make the model answer the bare acknowledgement; one user message with the image would drop the tool-role turn.
- `LanguageModel` gained `SupportsToolCalling` (true for `Gemma4`) and an `EngineReleasing` event the client uses to release its conversation.
- LiteRT-LM tool facts (checked against Gemma 4 E2B with v0.17.1 and v0.18.0): `ConversationConfig.ToolsJson` takes `[{"type":"function","function":{name,description,parameters}}]`; replies carry `"tool_calls":[{"type":"function","function":{"name","arguments":{...}}}]` (no ids - the client generates them and maps them back to names; since 2026-10-26 it also learns the names from the `FunctionCallContent`s of each request, so a chat continued with a new client - the model reloaded on another backend or context window, a restored agent session - can answer the previous client's calls), arriving as one streamed chunk; tool results must be sent as `{"role":"tool","content":[{"type":"tool_response","name":...,"response":...}]}` (the shape LiteRT-LM's Swift API uses; the nested `"tool_response":{"name","value"}` shape from its processor test is ignored by Gemma 4's template).
- Constrained decoding (`ConversationConfig.EnableConstrainedDecoding`; `LiteRtLmChatClient.EnableConstrainedDecoding`, on by default; `TestChatClientTools` runs it off, `TestChatClientToolsConstrained` on) works with v0.18.0 but crashes the process with v0.17.1 (SIGSEGV in `CompositeLogitMask::Apply`): that tag ships a stale prebuilt `libGemmaModelConstraintProvider` (2026-08-26, LFS commit 3dc788a4) whose `FstConstraint` predates the `Constraint::ComputeMask` virtual added 2026-08-21, so `liblitert-lm`'s `ComputeMask` call lands on the prebuilt's `ComputeBitmap` and the returned `Bitmap` is used as a `LogitMask`; v0.18.0 ships the fixed 2026-09-16 prebuilt.
- With context management a round's output budget is `ChatOptions.MaxOutputTokens`, else `DefaultMaxOutputTokens` (4,096 since 2026-10-28; it was a hard-coded 1,024, which cut worksheet answers off at ~1,600 characters without a word), never more than the window has left; its thinking at most `MaxThinkingTokens` (1,024; it was 256, which cut Gemma 4 12B's thinking off mid-formula, and the model went on thinking in the answer until the length limit) and a third of the budget. A reply that hits the budget ends with `FinishReason.Length`, and `ChatConversation` adds `CutOffNotice` under it (not given to the model). On the Pixel Fold with E2B, "when you see a person, play a sound and take a picture" thought for 142 s at 1,024 and 160 s at 256 (an extra tool round), with the same monitor.

## Thinking with images or audio in the initial messages (LiteRT-LM v0.18.0 bug, fixed in v0.19.0)

- LiteRT-LM v0.18.0 bug, worked around in `Chat` and `LiteRtLmChatClient` until the v0.19.0 update: with thinking, each new message makes LiteRT-LM rewind the conversation and re-read it without the previous reply's thinking (`filter_channel_content_from_kv_cache`, `Conversation::RewindAndGetInputDataVector`), and when that re-read includes the conversation's initial messages (`ConversationConfig.MessagesJson` - a reopened chat, after compaction, or any rebuilt `IChatClient` conversation) it renders their image/audio placeholders but passes only the newer messages' media, so the second message after such a rebuild failed; both now set `ConversationConfig.FilterChannelContentFromKvCache = false` when the initial messages have attachments (the thinking then stays in the KV cache).
- v0.19.0 reworked that filtering (`97e6dc7d` "Eagerly filter channel content from KV cache after decode", `3717c6da`): `TestHistoryWithImageAndThinking` passes without the workaround (it failed every time without it on v0.18.0), so the workaround was removed (2026-11-01); the thinking is filtered from the KV cache again.

## Thinking with tools crashes the Windows build (LiteRT-LM v0.19.0: the prebuilt constraint provider's std::vector layout)

- **Symptom (2026-11-02):** on Windows, a conversation with tools (constrained decoding is on by default with tools) and thinking on aborts the process on the first decode step, on the CPU and the GPU alike: exception code `0xc0000409`, a `std::length_error` that nothing catches, so `terminate`. It is the demo's default (Think on, with tools). Thinking alone, tools alone and tools with constrained decoding but no thinking all work.
- **Where:** LiteRT-LM v0.19.0 wraps the user's constraint in `ThinkingBudgetConstraint` whenever thinking is on (`runtime/core/tasks.cc`). Its `ComputeMask` copies the user mask's words inline: `std::vector<uint64_t> words(bitmap.words().begin(), bitmap.words().end())` after `static_cast<const BitmapLogitMask&>`. The user constraint comes from the prebuilt `libGemmaModelConstraintProvider.dll`, and that mask object was made by the DLL's own copy of `BitmapLogitMask`.
- **Cause (checked in a debugger run, with the mask object's memory):** the prebuilt DLL's `std::vector` is laid out as {data, size, capacity} (its constructor compares `[+0x18]` against a word count, its resize helper and destructor treat `[+0x10]` as a capacity in elements: the mask held `ptr, 0x2003, 0x2003`), while `liblitert-lm.dll` built by `bazel_build_litert.ps1` (the MSVC STL, as upstream's own Windows CI builds) lays it out as {first, last, end}. Reading `last - first` then gives a negative size and `std::vector`'s constructor throws `length_error`. Which toolchain built the DLL isn't documented (the dump shows an STL that isn't MSVC's); the DLL is from LiteRT-LM's commit `d99b438f` (2026-10-09), the same as every platform's, and the other platforms work. Anything else that crosses the DLL boundary as a standard-library type would have the same problem; only this inline read is known.
- **How it was found:** the app's crash dumps (`%LOCALAPPDATA%\CrashDumps`; `dotnet-dump` can't print a native stack, so a small script walked the thread's stack and symbolized it with `llvm-symbolizer` and the Bazel-built `litert-lm.pdb`), the disassembly of `ComputeMask` (`llvm-objdump`), and a small debugger of our own (Win32 debug API + DbgHelp) that stops on the first-chance `length_error`, unwinds to the `ComputeMask` frame and reads `r14`'s object.
- **Fixed in our build (2026-11-02): a patched copy of LiteRT-LM.** `platforms/windows/litert_lm_patches/foreign-bitmap-mask.patch` adds `IsHostBitmapLogitMask(mask)` (the mask's vtable pointer is this binary's `BitmapLogitMask` vtable; the `type_info` names of the two classes are equal, so RTTI can't tell them apart) and uses it at the four places that read a bitmap mask's words directly: `ThinkingBudgetConstraint::ComputeMask` (a foreign bitmap takes the existing overlay path), `ApplyCompositeImpl` (applied through its own virtual `Apply`), `CollectMasks` of the GPU mask runner (reported as unsupported, so the caller masks on the host) and the composite constraint's bitmap wrapper (the allowed tokens are found by applying the mask to a zeroed logit vector). `bazel_build_litert.ps1` stages a copy of the submodule (`p` next to `o` and `u`, with its own Bazel output base `q`, rebuilt only when the pinned commit or a patch changes; the submodule isn't edited), applies the patches and builds `liblitert-lm.dll`, `omniextern.dll` and the accelerator from it; `-NoLiteRtLmPatches` builds from the pristine submodule. Checked on the CPU and the GPU (RTX 3070): tools, constrained decoding and thinking together (`TestChatClientToolsWithThinking` with the client's defaults), the GPU chat and embedding tests, and the packaged demo with Think on. `LiteRtLmChatClient.EnableConstrainedDecodingWithThinking` is on by default again (turn it off with a Windows liblitert-lm built without the patch). A first full build of the patched tree takes about 20 minutes. Still to do: report it to LiteRT-LM (the provider and the host must be built with the same standard library, or `ThinkingBudgetConstraint` and the others must not read the mask's words inline), and drop the patch when it is fixed.
