# Native builds

How the native libraries (`tfliteextern`, `libLiteRt`, `liblitert-lm`) are built for each platform, and the commands. Moved here from CLAUDE.md, which keeps the short version.

## Overview

- **Windows x64 (both CMake and Bazel)**, **macOS (Bazel)**, **iOS/Mac Catalyst (Bazel)**, **Android (Bazel)**, **Ubuntu (Bazel)**, and **Debian ARM (Bazel)** build against `litert/tflite` (the `google-ai-edge/LiteRT` submodule). There is no `tensorflow/` submodule in this repo.

## CMake (Windows and macOS)

- CMake (Windows and macOS) builds directly from `litertextern/tfliteextern/`; `litert/tflite`'s own CMake project downloads the extra TF source it needs (e.g. MLIR/compiler files) itself via `FetchContent` at configure time. `litertextern/tfliteextern/CMakeLists.txt`'s `APPLE` branch picks its output subfolder (`runtimes/osx/native/arm64` or `.../x64`) via the same self-detected `IS_ARM64` (`check_symbol_exists("__aarch64__", ...)`) the `WIN32`/Linux branches already used — it used to check `EMGUCV_ARCH`, an Emgu.CV-only convention nothing in this repo ever sets, so it silently always fell into the x64 branch. `litert/tflite`'s own `profiling/proto`, `tools/benchmark/proto` (and transitively `model_runtime_info_proto`) CMake targets pass `protoc` a `--proto_path=${TENSORFLOW_SOURCE_DIR}` that doesn't encompass their actual `.proto` files (which live under `litert/tflite/`, not the separate FetchContent-downloaded TF tree `TENSORFLOW_SOURCE_DIR` points at) — breaking a plain `cmake --build .`, even though `tfliteextern` itself doesn't depend on any of them and builds fine alone. Since litert is a pristine submodule we don't patch upstream, `litertextern/tfliteextern/CMakeLists.txt` marks `profiling_info_proto`/`model_runtime_info_proto`/`benchmark_result_proto` `EXCLUDE_FROM_ALL` after the `ADD_SUBDIRECTORY` call instead, fixing `cmake --build .` generally; `platforms/macos/cmake_build_tflite` still targets `tfliteextern` specifically anyway, to skip litert's unrelated benchmark/example targets entirely. On macOS, `TFLITEEXTERN_LINK_LITERT` (an option in `litertextern/tfliteextern/CMakeLists.txt`, on by default for macOS only) makes the project `ADD_SUBDIRECTORY` LiteRT's own CMake project (`litert/litert`, which adds `litert/tflite` itself) instead of `litert/tflite` alone, and link `tfliteextern` against its `litert_runtime_c_api_shared_lib` (`libLiteRt.dylib`) — the same split as the Bazel build. On Apple, LiteRT's CMake links `libLiteRt` with `-all_load` and no export list, so it exports the `TfLite*` C API tfliteextern needs (and ~10k symbols in all — 14.9 MB for arm64 vs 6.8 MB from Bazel), and links Metal itself. `platforms/macos/cmake_build_tflite` configures with `CMAKE_BUILD_TYPE=Release` (the Makefile generator ignores `--config`) and `CMAKE_POLICY_VERSION_MINIMUM=3.5` (as LiteRT's presets do, for CMake 4). The CMake build's TFLite reports the TensorFlow version `litertextern/tfliteextern/CMakeLists.txt` finds - `TFLITEEXTERN_TF_VERSION` if given, else the `GIT_TAG` litert/tflite's CMake downloaded (2.21.0-rc0 up to LiteRT `26895c9f`; at `dcb657e8` it no longer downloads TensorFlow), else the `tflite_version.txt` the Bazel builds write (2.23.0 with LiteRT-LM v0.19.0; so build macOS with Bazel first) - and defines `TF_MAJOR_VERSION` etc. from it before adding LiteRT's directories; LiteRT's own CMake hard-codes a stale 2.19.0 on its `tensorflow-lite` target (or, before the v0.18.0 update, defined nothing, so `version.h` fell back to it) - ours comes later on the compiler command line and wins, with harmless `-Wmacro-redefined` warnings) vs 2.22.0-dev0 from Bazel (LiteRT-LM's `TENSORFLOW_REF`). Windows/Linux CMake builds keep the statically linked tfliteextern. Only single-arch (host) builds are supported from CMake — setting `CMAKE_OSX_ARCHITECTURES` to build a universal arm64+x86_64 binary in one pass breaks that same `check_symbol_exists()` detection, since it only compiles for one architecture at a time; a fat binary would need separate per-arch builds `lipo`'d together, as the Bazel path already does.

## Bazel: staging into the LiteRT-LM workspace

- Bazel needs the wrapper package to live *inside* a LiteRT(-LM) workspace (a pristine submodule we don't patch upstream), so `bazel_build_litert.ps1` (Windows), `bazel_build_macos` (macOS), `bazel_build_xcframework` (iOS), `platforms/android/bazel_build_tflite_android`, and the Ubuntu and Debian (`platforms/ubuntu/*/bazel_build_litert`, `platforms/debian/{bookworm,trixie}/bazel_build_litert`) scripts each copy `litertextern/tfliteextern/bazel/{BUILD,tfliteextern.def}` plus the shared `litertextern/tfliteextern/*.cc/.h` and `litertextern/imgproc/*.cc/.h` sources into a fresh `tfliteextern/` package inside that workspace on every run, then build from there. All of them stage into `LiteRT-LM/tfliteextern/` and build in the **LiteRT-LM** submodule's workspace, with the `BUILD` file's `//tflite`/`//litert` labels rewritten to `@litert//...` (LiteRT-LM's `WORKSPACE` fetches LiteRT as the external repository `@litert`, pinned to the same commit as the `litert` submodule — see the macOS bullet below). Bazel always fetches its own pinned TF archive (no local-submodule-reuse option — see the copied `BUILD`'s comments for why). The `BUILD` file's `.def`/`/DEF:` export-list trick is Windows-only (via `select()`); other platforms export every non-static symbol by default, verified by inspecting each build's symbol table. Switching Windows from `litert` to `LiteRT-LM` needed no change to the checked-in `litert_windows_exports.def` — verified by rebuilding `//tfliteextern:libLiteRt` against the newer commit and comparing `dumpbin /exports` (653 live exports vs. 652 listed) and by re-running `Emgu.TF.Lite.Test.Net`'s `TestGetVersion` against the resulting `tfliteextern.dll`.
- **`omniextern`** (`litertextern/omniextern`: Emgu's C API over LiteRT-LM's C++ `OmniEngine`: speech recognition and, since 2026-11-01, text to image and text to speech; see `docs/litert-lm.md`; called `asrextern` before LiteRT-LM v0.19.0) is staged the same way into `LiteRT-LM/omniextern/` by the macOS, iOS (`bazel_build_xcframework`), Android, Ubuntu and Windows scripts, with no label rewriting (its deps are LiteRT-LM's own `//omni:omni_engine`, `//omni:omni_session`, `//omni:omni_registry`, `//omni/text2speech:tts_session`, `//runtime/proto:speech2text_session_config_cc_proto`, `:text2image_session_config_cc_proto` and `:text2speech_session_config_cc_proto`, and one `alwayslink` target per model it can load, which registers itself with `OmniRegistry`: `//omni/speech2text:parakeet_tdt` and `:qwen3_asr`, `//omni/text2image:bonsai_flux2` and `:flux2_klein`, `//omni/text2speech:kokoro` - which brings cppjieba (MIT) and kissfft (BSD) along). `//omniextern:omniextern` is a `linkshared` `cc_binary` modelled on `//c:litert-lm` and built in the same Bazel invocation, with `--define=litert_runtime_link_mode=dynamic`, so it links against `libLiteRt` too. Outputs: `lib/runtimes/osx/native/libomniextern.dylib` (arm64, 21.5 MB with v0.19.0 and Parakeet only, 21.8 MB with the two image models too - Android arm64 18.3 to 18.5 MB, iOS 21.0 to 21.3 MB: the FLUX.2 stages are small next to the shared omni code; same `copy_dylib` fix-ups), `lib/android/<arm64-v8a|x86_64>/libomniextern.so` (stripped, needs `libLiteRt.so`), `lib/ios/omniextern.xcframework` (wrapped like `LiteRtLm.framework`, `check_bound`, linked only to `@rpath/LiteRt.framework/LiteRt`), `lib/runtimes/ubuntu-*/native/libomniextern.so`, and on Windows `omniextern.dll` renamed to `libomniextern.dll`. Its functions catch every C++ exception and return a status code with a thread-local message (`omniextern_get_last_error_message`), like LiteRT-LM's C API. Like `liblitert-lm` before v0.19.0, it exports its dependencies' symbols too (Abseil etc.; `-fvisibility=hidden` only covers its own source); the libraries each bind their own copies (two-level namespace on macOS, `-Bsymbolic` on Linux/Android). The Ubuntu script changes haven't been built; the Windows one has (2026-11-01).

## The C API wrapper

- `tfliteextern.cc` uses only the TensorFlow Lite **C API** (`tflite/c/c_api.h`, `c_api_experimental.h`, `common.h`, plus `tflite/schema/schema_generated.h` for model introspection). The `tfe*` entry points the C# side P/Invokes are unchanged, but their opaque handles are now tfliteextern's own small wrapper structs (`TfeModel`, `TfeInterpreter`, ...) around the C API objects. Gaps vs. the old C++-API wrapper: `TensorSize`/`NodeSize` come from the model's primary subgraph (excluding tensors/nodes delegates add); the C API fixes the thread count at creation, so `SetNumThreads` before `AllocateTensors` re-creates the interpreter (re-applying delegates) and after it is ignored with a stderr warning; `DynamicBuffer` (string tensors) is reimplemented on top of the exported `TfLiteTensorReset`. Errors reported through `tfeRedirectError`'s callback are thrown as exceptions by the C# handler, which .NET can't unwind through native frames on macOS/Linux — so new non-fatal diagnostics go to stderr instead. On Android, NNAPI uses its C API (`TfLiteNnapiDelegateCreate`, part of `libLiteRt.so`); the TFLite GPU delegate V2 is C++, Android-only, and compiled out (`WITHOUT_GPU_DELEGATE`, `tfeGpuDelegateV2Create` returns null) in the dynamically linked Android build.

## macOS (Bazel)

- `//tfliteextern:tfliteextern` (a `cc_binary`, `linkshared`) is the shared-library form used by Windows (and the static-link fallback elsewhere), statically linking the TFLite C API. **macOS** instead builds `//tfliteextern:tfliteextern_dylib`, a `cc_shared_library` with `dynamic_deps = [":litert_runtime"]`: `:litert_runtime` builds `libLiteRt.dylib` from LiteRT's `//litert/c:litert_tflite_runtime_c_api_so_shim` (LiteRT's runtime, exporting both the `LiteRt*` and `TfLite*` C APIs via the staged `litert_exported_symbols_darwin.lds`), with the install name set and `-framework Metal` linked — LiteRT's own `litert_tflite_runtime_c_api_so` sets neither, and its `.bazelrc` builds macOS with `-undefined dynamic_lookup`, so its `MTLCreateSystemDefaultDevice` reference would otherwise only resolve if something else loaded Metal. `exports_filter` lets `tfliteextern_dylib` take every TFLite library from `libLiteRt.dylib`, so `libtfliteextern.dylib` is only the wrapper (~80 KB per arch vs ~7–9 MB when statically linked) and depends on `@rpath/libLiteRt.dylib` with an `@loader_path` rpath. `bazel_build_macos` builds these in the `LiteRT-LM/` submodule's Bazel workspace (Bazel 7.6.1 per its `.bazelversion`), against the LiteRT commit LiteRT-LM's `WORKSPACE` fetches as the external repository `@litert` (`dcb657e8` for LiteRT-LM v0.19.0, the same commit the `litert` submodule is pinned to), so `libLiteRt.dylib` comes from the same LiteRT source as LiteRT-LM's own `liblitert-lm.dylib` (built with `--define=litert_runtime_link_mode=dynamic`, it depends on `@rpath/libLiteRt.dylib`, and ours exports every `LiteRt*` function it calls). While staging, the script rewrites our `BUILD` file's `"//tflite`/`"//litert` labels to `"@litert//...`; that LiteRT has no `tflite/ios/ios.bzl`, so `BUILD` defines the iOS minimum version itself. `.gitmodules` sets `ignore = dirty` on both submodules, so the staged `tfliteextern/` packages don't show as changes. For `darwin_arm64` the script also builds LiteRT-LM's `//c:litert-lm` that way, as a separate Bazel invocation with `--platform_suffix=-litert_lm_dynamic` (the define can't apply to our targets — in dynamic mode LiteRT's C API libraries resolve to headers only — and isn't part of Bazel's output folder name, so without the suffix the two builds would overwrite each other's outputs), and copies it to `lib/runtimes/osx/native/liblitert-lm{-darwin_arm64,}.dylib` (install name fixed to `@rpath/liblitert-lm.dylib`) together with LiteRT-LM's prebuilt `libGemmaModelConstraintProvider.dylib` and (since v0.19.0) `libwebgpu_dawn.dylib` (Google's Dawn, 15 MB: the macOS build links LiteRT-LM's WebGPU top-k sampler as well as the Metal one, and `liblitert-lm.dylib` has a load dependency on Dawn; keeping only the Metal sampler with `--define=LITERT_GPU_ACCELERATOR=metal` fails Bazel's analysis with an ambiguous `select` together with the dynamic link mode), which it depends on and which are checked to be real Mach-O files, not Git LFS pointers. LiteRT-LM doesn't support Intel Macs (that prebuilt only exists for macOS arm64), so `liblitert-lm.dylib` is arm64 only, while `libLiteRt.dylib`/`libtfliteextern.dylib` stay universal; TFLite's kernels and XNNPACK remain inside `liblitert-lm.dylib` (19 MB with v0.19.0, which exports only the `litert_lm_*` C API; 27.5 MB before), since its embedding code uses TFLite's C++ API. Verified: loading `liblitert-lm.dylib` and `libtfliteextern.dylib` in one process maps a single `libLiteRt.dylib`. `bazel_build_macos <cpu>` builds both targets, copies them to `lib/runtimes/osx/native/{libtfliteextern,libLiteRt}-<cpu>.dylib` (dropping Bazel's extra `_solib`/runfiles rpaths, then re-signing ad hoc since `install_name_tool` invalidates the arm64 signature), and `lipo`s each into the universal `libtfliteextern.dylib`/`libLiteRt.dylib`; `bazel_build_macos_fat` drives `darwin_arm64` and `darwin`.
- `libLiteRt.dylib` is also what the `Emgu.LiteRT` C# classes (`Emgu.LiteRT/`, built by `Emgu.LiteRT/NetStandard/Emgu.LiteRT.csproj` into its own `Emgu.LiteRT.dll`, configured from `cmake/Emgu.LiteRT.*.in`) P/Invoke directly via `DllImport("libLiteRt")` — one runtime serves both the `Emgu.TF.Lite` (Interpreter) and `Emgu.LiteRT` (CompiledModel) APIs. GPU/NPU accelerators are optional plugin dylibs (`libLiteRtMetalAccelerator.dylib` etc.) it tries to load at runtime; without them it logs a warning and uses the built-in XNNPACK CPU accelerator. XNNPACK is part of `libLiteRt`, so on macOS the Interpreter API also uses it by default (the static builds still compile tfliteextern with `-DWITHOUT_XNNPACK`). When `lib/runtimes/osx/native/libLiteRt.dylib` exists, the top-level `CMakeLists.txt` adds it to the `Emgu.LiteRT.runtime.macos` nuspec next to `libtfliteextern.dylib`, and `Emgu.LiteRT.Runtime/Mac`'s `.projitems` copies it to the build output; the CPack zip already picks it up via its `*.dylib` install pattern.

## iOS

- **iOS** uses the same dynamic split as macOS and Android: `platforms/ios/bazel_build_xcframework` (one script since 2026-11-09: LiteRT, then LiteRT-LM; `--without-litert-lm` for the first part only) first builds the macOS targets `//tfliteextern:litert_runtime` and `//tfliteextern:tfliteextern_dylib` (both also `target_compatible_with` iOS) with `--config=ios_arm64` / `ios_sim_arm64` and `--ios_minimum_os` from `cmake/ios_min_version.txt` (15.0) in the LiteRT-LM workspace, and wraps them (its `wrap_framework`: install name `@rpath/<name>.framework/<name>`, references to the other libraries changed to their frameworks, Bazel's rpaths replaced by `@loader_path/..`, an `Info.plist`, ad hoc signing) into `lib/ios/LiteRt.xcframework` (LiteRT's runtime, ~6.5 MB per slice, `LiteRt*`/`TfLite*` exported - every one of `Emgu.LiteRT`'s 39 imports) and `lib/ios/tfliteextern.xcframework` (~80-100 KB, linked to `@rpath/LiteRt.framework/LiteRt`), device arm64 + simulator arm64. LiteRT-LM's `.bazelrc` applies its `build:macos` config on a macOS host even to iOS builds, including `-undefined dynamic_lookup`, so a missing symbol doesn't fail the link: the scripts' `check_bound` fails the build if `nm -m -u` shows any symbol not bound to a library. That found TFLite's iOS platform profiler calling `tflite::profiling::MaybeCreateSignpostProfiler()`, from the `objc_library` `//tflite/profiling:signpost_profiler`, which `cc_shared_library` silently leaves out (its graph aspect doesn't cover `objc_library`), so `:litert_runtime` passes that archive (`:signpost_profiler_archive`) to the link on iOS. `Emgu.LiteRT.Runtime/Maui/iOS`'s `.csproj` embeds both (`NativeReference Kind=Framework`), and the DllImports name them by path: `TfLiteInvoke.ExternLibrary` is `@rpath/tfliteextern.framework/tfliteextern` and `LiteRtInvoke.LiteRtLibrary` `@rpath/LiteRt.framework/LiteRt` on iOS (Mac Catalyst and Unity iOS keep the static `__Internal` tfliteextern). The top-level `CMakeLists.txt` sets `HAVE_IOS_LITE` when both xcframeworks exist. Before, iOS linked a static `tfliteextern` with its own TFLite into the app, and `Emgu.LiteRT` used the LiteRT inside LiteRT-LM's CLiteRTLM framework, so it needed the LiteRT-LM add-on and iOS 26.4.
- `//tfliteextern:tfliteextern_ios_framework` (a `cc_library` wrapped in `ios_static_framework`, no `hdrs` — the umbrella header rules_apple would generate collides with our own `tfliteextern.h`) is the static-library form, where `DllImport("__Internal")` finds the tfe* symbols in the app binary; the iOS runtime no longer uses it. No script builds it any more: `bazel_build_tflite_ios <config>`, which made `lib/ios/libtfliteextern_<config>.a` from it, and `bazel_build_mac_catalyst` were removed on 2026-11-09.
- **Mac Catalyst does not work through Bazel**: rules_apple/apple_support have no Catalyst platform, and a Bazel build for `darwin_<arch>` (what the removed `bazel_build_tflite_ios darwin_<arch>` and `bazel_build_mac_catalyst` did) actually produces **iOS Simulator** objects (`LC_BUILD_VERSION` platform 7, not Mac Catalyst's 6), which a Catalyst app can't link. Mac Catalyst loads the macOS dylibs instead (see Building, "Mac Catalyst").

## iOS and Mac Catalyst target frameworks

The bare `net10.0-ios` / `net10.0-maccatalyst` binds to the newest iOS bindings in the installed .NET workload, which need the matching Xcode (27.x bindings need Xcode 27), so a Mac with an older Xcode - the Intel Mac mini's maximum is 26.3 - couldn't build the same tree. The workloads still ship older bindings, so, as in Emgu CV (2026-11-05), `platforms/macos/apple_tfm_version.sh` (a copy of Emgu CV's) picks the platform version from the installed Xcode's iOS SDK, and the top-level `CMakeLists.txt` puts it in every generated `Directory.Build.props` as `${IOS_TFM_VERSION}`:

| Xcode | TFM |
|---|---|
| 27+ | `net10.0-ios` / `net10.0-maccatalyst` |
| 26.x | `net10.0-ios26.0` / `net10.0-maccatalyst26.0` |

Every 26.x Xcode uses 26.0, not its own minor version: each SDK pack accepts only its own version plus 26.0, so a version like 26.5 stops being valid once a newer workload is installed (`NETSDK1140`). Override with `EMGU_IOS_TFM_VERSION=<ver>` (the script) or `-DIOS_TFM_VERSION=<ver>` (CMake); on other hosts it is empty. Re-run CMake after changing Xcode. Commands that name the TFM - `dotnet build -f`, the `bin/Debug/<tfm>/` paths, `run_catalyst`, `make_licenses.py` and the `ios` CI job - use the same script. Checked on the Intel Mac mini (Xcode 26.3, workload with 26.x and 27.x packs): the demo's C# builds as `net10.0-ios26.0`.

The minimum iOS version is in `cmake/ios_min_version.txt` (15.0), and only there: `platforms/ios/bazel_build_xcframework` (`--ios_minimum_os` and each framework's `MinimumOSVersion`), and the iOS `SupportedOSPlatformVersion` of the generated props of the MAUI projects (the demo, MauiChat, the `Emgu.LiteRT.LM.Maui*` and `Models.CV.Maui` libraries, the two MAUI runtime packages) read it; the csproj files no longer set it, since a csproj value would override the props. The demo was 17.2 before; at 15.0 no call to an iOS 16+ API was reported (CA1416). The exception is `GemmaModelConstraintProvider.framework`, Google's prebuilt for iOS 26.4 (see "LiteRT-LM on iOS"): `LiteRtLm` links it, so whether the demo starts on an older iOS is untested.

## LiteRT-LM on iOS

- On **iOS**, LiteRT-LM's C API comes from the second part of `platforms/ios/bazel_build_xcframework`, which builds LiteRT-LM's C API per slice with `--define=litert_runtime_link_mode=dynamic --platform_suffix=-litert_lm_dynamic` (as on macOS) and wraps it into `lib/ios/LiteRtLm.xcframework`, linked to `@rpath/LiteRt.framework/LiteRt`, and `omniextern` into `lib/ios/omniextern.xcframework`. Since 2026-11-04 both come from `//omniextern_ios` (`litertextern/omniextern/bazel_ios`, staged next to `omniextern/`), two `cc_shared_library`s: `litert_lm` (LiteRT-LM's `//c:engine`, what `//c:litert-lm` is built from, exporting the runtime: 29 MB per slice, 21,000 symbols, the same 220 `litert_lm_*` functions) and `omniextern` (2.4 MB, only its `omniextern_*` functions exported) with `dynamic_deps` on it. Before, `//c:litert-lm` (18.6 MB) and `//omniextern:omniextern` (22.5 MB) each linked the whole runtime, and both registered miniaudio's Objective-C class `ma_ios_notification_handler`, so iOS warned at launch that the duplicate "may cause spurious casting failures and mysterious crashes"; now one copy, no warning (checked in the iOS 27.2 simulator, Qwen3-ASR and a Qwen3 0.6B chat, and on an iPad Air M4, also Gemma 4 E2B calling a tool with constrained decoding and thinking). The script also wraps LiteRT-LM's `prebuilt/ios_{arm64,sim_arm64}/libLiteRtMetalAccelerator.dylib` (Git LFS) into `lib/ios/LiteRtMetalAccelerator.xcframework` (2026-11-04): LiteRT loads its GPU accelerator by name - `dlopen("LiteRtMetalAccelerator")`, the executable of a `LiteRtMetalAccelerator.framework` (`litert/runtime/accelerators/gpu_registry.cc`, with no folder: LiteRT-LM sets no runtime library folder) - and dyld looks a bare name up in the calling library's rpaths, so its first part gives `LiteRt.framework` the rpath `@loader_path/../LiteRtMetalAccelerator.framework` (checked on a Mac with a test program: the caller's rpath is enough). On an iPad Air M4 the log then reads "Dynamically loaded GPU accelerator(LiteRtMetalAccelerator) registered": Gemma 4 E2B on the GPU loaded in 6.6 s and wrote 52 tokens/s, EmbeddingGemma 2 and Qwen3-ASR ran on it too. `cc_shared_library`'s graph aspect follows cc rules only, so what the C API reaches through `rust_library` (minijinja, llguidance, the tool-call parsers, tokenizers, the Rust standard library) and `objc_library` (miniaudio, TFLite's signpost profiler) isn't linked by it - LiteRT-LM's `-undefined dynamic_lookup` hid 84-94 unresolved symbols until the script's `check_bound` - so `static_archives.bzl` takes those archives from `//c:engine`'s `CcInfo` and passes them to the link (`-Wl,-filelist`; miniaudio `-force_load`ed, so `omniextern` binds to it).
- In dynamic mode LiteRT links LiteRT-LM against its own `libLiteRt.dylib`, which it builds as a **macOS** binary even in an iOS build (a `macos_dylib`), so the linker skipped it and `-undefined dynamic_lookup` left LiteRT-LM's 34 `LiteRt*` imports to flat lookup with no library recorded; the script passes the slice's `LiteRt.framework` binary to the link (`--linkopt`, a copy in a new folder each run, since Bazel doesn't track files named only there), which binds them all to it, and `check_bound` verifies nothing is left.
- As on macOS, TFLite's kernels, XNNPACK and much of LiteRT's runtime stay inside LiteRT-LM (its C++ code calls them), so the split saves little space (CLiteRTLM, with everything, was 28.3 MB per slice) - its point is that the base runtime works without LiteRT-LM and the packages match Android's.
- LiteRT-LM links LiteRT-LM's prebuilt `prebuilt/ios_{arm64,sim_arm64}/libGemmaModelConstraintProvider.dylib` (Git LFS), a loose dylib an app bundle can't contain, so the script wraps each slice into `GemmaModelConstraintProvider.framework` (`lib/ios/GemmaModelConstraintProvider.xcframework`).
- Google builds that prebuilt for iOS 26.4+, so LiteRT-LM needs iOS 26.4 at run time; the base frameworks need iOS 15. `Emgu.LiteRT.LM`'s `LiteRtLmLibrary` is `@rpath/LiteRtLm.framework/LiteRtLm` on iOS.
- **Not on an Intel Mac.** LiteRT-LM's Rust crates (`crates_repository` in `LiteRT-LM/WORKSPACE`, and `cxxbridge_cmd_deps`) list only the platforms of its patched `rules_rust` (`third_party/rules_rust/rules_rust.patch`): Apple Silicon Macs, Linux, Windows, iOS, Android and wasm, not `x86_64-apple-darwin`. Tools that run on the build machine (`cxxbridge_cmd`, the proc-macro crates) are then incompatible, and LiteRT-LM's build stops in the analysis phase: "Target //omniextern_ios:litert_lm is incompatible", the chain ending at `@cxxbridge_cmd_deps__clap-4.5.32//:clap` (2026-11-05, the Intel Mac mini). Adding the triple would mean patching LiteRT-LM and repinning its crate lockfile, so it isn't done: `bazel_build_xcframework` builds LiteRt and tfliteextern there, skipping LiteRT-LM by itself (24 minutes from a cold cache), and the demo builds without LiteRT-LM (its csproj's `EmguWithoutLiteRtLm`: the trimmer lists the frameworks `Emgu.LiteRT.LM`'s `DllImport`s name, `LiteRtLm` and `omniextern`, for the native link even when they aren't there, so the target removes them from `_LinkerFrameworks` and `--dlsym:+Emgu.LiteRT.LM.dll` looks their functions up at run time; `LiteRtLmInvoke.IsAvailable` is then false and the chat offers only its remote models). Run `bazel_build_xcframework` on an Apple Silicon Mac for the device models.
- The script used to build LiteRT-LM's own `//swift:CLiteRTLM` (`lib/ios/CLiteRTLM.xcframework`, with its own statically linked LiteRT) and deletes it.
- Verified in an iPhone 18 Pro simulator (iOS 27) with a temporary self-test: in one process the TF Lite Interpreter (`tfliteextern`, TFLite 2.22.0-dev0) and LiteRT's CompiledModel each recognized the space shuttle with MobileNet (1.0), Gemma 4 E2B loaded in 1.8 s and answered "Paris", and ZImageTurbo drew the watercolor fox (8 steps, 225 s, as fast as with CLiteRTLM), with one `LiteRt.framework` loaded.

## Android

- `platforms/android/bazel_build_tflite_android <arch>` (`x86`, `x86_64`, `arm`, `arm64`) stages the same `litertextern/` sources into the **LiteRT-LM** workspace exactly as the macOS script does (labels rewritten to `@litert//...`, so `libLiteRt.so` comes from LiteRT-LM's pinned LiteRT) and, like macOS, builds tfliteextern linked dynamically against LiteRT's runtime: `//tfliteextern:litert_runtime_so` (`libLiteRt.so` from `//litert/c:litert_tflite_runtime_c_api_so_shim`, exporting `LiteRt*`/`TfLite*` via the staged `litert_exported_symbols_linux.lds` version script, with `-Wl,-soname,libLiteRt.so` — LiteRT's own `litert_tflite_runtime_c_api_so` sets no SONAME, which would make `libtfliteextern.so` record a Bazel output path as its `DT_NEEDED`) and `//tfliteextern:tfliteextern_so` (`libtfliteextern.so`, `cc_shared_library` with `dynamic_deps`, sharing the `:tfliteextern_capi_lib` wrapper library with macOS). Both are copied to `lib/android/<abi>/` (matching what `Emgu.LiteRT.Runtime/Maui/Android`'s `.csproj` packages; it also packages `libLiteRt.so` when present). `libLiteRt.so` contains the TFLite C API, XNNPACK and the NNAPI delegate (C API - `:litert_runtime_so` lists `//tflite/delegates/nnapi:nnapi_delegate` and `:nnapi_delegate_no_nnapi_implementation` as Android deps itself, since LiteRT's runtime stopped pulling it in after the LiteRT-LM v0.17.1 commit, which made the v0.18.0 Android link fail with undefined `TfLiteNnapiDelegateCreate`) but not the TFLite GPU delegate V2 — LiteRT does GPU through its separate accelerator plugin — and that delegate needs TFLite internals `libLiteRt.so` doesn't export, so `:tfliteextern_capi_lib` defines `WITHOUT_GPU_DELEGATE` on Android. Each `.so` links its own static libc++ (most of `libtfliteextern.so`'s ~0.9 MB stripped size); only C APIs cross between them. The script strips both with the NDK's `llvm-strip --strip-unneeded` (found under `$ANDROID_NDK_HOME/toolchains/llvm/prebuilt/*/bin`, so it works from a Linux or macOS host): debug info otherwise roughly triples their size, and the dynamic symbol tables are unchanged (verified). Stripped sizes: `libLiteRt.so` 3.8–8.8 MB, `libtfliteextern.so` 0.6–0.9 MB depending on the ABI. Verified on an arm64 API 35 emulator: the MAUI demo loads both libraries and calls into `libLiteRt.so`. For `arm64` and `x86_64` it also copies LiteRT-LM's prebuilt GPU (OpenCL) accelerator `libLiteRtOpenClAccelerator.so`, and builds LiteRT-LM's `//c:litert-lm` with `--define=litert_runtime_link_mode=dynamic --platform_suffix=-litert_lm_dynamic` (as on macOS) and copies `liblitert-lm.so` (stripped; `DT_NEEDED` `libLiteRt.so`, `RUNPATH $ORIGIN`) plus LiteRT-LM's prebuilt `libGemmaModelConstraintProvider.so` to `lib/android/<abi>/`; that prebuilt only exists for those two ABIs, so `armeabi-v7a`/`x86` get no LiteRT-LM. Its 43 `LiteRt*` imports carry the `VERS_1.0` symbol version, which our `libLiteRt.so` (`litert_exported_symbols_linux.lds`) defines too — verified that every import of `liblitert-lm.so` and `libtfliteextern.so` resolves. On a Linux host with clang installed, the script adds `--repo_env=CC=clang --repo_env=CXX=clang++` so the host-side build tools (Bazel's `[for tool]` actions; Android code itself uses the NDK) are compiled with clang: Ubuntu 26.04's GCC 15 rejects Abseil's `raw_hash_set.cc` ("Never use <bmi2intrin.h> directly"). On a macOS host the script adds `--host_linkopt=-Wl,-undefined,dynamic_lookup`: LiteRT-LM's `build:android` sets `--noenable_platform_specific_config`, so its `build:macos` host link option doesn't apply, and without it the host Rust proc-macro dylibs its build tools need come out unloadable by dyld ("mis-aligned LINKEDIT string pool"), failing with rustc `E0463 can't find crate`. Verified on the arm64 API 35 emulator: the MAUI demo loads `libtfliteextern.so`/`libLiteRt.so` built this way and creates the XNNPACK delegate. Two things needed fixing beyond staging the sources:
- The statically linked `//tfliteextern:tfliteextern` (no longer what the script builds) still links the GPU delegate on Android: `litertextern/tfliteextern/bazel/BUILD`'s `_TFLITEEXTERN_DEPS` adds `//tflite/delegates/gpu:delegate` + `:delegate_options` (and NNAPI) behind a `select({"@org_tensorflow//tensorflow:android": [...], "//conditions:default": []})` — those targets need EGL and don't build on the other platforms.
- Of litert's four `.bazelrc` `android_*` configs, only `android_arm64` sets `--incompatible_enable_cc_toolchain_resolution`/`--incompatible_enable_android_toolchain_resolution`; the other three fall back to a legacy `--crosstool_top=//external:android/crosstool` alias that isn't actually defined anywhere in this WORKSPACE (it silently resolves to the host `local_config_cc` toolchain instead, which doesn't have a toolchain for a non-host cpu, or produces `/bin/false`-stubbed compile actions). The build script passes both flags explicitly for every arch to force the same NDK-toolchain-via-platforms resolution arm64 already gets from its config.

## Linux

- `platforms/ubuntu/24.04/bazel_build_litert` follows the same staging pattern, builds `//tfliteextern:tfliteextern` with `--config=linux` (`--config=linux_arm64` too on an aarch64 host), and copies the result to `lib/runtimes/ubuntu-x64/native/libtfliteextern.so` (or `ubuntu-arm64`), matching what `Emgu.LiteRT.Runtime/Ubuntu`'s `.projitems` expects. No GPU-delegate select() or toolchain-resolution override needed here — Linux isn't `__ANDROID__` and already resolves its host toolchain correctly. It also builds `liblitert-lm.so` and `libomniextern.so` and copies LiteRT-LM's prebuilt `libGemmaModelConstraintProvider.so` and, since v0.19.0, `libwebgpu_dawn.so` (Google's Dawn, which LiteRT-LM's WebGPU sampler links, as on macOS and Windows) next to them; both are Git LFS files, checked to be real ELF libraries (`git -C LiteRT-LM lfs pull`). The CI fetches only the files each job needs (`--include=` in `.github/workflows/native.yml`): a prebuilt the build starts linking has to be added there too, or the job fails (Dawn's pointer file: `libwebgpu_dawn.so:1: unknown directive: version` on Linux, "not a Mach-O library" on macOS; 2026-11-01 to 11-03).
- `platforms/debian/{bookworm,trixie}/bazel_build_litert` (identical files) build `//tfliteextern:litert_runtime_so` and `//tfliteextern:tfliteextern_so` on a native ARM Debian host (`--config=linux --config=linux_arm64` on 64-bit, plain `--config=linux` on armhf) with clang forced via `--repo_env=CC=/usr/bin/clang` (GCC >= 14 rejects LiteRT's `target("dotprod")` attribute), and copy `libLiteRt.so`/`libtfliteextern.so` to `lib/runtimes/linux-arm64/native/` (or `linux-arm`). They also write `debian_version.txt` (the release codename, e.g. `trixie`, from `/etc/os-release`) there for the nuget package ids, as the Ubuntu scripts write `ubuntu_version.txt` (see `docs/packaging.md`).
- On arm64 they also build `liblitert-lm.so` and `libomniextern.so` (as the Ubuntu script does, `--define=litert_runtime_link_mode=dynamic`), but by default without LiteRT-LM's prebuilt `libGemmaModelConstraintProvider.so` and `libwebgpu_dawn.so`. Those are built with AES and die at load ("This binary was compiled with aes enabled, but this feature is not available on this processor", then SIGILL) on CPUs without the ARMv8 crypto extension: the Raspberry Pi 4 (Cortex-A72; also the Pi 400, CM4, Pi 3, Zero 2 W), while the Pi 5 (Cortex-A76) has it. LiteRT-LM links both unconditionally on `linux_arm64`, so the scripts build from a patched copy of the LiteRT-LM tree in `litert_lm_patched/` (gitignored, re-synced with `rsync` each run; the submodule isn't edited): `platforms/debian/litert_lm_patches/cpu-only-engine.patch` points `//runtime/engine:engine_impl_selected` at `//runtime/core:engine_advanced_impl_cpu_only` (no WebGPU sampler, so no Dawn), and `--//build_config:enable_fst_constraints=false` makes constrained decoding use llguidance (Rust, built from source; LiteRT-LM's BUILD still says "Make LLGuidance the default once it is validated") instead of the Gemma constraint provider. `bazel cquery 'deps(//c:litert-lm) union deps(//omniextern:omniextern)'` confirmed neither prebuilt is left. Verified on a Pi 4 (2026-11-05): `liblitert-lm.so` (15.3 MB, `DT_NEEDED` only `libLiteRt.so` and system libraries) loads and `litert_lm_get_api_version` returns 1.0.0. With `-p:TestModels=true` on the same Pi 4 (CPU): `TestQwen3Chat` (Qwen3-0.6B, 343 MB) passed in 1 m 17 s with the model cached, and `TestChatClientToolsConstrained` (Gemma 4 E2B, 2.6 GB, constrained decoding through llguidance) passed in 7 m 9 s including the download - one tool call, "The secret code of Alice is 7391.", follow-up "1937". LiteRT-LM logs "Failed to get benchmark info: INTERNAL: Benchmark is not enabled" after each turn; it doesn't affect the replies. The copy is its own Bazel workspace, so the first build is a cold one (about 3.5 hours on the Pi 4). `LITERT_LM_PREBUILTS=1` builds the unpatched submodule with both prebuilts instead (needs `git -C LiteRT-LM lfs pull`, hence `git-lfs` in `apt_install_dependency.sh`, and an AES CPU).

### Windows Bazel pitfalls (seen 2026-11-02, rebuilding the patched `liblitert-lm` with `bazel_build_litert.ps1 64 -Gpu`)
- **"FATAL: corrupt installation: file 'u\install\...\embedded_tools\MODULE.bazel' is missing or modified":** a Bazel server (a `java.exe` whose command line names `u\install`) is still running from an interrupted build and holds an install that was changed under it. Stop that `java.exe` (`Get-CimInstance Win32_Process -Filter "Name='java.exe'"`), delete `u\install`, and build again: Bazel unpacks a new one. The patched build's output base `q` has its `install` symbolic link into `u\install`, so it goes with it.
- **"Every .bzl file must have a corresponding package, but '@@org_tensorflow//tensorflow:workspace3.bzl' does not have one"** (then the same for `@@rules_cc//cc:extensions.bzl`...): the build that hit the corrupt install above was cut off while it re-fetched the external repositories, and left many of them in `q/external` as **empty folders next to their `@<name>.marker` files**, which Bazel takes to mean "fetched". Stop the `q` server (`java.exe` with `q\javalog.properties` in its command line), delete every empty folder in `q/external` together with its marker (`for d in */; do [ -z "$(ls -A "$d")" ] && rm -rf "$d" "@${d%/}.marker"; done`), and build again: it fetches them again (226 repositories, about 14 minutes with the compile of the changed sources). Deleting only the repository the error names is not enough: the next error names another.
- **Side effects of the script in `lib/runtimes/win-x64/native`:** it copies the Visual C++ runtime DLLs (`msvcp140*.dll`, `vcruntime140*.dll`, `concrt140.dll`, `vccorlib140.dll`) there, and `dotnet build` then fails with NETSDK1152 (duplicate files in the publish output): delete them after every native build (the build leaves no other file of that kind there). Bazel's own outputs are copied **read-only**, so putting other copies of those DLLs back (for example to restore a backup) fails with "Permission denied" until `IsReadOnly` is cleared (`Get-ChildItem lib\runtimes\win-x64\native\*.dll | ForEach-Object { $_.IsReadOnly = $false }`).

### Mac Catalyst
No build of its own since 2026-11-09: a Mac Catalyst app loads the macOS dylibs from `lib/runtimes/osx/native/`, built by `platforms/macos/bazel_build_macos_fat` - `libtfliteextern.dylib` and `libLiteRt.dylib` from `Emgu.LiteRT.Runtime/Maui/Mac` (the package `Emgu.LiteRT.runtime.maui.macos`), LiteRT-LM's and the Metal accelerator from their add-ons - out of the app's `Contents/MonoBundle`, where `DllImport` finds them (`TfLiteInvoke.ExternLibrary` is `tfliteextern` there, as on macOS). A Catalyst app can't link a macOS library (the linker refuses: "building for Mac Catalyst, but linking in ... built for macOS"), but dyld loads one at run time. Apple doesn't document that, and the App Store's view of it is untested; a fallback is marking the dylibs as Mac Catalyst (`LC_BUILD_VERSION` platform 6) with `vtool`, which Apple DTS calls a last resort. Before, `platforms/ios/cmake_build_tflite_catalyst` built a static `lib/ios/libtfliteextern_darwin_<arch>.a` with clang's `-target <arch>-apple-ios15.0-macabi`, force-loaded into the app (`DllImport("__Internal")`): it carried a second copy of TFLite, without XNNPACK, and a Catalyst app had no `libLiteRt.dylib` unless the LiteRT-LM add-on brought one. The macOS `libtfliteextern.dylib` and `libLiteRt.dylib` are universal (arm64 and x86_64); LiteRT-LM's dylibs are arm64 only. Building the demo for Catalyst needed:
- `net10.0-maccatalyst` in the MAUI UI runtime's target frameworks (`cmake/Emgu.LiteRT.runtime.maui.Directory.Build.props.in`, macOS/Windows hosts) — otherwise Catalyst apps resolve its `netstandard2.0` build, which never references the Mac runtime project, so no tfliteextern was linked at all.
- The UIScene life cycle: UIKit refuses to launch apps built with the macOS 27 SDK without it, so `Emgu.LiteRT.Example/Maui/Platforms/MacCatalyst/Info.plist` declares a `UIApplicationSceneManifest` using MAUI's default scene configuration with `SceneDelegate.cs` (a `MauiUISceneDelegate`).
- `-p:ValidateXcodeVersion=false` when the .NET MacCatalyst SDK pack doesn't match the installed Xcode exactly (e.g. pack 26.5 wants Xcode 26.6 while Xcode 27.0 is installed): `dotnet build Emgu.LiteRT.Example/Maui/Maui.Demo.Lite.csproj -f net10.0-maccatalyst$(platforms/macos/apple_tfm_version.sh) -c Debug -p:ValidateXcodeVersion=false` (the TFM: "iOS and Mac Catalyst target frameworks"). MAUI incremental builds may keep a stale bundled `Info.plist`; delete `bin/obj/Debug/net10.0-maccatalyst` after editing it.

### Android (from Linux or macOS)
The Android binaries can be built on either a Linux or a macOS host, with the same script:
```bash
platforms/android/bazel_build_tflite_android arm64   # or: x86_64, arm, x86
```
Writes `lib/android/<abi>/libtfliteextern.so` and `libLiteRt.so` (`arm64-v8a`, `x86_64`, `armeabi-v7a`, `x86`), 16 KB page-aligned and stripped of debug info, plus `liblitert-lm.so` and `libGemmaModelConstraintProvider.so` for `arm64-v8a`/`x86_64` only (needs `git -C LiteRT-LM lfs pull`). `libtfliteextern.so` links dynamically against `libLiteRt.so`, LiteRT's runtime, which `Emgu.LiteRT` also uses directly. NNAPI is supported; the TFLite GPU delegate isn't (`tfeGpuDelegateV2Create` returns null). Run once per ABI; extra arguments are passed to `bazel build`. The script reads the SDK from `ANDROID_HOME` and the NDK from `ANDROID_NDK_HOME`, else the newest version under `$ANDROID_HOME/ndk`:
- **Linux**: `ANDROID_HOME` defaults to `/usr/lib/android-sdk` (the build image layout) when unset.
- **macOS**: set `ANDROID_HOME` to the Android Studio SDK, usually `~/Library/Android/sdk` (no default — the Linux path doesn't exist there). Verified with NDK 28.0.12916984 for all four ABIs.

## CI

- `.github/workflows/native.yml`'s `ios` job builds the iOS xcframeworks (`bazel_build_xcframework`), then the MAUI demo for the iOS simulator (`-f net10.0-ios -p:RuntimeIdentifier=iossimulator-arm64 -p:ValidateXcodeVersion=false`, no signing needed), and checks that the `.app`'s `Frameworks` folder holds all four as simulator binaries, with every `@rpath/*.framework` each one links also embedded. Its `windows` job runs `bazel_build_litert.ps1 64` on `windows-latest` (its own Bazelisk, passed to the script as `BAZEL_COMMAND`, which runs LiteRT-LM's `.bazelversion` - the runner's `bazel.exe` ran 9.x regardless of `USE_BAZEL_VERSION` - Python 3.12, `BAZEL_SH` = MSYS2's bash, `LITERT_LM_BAZEL_ROOT=D:\` so the LiteRT-LM build's output folders sit directly under the drive root and its paths stay under 260 characters - a `subst` drive letter didn't work, since Bazel resolves it to the real path, and under the checkout one Rust object reached 261; with that, the build reached the link of `liblitert-lm.dll`, which needs LiteRT-LM's `libGemmaModelConstraintProvider.dll` and its import library `.lib` - both Git LFS files, both pulled; with only the `.lib`'s pointer file the link failed with LNK1107 after 80 minutes, and the script now checks both before building), checks that all four DLLs were written - the script carries on past a failed Bazel build - and runs the whole test suite, `Native` tests included.
