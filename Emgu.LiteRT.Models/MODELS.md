# Models

The ready-made models: `Emgu.LiteRT.Models` (on LiteRT's CompiledModel API), `Emgu.LiteRT.Models.CV` (taking Emgu CV images), `Emgu.TF.Lite.Models` and `Emgu.TF.Lite.ImageIO` (on the TFLite Interpreter). The per-model evaluations are the other `*.md` files in this folder. Moved here from CLAUDE.md, which keeps the short version.

## Emgu.LiteRT.Models

- **Models layer** — `Emgu.LiteRT.Models/` (own `Emgu.LiteRT.Models.dll` and nuget package `Emgu.LiteRT.Models`, `EMGU_LITERT_MODELS_NUGET_ID`, props/README from `cmake/Emgu.LiteRT.Models.*.in`; netstandard2.0 + ios/android/maccatalyst; depends on `Emgu.LiteRT`, `Emgu.LiteRT.Util` and `Emgu.TF.Lite.ImageIO`) wraps the same models as `Emgu.TF.Lite.Models` - `Mobilenet`, `Inception`, `CocoSsdMobilenetV1`/`V3` (same files, `Init`/`Recognize`/`RecognitionResult`) - on LiteRT's CompiledModel API: the base `CompiledImageModel` downloads model + labels, creates `Environment`/`Model`/`CompiledModel` (for `HwAccelerators`, CPU by default) and the signature's input/output `TensorBuffer`s on a background thread, and reads images into the locked input buffer with `NativeImageIO.ReadImageFileToTensor<T>` (which needs tfliteextern for its pixel conversion, hence the `Emgu.TF.Lite.ImageIO` dependency).
- No Unity variants.
- `UnitTestLiteRtModels.cs` compares each with its Interpreter counterpart (identical results for MobileNet/Inception/Coco SSD V3 on the CPU; Coco SSD V1, quantized, differs by ~0.01 in scores; MobileNet on the Metal GPU 0.8213 vs 0.8224).

## Z-Image-Turbo (text to image)

- Stable Diffusion 1.5 was evaluated as a smaller second image model for phones and not adopted (2026-10-24): see [STABLE_DIFFUSION_EVALUATION.md](STABLE_DIFFUSION_EVALUATION.md).
- `ZImageTurbo` (`ZImageTurbo.cs`, with the internal `ZImageMath.cs`, `QwenTokenizer.cs` and `RangeDownloader.cs`) is text-to-image with Z-Image-Turbo (Alibaba Tongyi-MAI, 6B single-stream diffusion transformer, Apache-2.0) through the 13 int8 graphs of `litert-community/Z-Image-Turbo-LiteRT` (9.8 GB: the Qwen3-4B text encoder `qwen_enc` 3.5 GB - larger than a flatbuffer's 2 GB, and it loads - six 866 MB transformer shards `zc_main0..5`, embedders/refiners `z_embx`/`z_refx`/`z_embc`/`z_refc`, `zc_final`, the VAE decoder `zvae`; 256x256 only) plus host tensors no graph contains - Qwen3's `embed_tokens` (bf16, 778 MB), the timestep MLP `t_embedder.mlp.{0,2}` and `cap_pad_token` - which `RangeDownloader` reads from the original `Tongyi-MAI/Z-Image-Turbo` safetensors shards by HTTP range (0.78 GB of 32 GB; header parsed with `System.Text.Json`, now a netstandard2.0 dependency of the package), along with `vocab.json`/`merges.txt`; both revisions pinned, resumable `.part` files, completeness by size.
- Files go in `LocalApplicationData/Z-Image-Turbo` (`{name}.tflite`, `host/`, `cache/`; on this Mac a link to the data volume, since the boot disk is short of space).
- The host loop is ported from the Kotlin app https://github.com/alexeyw/android-image-generator (Apache-2.0; credited in the files): Qwen2 BPE with Z-Image's chat template (enable_thinking; 32-token caption = 24 prompt tokens + 8 template), embed on the host, `qwen_enc` (causal, no mask: padding can't reach the prompt rows), caption padded by repeating its last row -> `z_embc` -> pad slots replaced by `cap_pad_token` -> `z_refc` with caption RoPE; per step (FlowMatchEuler, shift 3; Turbo needs no CFG, so one pass): adaln = timestep MLP(t * 1000), patchify -> `z_embx` -> `z_refx` (image RoPE, adaln) -> [image, caption] -> `zc_main0..5` -> `zc_final` -> unpatchify -> Euler; then latent / 0.3611 + 0.1159 -> `zvae`; noise from a SplitMix64 + Box-Muller stream bit-identical with the Python reference, so seeds reproduce.
- Graph inputs are `(x, cos, sin[, adaln])`.
- Found while porting: the Kotlin tokenizer skips every `merges.txt` line starting with `#`, but merges such as `# #` start with it too, shifting every later rank (its tests have no `#`); ours skips only the `#version` header (`"## Title #1"` -> `##`, ` Title`, ` #`, `1`).
- Each graph is compiled on the CPU with 6 threads (`NumThreads`: cores minus two, at most six) and an XNNPACK weight cache (`cache/<name>.xnnpack_cache`, ~9 GB in all, written by the first image), run once and released - with the cache, compiling is a memory map (2-11 ms instead of 3-13 s), so streaming costs nothing and memory stays file-backed (3.9 GB peak RSS for the test).
- On an M1: first image 67 s (writing the caches), then 23 s for 8 steps; step 0's transformer output matched the reference's at cosine 0.999 and the image the reference's at 35.1 dB PSNR (`TestZImageTurbo`).
- Metal works with fp32 (fp16 gives NaN in `z_refc`/`z_refx`/`zc_main*`/`zvae`) but isn't faster (a shard 0.33 s vs 0.41 s on the CPU) and needs 16 s to compile each shard and ~5 GB per shard; the Kotlin app found the same on phones (GPU 284 s per image vs CPU 29 s on a Galaxy S25 Ultra).
- Those options come from `Emgu.LiteRT.Options.AddCpuOptions(CpuOptions)` (`NumThreads`, `WeightCachePath`) and `AddGpuOptions(GpuOptions)` (`Precision` - `GpuPrecision.Fp32` etc. - `AllowSrcQuantizedFcConvOps`, `SerializationDir`, `ModelCacheKey`, `SerializeProgramCache`): LiteRT's accelerator options are opaque payloads - a TOML text under the identifier `"xnnpack"` / `"gpu_options"`, which LiteRT's `LrtGetOpaque*OptionsData` helpers build but `libLiteRt` doesn't export - so C# builds the TOML and passes it through the exported `LiteRtCreateOpaqueOptions` (payload freed by a managed callback) / `LiteRtAddOpaqueOptions`; paths use forward slashes since LiteRT's parser takes the quoted text as is.
- Tests (`UnitTestZImageTurbo.cs`; golden fixtures fetched from the Kotlin repository at commit `bcdc30e0`, not copied): `TestZImageMath` (no model: schedule, timestep frequencies, RoPE, SplitMix64 bit for bit, noise, patchify, a recorded Euler step, VAE boundary), `TestZImageTokenizerAndTimestep` and `TestZImageTurbo` (`TEST_MODELS`; download the 10.6 GB model).
- Found on the way: a model file may not record an output's shape (`TFLite_Detection_PostProcess`'s outputs are `Float32[]`), and the compiled model only resolves it once its tensors are allocated, so `CompiledModel.CreateOutputBuffer` sized such buffers for one value and `Run` wrote past them (empty results, then crashes); it now asks for the resolved shapes (`CompiledModel.GetOutputTensorTypes(signatureIndex, updateAllocation: true)`, wrapping `LiteRtGetCompiledModelOutputTensorLayouts`) and creates a host buffer of that size.
- **Z-Image-Turbo on the GPU** (2026-11-02, Windows, RTX 3070 8 GB, WebGPU; `ZImageTurbo.Backend = "gpu"`; `UnitTestZImageTurbo`'s `TestZImageTurboGpu` and `TestZImageTurboGpuWithLessVideoMemory`): the nine graphs every step runs (`z_embx`, `z_refx`, `zc_main0`-`5`, `zc_final`; 5.8 GB of int8 weights) are compiled for the GPU when the model loads and stay there; the graphs a picture runs once (`qwen_enc`, `z_embc`, `z_refc`, `zvae`) stay on the CPU (one of them wouldn't compile on the GPU, and they cost little). "A red fox sitting in fresh snow at sunrise", seed 42, 8 steps:

  | | CPU | GPU, all 9 graphs | GPU, 4 of 9 (budget 2 GB) |
  |---|---|---|---|
  | Load | - | 38 s (from the program cache; **~2 minutes** the first time: ~13 s to compile each block, then 5.6 GB in `gpu-cache/`) | - |
  | First picture | 120-133 s | 17 s (the CPU graphs' first run) | 102 s |
  | Next pictures | 120-133 s | **4.3-4.7 s** | 102 s |
  | Video memory | - | ~5.5 GB (7.4 GB of the 8 GB in use) | ~2 GB |
  | PSNR against the CPU's picture | - | 28.2 dB | 24.7 dB |

  The two pictures are the same fox. Findings: the weights stay int8 on the GPU (`GpuOptions.AllowSrcQuantizedFcConvOps`: ~0.96 GB of video memory per 908 MB block, 1.11x its file; the option also quantizes the activations of the FC and convolution layers, hence 28 dB and not more), and the compute is **FP32**: FP16 and FP16 with FP32 accumulation give NaN in `zc_main0` with or without the int8 option (cosine NaN). With the option forced off (FP32) the process **aborted** while initializing the block on the GPU: running out of video memory is not an exception, so the budget has to be right before anything is compiled (`GpuMemory` asks DXGI for this process's free video memory, `Budget - CurrentUsage`, less 600 MB; `ZImageTurbo.ChooseGpuGraphs` takes the graphs that fit, in the order they run; the rest run on the CPU: compiling a block for each call costs ~3 s even with the cache, as much as running it on the CPU). A block compiled for the GPU runs in 0.07-0.12 s, against 3.1-3.4 s on the CPU, and matches it to cosine 0.9993 (0.9997 with the option unset, whose memory wasn't measured). Over-asking is not fatal, only slow (2026-11-05, a temporary test: one GPU model resident, a second with an explicit 9 GB budget in the same process, 11 GB of graphs on the 8 GB card): no exception and no abort, the picture came out, but in 42 s instead of 4.7 s, as the driver pages video memory out to system memory; so the budget decides the speed, and a hard abort happened only with the unquantized FP32 graph. In the demo the choice is "Z-Image-Turbo · GPU" (Windows with the GPU runtime); `ImageFeature` lets the image model go when another chat model is chosen or the chat model is reloaded, so the chat model has the video memory (`ChatFeature.OnModelChanged`, `OnModelReloadingAsync`).

## Bonsai Image and FLUX.2-klein (text to image through LiteRT-LM)

- In `Emgu.LiteRT.LM.Models`, not here: LiteRT-LM's OmniEngine (`omni/text2image`, C++ only) runs them, through Emgu's `libomniextern` (`omniextern_image_engine_create` / `omniextern_image_generate`, `Emgu.LiteRT.LM`'s `TextToImageEngine`). `TextToImageModel` downloads the model's one `.litertlm` (pinned revision, SHA-256) and draws with it; `BonsaiImage4B` (`bonsai-flux2`, PrismML's ternary Bonsai Image 4B on FLUX.2-klein's architecture, 4.27 GB) and `Flux2Klein4B` (`flux2-klein`, Black Forest Labs' FLUX.2-klein-4B int8, 4.65 GB), both Apache-2.0 and distilled for 4 steps. The chat draws with them through `Emgu.LiteRT.LM.Maui.Images`' `OmniImageModel` (Bonsai on the CPU is the demo's default; Z-Image-Turbo stays a choice).
- **256 x 256 in litert-community's files:** each `.litertlm` holds one graph per stage, made for 256; asking for 512 fails in LiteRT-LM (`INVALID_ARGUMENT` building the stages). **Bonsai at 512 x 512** is Emgu's repackaging (2026-11-01, `BonsaiImage4B512`, on Emgu's public S3 with its notice and licence, `emgu-public/bonsai/`): `litert-lm unpack`, `img_size: 512` in the metadata, the repository's 512 diffusion transformer `dit_gpu_int4b32.tflite`, a 512 VAE decoder exported by `tools/export_flux2_vae_decoder.py`, `litert-lm pack`. The repository's own 512 decoder (`vae_dec_fp32.tflite`) writes GroupNorm with 60 `GATHER_ND` and `SUM`, which the GPU delegates reject ("37 operations will run on the GPU, and the remaining 845 on the CPU", then LiteRT-LM's "not fully delegated" error - a `.litertlm` runs every graph on one backend, and its metadata has no per-stage backend); the export writes GroupNorm as reshape/`MEAN`/`RSQRT` like the 256 decoder in the `.litertlm` (549 ops, the same op set) and matches `vae_dec_fp32.tflite` to 6e-6. On an M1: 66 s a picture on the CPU (6.0 GB peak), 25 s on Metal (2.3 GB); the same file runs on both. FLUX.2-klein has no 512 graphs to repackage (its card: a different size means a re-export of the transformer). The demo offers 512 on Mac Catalyst and, on the GPU only, on Windows (below), not on phones: a phone's CPU would take a quarter of an hour, and on a Pixel Fold's GPU (Mali-G710, OpenCL, 2026-11-01) the first load took 159 s and a picture 201 s (the same fox as Metal's), but the app reached 7.0 GB PSS (about 5 GB of GPU memory), Android closed the other apps' processes to make room, and killed the demo (in the background at the time) before a second picture. The size is fixed when the engine is created (the stages take it from the session config; a prompt's own size is ignored); steps and seed are per picture (seed 0 is LiteRT-LM's fixed 42, so `TextToImageModel` takes seeds from 1). The same seed gives the same bytes on a backend; CPU and GPU pictures differ slightly.
- **No progress and no cancel:** a picture is one `ProcessNext()`; `GenerateAsync` returns at once on cancellation and the engine finishes the picture in the background (thrown away).
- **Caches** are named after the graphs (`flux2_dit_<file time>_<file size>.xnnpack_cache`, `..._mldrift_program_cache.bin`), the same for both models, so each model has a cache folder of its own (`TextToImageModel.CacheFolder`, `<model name>-cache` next to the file, `StorageModel.Image`'s cache folder): about 3.7 GB for the CPU and 3.3-3.6 GB for the GPU.
- On an M1 (2026-11-01, LiteRT-LM v0.19.0's `omni_runner`, "a red fox sitting in fresh snow at sunrise", 4 steps):

  | | Bonsai CPU | Bonsai GPU (Metal) | FLUX.2-klein CPU | FLUX.2-klein GPU (Metal) |
  |---|---|---|---|---|
  | First load (writes the caches) | 28 s | 33 s | 27 s | 26 s |
  | Later loads | 0.7-1.5 s | 2.9 s | 0.95 s | 3.3 s |
  | A picture (warm) | 24-25 s | 11.0 s | 23.3 s | 16.6 s |
  | Peak RSS (warm) | 4.8 GB | 2.1 GB | 5.6 GB | 2.2 GB |

  Both drew a convincing fox (Bonsai's more photographic); Z-Image-Turbo takes 23 s for 8 steps on the same Mac's CPU with a 10.6 GB download and ~9 GB of caches. Through the C# wrapper (`UnitTestTextToImage`, `TEST_MODELS`) the same times and the same picture as `omni_runner`.
- On a Pixel Fold (2026-11-02) Bonsai on the GPU beside Gemma 4 E2B on the GPU gets the demo killed by Android's low-memory killer (no error, so no CPU fallback); on the CPU it draws in 380 s. Measurements and the options: [BONSAI_ANDROID_MEMORY.md](BONSAI_ANDROID_MEMORY.md).

## YOLOX, D-FINE and PicoDet

- `YoloX` (`YoloX.cs`) runs the official Megvii YOLOX-Nano (ONNX converted to float32 LiteRT, 416x416 NHWC input of BGR 0-255 letterboxed top-left with padding 114, raw `[1,85,3549]` output) through `CompiledModel` and `Decode`s it as upstream's ONNX demo does (stride 8/16/32 grids, objectness times best class, class-agnostic NMS 0.45 with inclusive areas, boxes mapped back and clipped after NMS); `Emgu.LiteRT.Models.CV`'s `YoloXDetector` (used by the demo) downloads the weights on demand from Emgu's public S3 (3.7 MB, SHA-256 checked, not in Git or the app package; Apache-2.0 licence and notice hosted beside them) and runs them on the GPU - explicit FP32, GPU+CPU - when its detections on `surfers.jpg` match the CPU's and it is faster, else on the CPU (`GpuFailure` says why; measured full pipeline: M1 9.6 vs 23.6 ms, Galaxy S10 31.4 vs 62.6 ms, Pixel Fold 36.2 vs 42.6 ms), behind the `ICocoDetector` interface it shares with `CocoDetector`, as a "YOLOX Nano" photo page and a second visual agent `coco-yolox-nano` (the planner prefers `coco-ssd-mobilenet-v3` unless the user asks for YOLOX); `YoloXImageInput` (linked into the tests) writes the input; tests `UnitTestYoloX` (decoding, model-free) and `UnitTestYoloXNative` (parity with upstream's output on four images; GPU opt-in); about 23 ms on an M1's CPU vs V3's ~5 ms, 44-50 ms on a Pixel Fold vs 12-17 ms - details in `Emgu.LiteRT.Models/YOLOX_EVALUATION.md` (that folder holds the model notes - YOLOX, D-FINE, PicoDet, MobileNet V5, `HAND_GESTURES.md`, `POSE.md`, `YAMNET.md` - and `tools/` their conversion and check scripts, moved from the demo; the scripts find the demo's sample images under `Emgu.LiteRT.Example/Maui/Resources/Raw`) (D-FINE-N, Apache-2.0, was also converted and measured - 1.4-2.7x YOLOX-Nano's CPU time at 416 px and no phone GPU path - and is only offered as a CPU-only "D-FINE Nano" photo page on Mac Catalyst (`DFine.cs`, `DFineDetector`, weights from `emgu-public/dfine/`; no visual agent; `UnitTestDFine`): `DFINE_EVALUATION.md`, `Emgu.LiteRT.Models/tools/prepare_dfine_n.py`, `check_dfine_conversion.py`) (`PicoDet` - Baidu's PP-PicoDet-S 416, Apache-2.0, COCO AP 32.5 - is converted the same way, `Emgu.LiteRT.Models/tools/prepare_picodet_s.py`, with its two HardSigmoid nodes rewritten because the TFLite converter turns them into `RELU_0_TO_1`, which the Metal and OpenCL delegates can't compile; then it is fully accelerated: 3.9 ms on an M1, 17.8 ms on a Galaxy S10, 16.7 ms on a Pixel Fold, and 25-45% faster than YOLOX-Nano on phone CPUs; `PicoDetDetector` downloads it from `emgu-public/picodet/`, the "PicoDet S" page, `UnitTestPicoDet`: `PICODET_EVALUATION.md`) (and `MOBILENET_V5_EVALUATION.md`: V5's weights have no detection head yet).

## Depth Anything V2 (depth from one photo)

- `DepthAnythingV2` (`DepthAnythingV2.cs`, since 2026-10-28) runs Depth Anything V2 Small (DINOv2 Small + DPT, ~24.8M parameters, Apache 2.0) from Google's own LiteRT export, `litert-community/depth-anything-v2-small`: a fixed float32 NCHW `[1,3,518,686]` input (RGB stretched to 686 x 518 bicubic, /255, ImageNet mean/std) and a `[1,518,686]` relative depth, larger nearer (not metres). `ModelFile` is the 27.7 MB file with dynamic int8 weights (`depth_anything_v2_small_wi8_afp32.tflite`), as accurate and fast on the GPU as the 99.5 MB float32 one. `Emgu.LiteRT.Models.CV`'s `DepthEstimator` downloads it on demand, writes the input from a `Mat` (`DepthAnythingV2ImageInput`, the channels converted straight into the input planes) and returns a float `Mat` the photo's size, 0 farthest to 1 nearest; it uses the GPU at FP16 when its depth on `surfers.jpg` correlates > 0.999 with the CPU's and it is faster. `DepthEffects.BlurBackground` is portrait mode: Otsu's threshold of the depth splits the subject from the background, which is blurred more the farther it is (two blur levels), with a soft edge and a normalized convolution so the subject doesn't glow into the background; 6-80 ms on an M1 for 320-1000 px photos. Tests: `UnitTestDepthAnything` (people nearer than the sea and the sky, the split between them; the blur keeps a near half and blurs a far one; a GPU parity case, explicit). Measurements in `DEPTH_ANYTHING_EVALUATION.md`: on the M1 the GPU (Metal) takes 119 ms at FP16, the CPU 390 ms; on the Pixel Fold the GPU (OpenCL) ~0.5 s, the CPU 1.5-2.7 s - fine for photos, about 2 frames a second for the camera.

## Speaker voiceprints (who spoke)

- `SpeakerEmbedder` (`SpeakerEmbedder.cs`, since 2026-10-28) runs WeSpeaker's ResNet34 speaker embedding as litert-community converted it for pyannote 3.1's recipe (`litert-community/Speaker-Diarization-LiteRT`'s `wespeaker_emb_fp16.tflite`, 13.4 MB; the weights are CC-BY-4.0, pyannote's code MIT): input [1,500,80] Kaldi log-mel features of 5.015 s of 16 kHz speech (shorter speech repeated to fill it) with each bin's mean removed, output a 256-value fingerprint (normalized). `KaldiFbank` computes the features as torchaudio's `kaldi.fbank` does (25/10 ms Hamming frames, DC removed, pre-emphasis 0.97, 512-point power spectrum, 80 mel bins from 20 Hz, log floored at float's epsilon; the audio scaled to 16-bit values). `SpeakerVoiceprints` downloads it, tries the GPU at FP16 (kept when a test sound's fingerprint has a cosine similarity of at least 0.999 with the CPU's and it is faster) and fingerprints speech of any length (the mean of up to six 5 s stretches). The repository's segmentation model (pyannote segmentation-3.0) is ONNX only and isn't used: the meeting recorder cuts pieces at pauses instead (`Emgu.LiteRT.LM.Agents`' `MeetingAudioChunker`), and `SpeakerClustering` groups the pieces' fingerprints with pyannote's centroid linkage and threshold. The model card says XNNPACK declines the FP16 graph; with this repo's LiteRT the CPU runs it (122 ms per stretch on an M1, features included; Metal 28.5 ms). On a synthetic three-voice meeting (macOS voices) every turn was its speaker's (`UnitTestSpeakerVoiceprints`, skipped without `say`); with 3 s stretches, one voice's fingerprints had a cosine similarity of 0.82 on average, different voices' 0.20. Through a Mac's speakers and microphone the same meeting got 3 speakers with every line right, after fingerprinting only the speech frames (`SpeakerVoiceprints.Speech`; a piece that was mostly silence had the room's fingerprint) - see FEATURES.md's meeting notes. Not yet tried with real people.

## Noise removal (speech denoising)

- `SpeechDenoiser` (`SpeechDenoiser.cs`, since 2026-10-29) is the base of two 16 kHz mono noise removers, `Denoise(float[])` keeping the length; `DownloadAsync` gets each model at a pinned revision with its SHA-256. Not used by the demo: on the meeting notes they didn't help (below).
  - `CmganDenoiser` runs CMGAN (1.83M-parameter conformer, MIT, trained on VoiceBank-DEMAND) from `litert-community/CMGAN-LiteRT` (`cmgan_fp16.tflite`, 4.2 MB): a 2 s chunk RMS-normalized and reflect-padded by 200 samples in ([1,32400]), the cleaned spectrogram out (two [1,1,321,201], real and imaginary, magnitude^0.3); the class un-compresses it (scale by (re²+im²)^(7/6)), takes the inverse STFT (n_fft 400, hop 100, periodic Hamming, a DFT table) and cross-fades chunks overlapping by half (squared sine). GPU only - XNNPACK declines the graph - and at FP32 by default: at FP16 the M1's GPU garbled some chunks (one piece from 15 to -3 dB SI-SNR). On an M1 at FP32: 1.1x real time, the whole graph on the GPU (the model card: ~20 ms per 2 s chunk on a Pixel 8a, 376 ms on a Galaxy S26).
  - `DtlnDenoiser` runs DTLN (Westhausen and Meyer 2020, MIT, the DNS Challenge's data) from breizhn/DTLN's two stateful TFLite models (1.5 + 2.5 MB; [1,1,257] magnitudes and a [1,2,128,2] LSTM state in, a mask out; then [1,1,512] the masked block, its state): 512-sample blocks every 128 (a radix-2 FFT in the class), overlap-add. `Process` streams (any number of samples in, steps of 128 out, `Latency` 384 samples behind), `Denoise` aligns a whole recording. CPU, one thread: 43x real time on an M1.
- Measured on the Mac (2026-10-29): on synthetic noisy speech (macOS voices with room noise at 15 dB SNR) both raised SI-SNR to 21 dB (CMGAN 21.0, DTLN 21.1), but Gemma 4 E2B's word errors stayed 3.2% (CMGAN) and 4.4% (DTLN) against 3.8% without; on a Pixel Fold's distant, quiet meeting recording (-44 dBFS) they rose from 12% to 56% (DTLN) and 289% (CMGAN, invented text), and the speakers' fingerprints got further apart, not nearer. So: for audio people listen to, not before speech recognition or voiceprints. Tests: `UnitTestSpeechDenoisers` (a macOS voice with noise: each gains more than 3 dB - 15.0 to 19.0 dB DTLN, 20.2 dB CMGAN; DTLN streamed in uneven pieces gives the same samples; CMGAN skipped without a GPU accelerator).

## Hand tracking and gestures

- `HandTracker` (`HandTracker.cs`, `HandModelFiles.cs`, TODO item 40, `HAND_GESTURES.md`) is MediaPipe's hand tracking in C# on `CompiledModel`: the palm detector (192 px, SSD anchors, weighted NMS), the rotated hand rect, the landmark model (224 px, 21 landmarks plus world landmarks and handedness) and the gesture embedder and classifier (closed fist, open palm, pointing up, thumb down/up, victory, I love you, none; MediaPipe feeds the gesture features unrotated, so a sideways hand is none); the four models come from Google's `gesture_recognizer.task` (downloaded and unpacked, not copied to Emgu's S3 - their licence terms are unconfirmed), the classifier's dynamic batch dimension is patched to 1 on unpacking, `Emgu.LiteRT.Models.CV`'s `HandImageInput` (Emgu CV) letterboxes and warps; checked against MediaPipe's Python results on its five test images (same gestures, landmarks within 14 px) on the CPU and the Metal GPU; on the phones a whole frame is 14-20 ms on the CPU, not faster on the GPU, so the "Hand gestures" photo page defaults to the CPU.

## YAMNet (sound events)

- `YamNet` (`YamNet.cs`, TODO item 41, `Emgu.LiteRT.Models/YAMNET.md`) is Google's audio event classifier as MediaPipe ships it (`yamnet.tflite`, 4.1 MB, downloaded from Google and hash-checked, Apache-2.0 per its metadata only): 15,600 mono samples at 16 kHz in, 521 AudioSet class probabilities out, the spectrogram inside the graph, static shapes, the labels a zip appended to the file; it also reads WAV files and resamples; checked against Python's interpreter (`UnitTestYamNet`); `YamNetClassifier` (`YamNetClassifier.cs`, moved from the demo's `YamNetDetector`) downloads it to a `cacheDirectory` (default: a temp folder; the demo passes `FileSystem.CacheDirectory`, where it already was) and loads it on the CPU, with `Scores`/`Classify`; the demo's "Sound events" page listens through `AudioRecord` (Android) or an `AVAudioEngine` tap (Apple), scoring the last second twice a second at 3-5 ms (M1) / 7-17 ms (Galaxy S10) a window on the CPU.

## Pose tracking

- `PoseTracker` (`PoseTracker.cs`, `PoseModelFiles.cs`, TODO item 51, `POSE.md`) is MediaPipe's pose landmarker on `CompiledModel`: the pose detector (224 px, 2254 SSD anchors, weighted NMS), the square region from its first two keypoints (hip centre and a point on the circle round the body, x1.25, rotated upright), and the landmark model (256 px: 33 landmarks plus 6 auxiliary, visibility, presence - an already-sigmoided output, a trap -, world landmarks); the bundles `pose_landmarker_{lite,full,heavy}.task` are downloaded from Google and hash-checked (Apache-2.0 per the model card, which rules out surveillance, identification and life-critical use and covers one person within ~4 m with the head in view); checked against MediaPipe's Python results on its test image and five copies; 26 / 36 ms a frame (lite / full) on a Galaxy S10's CPU, the GPU doesn't compile fully; a "Body pose" photo page and (TODO item 52) the `body-pose` visual agent: `PoseGestures` reads arms raised, hand raised, waving (a `WaveDetector` over 2 s), standing, sitting and lying down from the landmarks (thighs measured along the spine, each leg on its own, a landmark under 0.5 visibility never used, nothing for falls), `PoseVisualAgent` makes them object classes of the camera monitors, and `VisualClasses.PostureForMonitor` reads the posture from the user's request when Gemma gives the person class or an agent's name as the label (it did for "raises their hand" and "lying down"); verified with Gemma 4 E2B on a Galaxy S10 and MediaPipe's photo as frames, not on a real person.

## Face tracking and expressions

- `FaceTracker` (`FaceTracker.cs`, `FaceModelFiles.cs`, `FACE.md`) is MediaPipe's face landmarker on `CompiledModel`: the face detector (BlazeFace short range, 128 px, 896 SSD anchors, input -1..1 with 0 padding, weighted NMS), the region (the box x1.5, eyes level), the landmark model (Face Mesh V2, 256 px, 478 landmarks, presence as a logit) and the blendshape model (52 ARKit-named expression scores from 146 landmarks in image pixels, always on the CPU - Metal can't compile it); Google's `face_landmarker.task` is downloaded and hash-checked, Apache-2.0 per the three model cards (no surveillance, identification or life-critical use), and the landmark model's dynamic batch is patched to 1 on unpacking (`FaceModelFiles.WithStaticBatch`, the gesture classifier's patch for 2-5-element shapes); `Emgu.LiteRT.Models.CV`'s `FaceDetector`/`FaceImageInput`; checked against MediaPipe's Python results on the demo's sample face - synthetic, drawn by `ZImageTurbo` (seed 22), since MediaPipe's own test portrait is a real, well-known person - and five copies (`tools/make_face_reference.py`, `TestData/face_reference.json`, `UnitTestFaceTracker`/`UnitTestFaceTrackerNative`: 0.13-0.42 px mean on the 256 px face, expressions within 0.05, CPU and Metal GPU the same); the demo's "Face" page (photo and live camera; 8 ms a frame on a Galaxy S10's CPU); `FaceExpressions` reads smiling, eyes closed, winking, mouth open and eyebrows raised from the blendshapes (thresholds from synthetic Z-Image faces, scores scaled so the threshold is 0.5, a monitor's default confidence) and the demo's `face-expression` visual agent (`FaceVisualAgent`, in `Emgu.LiteRT.LM.Agents.CV`; `VisualClasses.CanonicalExpression`/`ExpressionForMonitor`, checked before `PostureForMonitor`) makes them camera-monitor classes - the instructions rule out identification and drowsiness/attention use; `UnitTestFaceVisualAgent`/`UnitTestFaceVisualAgentNative` (synthetic faces in `TestData/face_*.jpg`); not yet tried with Gemma 4 or a real camera.

## Holistic landmarks

- `HolisticTracker` (`HolisticTracker.cs`, `HolisticModelFiles.cs`, `HOLISTIC.md`) is MediaPipe's holistic landmarker on `CompiledModel`: one person's pose (`PoseTracker` with the heatmap refinement), both hands (regions from the pose's wrist, pinky and index, corrected by the `hand_roi_refinement` model, then the hand landmark model; left and right from the pose, world landmarks moved to the pose's wrist) and face (BlazeFace in a region from the pose's head landmarks, Face Mesh V2 at 192 px, blendshapes); the seven models come from Google's `holistic_landmarker.task` (13.7 MB, downloaded and hash-checked, Apache-2.0 per the model cards, static shapes); a picture on its own, or frames of a video as MediaPipe's video mode (the body tracked from the last frame instead of the detector and smoothed by one-euro filters, each hand and the face kept in their last region while they move little: hands within 0.1 px of MediaPipe's video mode, 22-23 instead of 27-29 ms a frame on an M1, `make_holistic_video_reference.py`); `Emgu.LiteRT.Models.CV`'s `HolisticDetector`/`HolisticImageInput` (the pose models always on the CPU - they don't compile for the GPU; the hand and face models on the GPU when it matches the CPU and is faster: the M1's Metal yes, 30.5 -> 24 ms, the phones' OpenCL no); checked against MediaPipe's Python results on a synthetic waist-up picture (`holistic_person.png`, Z-Image seed 2) and four copies (`tools/make_holistic_reference.py`, `TestData/holistic_reference.json`, `UnitTestHolisticTracker`/`UnitTestHolisticTrackerNative`: pose 0.2-1.0 px mean, hands 0.1-0.4, face 0.05-0.13 of 256 px, expressions within 0.06); a frame 31 ms on an M1's CPU, 50-72 ms on a Galaxy S10's, 53-62 ms on a Pixel Fold's (2 threads; 4 are slower there). Porting it found that the pose and hand crops padded with black and shifted the corners by half a pixel where MediaPipe repeats the edges and maps corners to corners; fixed in all the `*ImageInput` crops (pose parity 3.6-7.6 -> 1.0-3.0 px). The demo's "Holistic" page (photo or live camera), and its `holistic` visual agent: a posture combined with an expression ("hand raised and smiling", `HolisticGestures`) and covering the eyes, a hand over the mouth or on the face as camera-monitor classes, with `VisualClasses.HolisticForMonitor` reading the request when Gemma's label is half of one or a mistake (5 of 5 routed right on an M1; the hand-on-face rules miss a hand at the side of the jaw and can take a chin cradle for a covered mouth).

- `Emgu.LiteRT.Models.CV.Maui/` (own `Emgu.LiteRT.Models.CV.Maui.dll` and nuget package, `EMGU_LITERT_MODELS_CV_MAUI_NUGET_ID` = `Emgu.LiteRT.Models.CV.Maui`, props/README from `cmake/Emgu.LiteRT.Models.CV.Maui.*.in`; `Maui/`, android/ios/maccatalyst, windows on Windows hosts, built by CMake on macOS/Windows only; namespace `Emgu.LiteRT.Models.CV.Maui`; depends on `Emgu.CV.runtime.maui.mini` 4.12 - whose `CvImageView` is the Android preview - and `Microsoft.Maui.Controls`, not on `Emgu.LiteRT.Models.CV` itself) is the live camera the MAUI demo's camera monitors and live demo pages use, moved out of the demo on 2026-10-25: `LiveCamera` (BGR `Mat`s at most 960 px, turned by `RotationDegrees` - `FrameRotation(front)` gives Android's - up to 30 fps through `FrameReady` on the camera's thread, `CaptureAsync` JPEG snapshots; Android through Camera2 - `LiveCamera.Camera2.cs`: a 640x480 YUV reader, the session configured again with a JPEG reader for `TakePhotoAsync` or a MediaRecorder surface for `RecordClipAsync`, `Front` and `FindCameraId` for the selfie camera - with OpenCV's Android camera as the fallback; iOS through AVFoundation since 2026-11-04 - `LiveCamera.AVFoundation.cs`: a BGRA video data output in a 4:3 format since 2026-11-05 (1920x1440 on an iPad Air M4, full-sensor photos; the 720p preset where there is none) whose buffers are wrapped as `Mat`s, upright from the connection's orientation, an `AVCapturePhotoOutput` for `TakePhotoAsync` and an `AVAssetWriter` fed the same buffers for `RecordClipAsync`; `HasFrontCamera` on both; the shared photo and clip code in `LiveCamera.cs`; OpenCV's capture on Mac Catalyst - its own size kept, since AVFoundation throws on a larger one - and Windows - DirectShow first, Media Foundation took 11-12 s to open a webcam) and `LiveCameraPreview` (each platform's image view; on iOS `LiveCameraPreviewHandler`, an `AVSampleBufferDisplayLayer` fed pooled IOSurface pixel buffers, registered by `UseLiveCamera()`). ## Emgu.TF.Lite.Models and Emgu.TF.Lite.ImageIO

- `Emgu.TF.Lite.Models/` (nuget `PackageId` still `Emgu.LiteRT.Tflite.Models`) provides high-level pre-built model helpers (MobileNet, COCO SSD, etc.) that download weights and run inference, built on the TFLite Interpreter API (`Emgu.TF.Lite`), not LiteRT's own CompiledModel API.
- `Emgu.TF.Lite.ImageIO/` (folder, csproj, `AssemblyName`, nuget `PackageId` and C# namespace all `Emgu.TF.Lite.ImageIO` — renamed from `Emgu.Models/`, then briefly `Emgu.LiteRT.ImageIO/`) is its own project and nuget package, providing `NativeImageIO`/`JpegData` - these couldn't move into `Emgu.LiteRT.Util` the way `Annotation`/`DownloadableFile`/`FileDownloadManager` did, because `NativeImageIO` calls `Emgu.TF.Lite.Toolbox`'s native pixel-conversion P/Invokes, which live in `Emgu.TF.Lite`; `Emgu.TF.Lite` itself depends on `Emgu.LiteRT.Util`, so putting `NativeImageIO` there too would create a circular project reference.
- `Emgu.TF.Lite.ImageIO.csproj` instead `ProjectReference`s both `Emgu.LiteRT.Util` (for `Annotation`, which `NativeImageIO`'s platform variants take as a parameter) and `Emgu.TF.Lite` (for `Toolbox`) directly, and depends on both as nuget dependencies when packed.
- `Android/AndroidFileAsset.cs` lives in this folder too but was already namespaced `Emgu.LiteRT.Util` (pre-existing, left as-is) rather than `Emgu.Models`/`Emgu.TF.Lite.ImageIO`.
