# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

Emgu TF Lite is a cross-platform .NET wrapper for the Google TensorFlow Lite library, enabling TF Lite functions to be called from C#, VB, VC++, and IronPython. It loads and runs TensorFlow Lite models on Windows, macOS, Linux, Android, and iOS.

The native C++ layer is exposed through P/Invoke via the `tfliteextern` extern library.

## Architecture

### Layer structure
1. **Native layer** — C/C++ wrapper DLL (`tfliteextern`) built with CMake or Bazel; must be present in `lib/runtimes/<rid>/native/` before building .NET code.
   - **Windows x64 (both CMake and Bazel)**, **macOS (Bazel)**, **iOS/Mac Catalyst (Bazel)**, **Android (Bazel)**, **Ubuntu (Bazel)**, and **Debian ARM (Bazel)** build against `litert/tflite` (the `google-ai-edge/LiteRT` submodule). There is no `tensorflow/` submodule in this repo.
     - CMake (Windows and macOS) builds directly from `litertextern/tfliteextern/`; `litert/tflite`'s own CMake project downloads the extra TF source it needs (e.g. MLIR/compiler files) itself via `FetchContent` at configure time. `litertextern/tfliteextern/CMakeLists.txt`'s `APPLE` branch picks its output subfolder (`runtimes/osx/native/arm64` or `.../x64`) via the same self-detected `IS_ARM64` (`check_symbol_exists("__aarch64__", ...)`) the `WIN32`/Linux branches already used — it used to check `EMGUCV_ARCH`, an Emgu.CV-only convention nothing in this repo ever sets, so it silently always fell into the x64 branch. `litert/tflite`'s own `profiling/proto`, `tools/benchmark/proto` (and transitively `model_runtime_info_proto`) CMake targets pass `protoc` a `--proto_path=${TENSORFLOW_SOURCE_DIR}` that doesn't encompass their actual `.proto` files (which live under `litert/tflite/`, not the separate FetchContent-downloaded TF tree `TENSORFLOW_SOURCE_DIR` points at) — breaking a plain `cmake --build .`, even though `tfliteextern` itself doesn't depend on any of them and builds fine alone. Since litert is a pristine submodule we don't patch upstream, `litertextern/tfliteextern/CMakeLists.txt` marks `profiling_info_proto`/`model_runtime_info_proto`/`benchmark_result_proto` `EXCLUDE_FROM_ALL` after the `ADD_SUBDIRECTORY` call instead, fixing `cmake --build .` generally; `platforms/macos/cmake_build_tflite` still targets `tfliteextern` specifically anyway, to skip litert's unrelated benchmark/example targets entirely. On macOS, `TFLITEEXTERN_LINK_LITERT` (an option in `litertextern/tfliteextern/CMakeLists.txt`, on by default for macOS only) makes the project `ADD_SUBDIRECTORY` LiteRT's own CMake project (`litert/litert`, which adds `litert/tflite` itself) instead of `litert/tflite` alone, and link `tfliteextern` against its `litert_runtime_c_api_shared_lib` (`libLiteRt.dylib`) — the same split as the Bazel build. On Apple, LiteRT's CMake links `libLiteRt` with `-all_load` and no export list, so it exports the `TfLite*` C API tfliteextern needs (and ~10k symbols in all — 14.9 MB for arm64 vs 6.8 MB from Bazel), and links Metal itself. `platforms/macos/cmake_build_tflite` configures with `CMAKE_BUILD_TYPE=Release` (the Makefile generator ignores `--config`) and `CMAKE_POLICY_VERSION_MINIMUM=3.5` (as LiteRT's presets do, for CMake 4). The CMake build's TFLite reports TensorFlow 2.21.0-rc0 (the `GIT_TAG` litert/tflite's CMake downloads; `litertextern/tfliteextern/CMakeLists.txt` defines `TF_MAJOR_VERSION` etc. from it before adding LiteRT's directories; LiteRT's own CMake hard-codes a stale 2.19.0 on its `tensorflow-lite` target (or, before the v0.18.0 update, defined nothing, so `version.h` fell back to it) - ours comes later on the compiler command line and wins, with harmless `-Wmacro-redefined` warnings) vs 2.22.0-dev0 from Bazel (LiteRT-LM's `TENSORFLOW_REF`). Windows/Linux CMake builds keep the statically linked tfliteextern. Only single-arch (host) builds are supported from CMake — setting `CMAKE_OSX_ARCHITECTURES` to build a universal arm64+x86_64 binary in one pass breaks that same `check_symbol_exists()` detection, since it only compiles for one architecture at a time; a fat binary would need separate per-arch builds `lipo`'d together, as the Bazel path already does.
     - Bazel needs the wrapper package to live *inside* a LiteRT(-LM) workspace (a pristine submodule we don't patch upstream), so `bazel_build_litert.ps1` (Windows), `bazel_build_tflite_macos` (macOS), `bazel_build_tflite_ios` (iOS/Mac Catalyst), `platforms/android/bazel_build_tflite_android`, and the Ubuntu and Debian (`platforms/{ubuntu/*,debian/{bookworm,trixie}}/bazel_build_tflite`) scripts each copy `litertextern/tfliteextern/bazel/{BUILD,tfliteextern.def}` plus the shared `litertextern/tfliteextern/*.cc/.h` and `litertextern/imgproc/*.cc/.h` sources into a fresh `tfliteextern/` package inside that workspace on every run, then build from there. All of them stage into `LiteRT-LM/tfliteextern/` and build in the **LiteRT-LM** submodule's workspace, with the `BUILD` file's `//tflite`/`//litert` labels rewritten to `@litert//...` (LiteRT-LM's `WORKSPACE` fetches LiteRT as the external repository `@litert`, pinned to the same commit as the `litert` submodule — see the macOS bullet below). Bazel always fetches its own pinned TF archive (no local-submodule-reuse option — see the copied `BUILD`'s comments for why). The `BUILD` file's `.def`/`/DEF:` export-list trick is Windows-only (via `select()`); other platforms export every non-static symbol by default, verified by inspecting each build's symbol table. Switching Windows from `litert` to `LiteRT-LM` needed no change to the checked-in `litert_windows_exports.def` — verified by rebuilding `//tfliteextern:libLiteRt` against the newer commit and comparing `dumpbin /exports` (653 live exports vs. 652 listed) and by re-running `Emgu.TF.Lite.Test.Net`'s `TestGetVersion` against the resulting `tfliteextern.dll`.
       - `tfliteextern.cc` uses only the TensorFlow Lite **C API** (`tflite/c/c_api.h`, `c_api_experimental.h`, `common.h`, plus `tflite/schema/schema_generated.h` for model introspection). The `tfe*` entry points the C# side P/Invokes are unchanged, but their opaque handles are now tfliteextern's own small wrapper structs (`TfeModel`, `TfeInterpreter`, ...) around the C API objects. Gaps vs. the old C++-API wrapper: `TensorSize`/`NodeSize` come from the model's primary subgraph (excluding tensors/nodes delegates add); the C API fixes the thread count at creation, so `SetNumThreads` before `AllocateTensors` re-creates the interpreter (re-applying delegates) and after it is ignored with a stderr warning; `DynamicBuffer` (string tensors) is reimplemented on top of the exported `TfLiteTensorReset`. Errors reported through `tfeRedirectError`'s callback are thrown as exceptions by the C# handler, which .NET can't unwind through native frames on macOS/Linux — so new non-fatal diagnostics go to stderr instead. On Android, NNAPI uses its C API (`TfLiteNnapiDelegateCreate`, part of `libLiteRt.so`); the TFLite GPU delegate V2 is C++, Android-only, and compiled out (`WITHOUT_GPU_DELEGATE`, `tfeGpuDelegateV2Create` returns null) in the dynamically linked Android build.
       - `//tfliteextern:tfliteextern` (a `cc_binary`, `linkshared`) is the shared-library form used by Windows (and the static-link fallback elsewhere), statically linking the TFLite C API. **macOS** instead builds `//tfliteextern:tfliteextern_dylib`, a `cc_shared_library` with `dynamic_deps = [":litert_runtime"]`: `:litert_runtime` builds `libLiteRt.dylib` from LiteRT's `//litert/c:litert_tflite_runtime_c_api_so_shim` (LiteRT's runtime, exporting both the `LiteRt*` and `TfLite*` C APIs via the staged `litert_exported_symbols_darwin.lds`), with the install name set and `-framework Metal` linked — LiteRT's own `litert_tflite_runtime_c_api_so` sets neither, and its `.bazelrc` builds macOS with `-undefined dynamic_lookup`, so its `MTLCreateSystemDefaultDevice` reference would otherwise only resolve if something else loaded Metal. `exports_filter` lets `tfliteextern_dylib` take every TFLite library from `libLiteRt.dylib`, so `libtfliteextern.dylib` is only the wrapper (~80 KB per arch vs ~7–9 MB when statically linked) and depends on `@rpath/libLiteRt.dylib` with an `@loader_path` rpath. `bazel_build_tflite_macos` builds these in the `LiteRT-LM/` submodule's Bazel workspace (Bazel 7.6.1 per its `.bazelversion`), against the LiteRT commit LiteRT-LM's `WORKSPACE` fetches as the external repository `@litert` (`26895c9f` for LiteRT-LM v0.18.0, the same commit the `litert` submodule is pinned to), so `libLiteRt.dylib` comes from the same LiteRT source as LiteRT-LM's own `liblitert-lm.dylib` (built with `--define=litert_runtime_link_mode=dynamic`, it depends on `@rpath/libLiteRt.dylib`, and ours exports every `LiteRt*` function it calls). While staging, the script rewrites our `BUILD` file's `"//tflite`/`"//litert` labels to `"@litert//...`; that LiteRT has no `tflite/ios/ios.bzl`, so `BUILD` defines the iOS minimum version itself. `.gitmodules` sets `ignore = dirty` on both submodules, so the staged `tfliteextern/` packages don't show as changes. For `darwin_arm64` the script also builds LiteRT-LM's `//c:litert-lm` that way, as a separate Bazel invocation with `--platform_suffix=-litert_lm_dynamic` (the define can't apply to our targets — in dynamic mode LiteRT's C API libraries resolve to headers only — and isn't part of Bazel's output folder name, so without the suffix the two builds would overwrite each other's outputs), and copies it to `lib/runtimes/osx/native/liblitert-lm{-darwin_arm64,}.dylib` (install name fixed to `@rpath/liblitert-lm.dylib`) together with LiteRT-LM's prebuilt `libGemmaModelConstraintProvider.dylib`, which it depends on and which is checked to be a real Mach-O file, not a Git LFS pointer. LiteRT-LM doesn't support Intel Macs (that prebuilt only exists for macOS arm64), so `liblitert-lm.dylib` is arm64 only, while `libLiteRt.dylib`/`libtfliteextern.dylib` stay universal; TFLite's kernels and XNNPACK remain inside `liblitert-lm.dylib` (~30 MB), since its embedding code uses TFLite's C++ API. Verified: loading `liblitert-lm.dylib` and `libtfliteextern.dylib` in one process maps a single `libLiteRt.dylib`. `bazel_build_tflite_macos <cpu>` builds both targets, copies them to `lib/runtimes/osx/native/{libtfliteextern,libLiteRt}-<cpu>.dylib` (dropping Bazel's extra `_solib`/runfiles rpaths, then re-signing ad hoc since `install_name_tool` invalidates the arm64 signature), and `lipo`s each into the universal `libtfliteextern.dylib`/`libLiteRt.dylib`; `bazel_build_tflite_macos_fat` drives `darwin_arm64` and `darwin`.
       - `libLiteRt.dylib` is also what the `Emgu.LiteRT` C# classes (`Emgu.LiteRT/`, built by `Emgu.LiteRT/NetStandard/Emgu.LiteRT.csproj` into its own `Emgu.LiteRT.dll`, configured from `cmake/Emgu.LiteRT.*.in`) P/Invoke directly via `DllImport("libLiteRt")` — one runtime serves both the `Emgu.TF.Lite` (Interpreter) and `Emgu.LiteRT` (CompiledModel) APIs. GPU/NPU accelerators are optional plugin dylibs (`libLiteRtMetalAccelerator.dylib` etc.) it tries to load at runtime; without them it logs a warning and uses the built-in XNNPACK CPU accelerator. XNNPACK is part of `libLiteRt`, so on macOS the Interpreter API also uses it by default (the static builds still compile tfliteextern with `-DWITHOUT_XNNPACK`). When `lib/runtimes/osx/native/libLiteRt.dylib` exists, the top-level `CMakeLists.txt` adds it to the `Emgu.LiteRT.runtime.macos` nuspec next to `libtfliteextern.dylib`, and `Emgu.LiteRT.Runtime/Mac`'s `.projitems` copies it to the build output; the CPack zip already picks it up via its `*.dylib` install pattern.
       - **iOS** uses the same dynamic split as macOS and Android: `platforms/ios/bazel_build_tflite_ios_frameworks` (also run by `bazel_build_xcframework`) builds the macOS targets `//tfliteextern:litert_runtime` and `//tfliteextern:tfliteextern_dylib` (both also `target_compatible_with` iOS) with `--config=ios_arm64` / `ios_sim_arm64` and `--ios_minimum_os=15.0` in the LiteRT-LM workspace, and wraps them (`platforms/ios/ios_frameworks.sh`: install name `@rpath/<name>.framework/<name>`, references to the other libraries changed to their frameworks, Bazel's rpaths replaced by `@loader_path/..`, an `Info.plist`, ad hoc signing) into `lib/ios/LiteRt.xcframework` (LiteRT's runtime, ~6.5 MB per slice, `LiteRt*`/`TfLite*` exported - every one of `Emgu.LiteRT`'s 39 imports) and `lib/ios/tfliteextern.xcframework` (~80-100 KB, linked to `@rpath/LiteRt.framework/LiteRt`), device arm64 + simulator arm64. LiteRT-LM's `.bazelrc` applies its `build:macos` config on a macOS host even to iOS builds, including `-undefined dynamic_lookup`, so a missing symbol doesn't fail the link: the scripts' `check_bound` fails the build if `nm -m -u` shows any symbol not bound to a library. That found TFLite's iOS platform profiler calling `tflite::profiling::MaybeCreateSignpostProfiler()`, from the `objc_library` `//tflite/profiling:signpost_profiler`, which `cc_shared_library` silently leaves out (its graph aspect doesn't cover `objc_library`), so `:litert_runtime` passes that archive (`:signpost_profiler_archive`) to the link on iOS. `Emgu.LiteRT.Runtime/Maui/iOS`'s `.csproj` embeds both (`NativeReference Kind=Framework`), and the DllImports name them by path: `TfLiteInvoke.ExternLibrary` is `@rpath/tfliteextern.framework/tfliteextern` and `LiteRtInvoke.LiteRtLibrary` `@rpath/LiteRt.framework/LiteRt` on iOS (Mac Catalyst and Unity iOS keep the static `__Internal` tfliteextern). The top-level `CMakeLists.txt` sets `HAVE_IOS_LITE` when both xcframeworks exist. Before, iOS linked a static `tfliteextern` with its own TFLite into the app, and `Emgu.LiteRT` used the LiteRT inside LiteRT-LM's CLiteRTLM framework, so it needed the LiteRT-LM add-on and iOS 26.4.
       - `//tfliteextern:tfliteextern_ios_framework` (a `cc_library` wrapped in `ios_static_framework`, no `hdrs` — the umbrella header rules_apple would generate collides with our own `tfliteextern.h`) is the static-library form, where `DllImport("__Internal")` finds the tfe* symbols in the app binary; the iOS runtime no longer uses it. `bazel_build_tflite_ios <config>` (configs: `ios_arm64`, `ios_sim_arm64`, `ios_x86_64`, `ios_armv7`, `darwin_x86_64`/`darwin_arm64`) unzips the resulting `tfliteextern.framework`, extracts the raw archive, and names it `lib/ios/libtfliteextern_<config>.a`; `bazel_build_mac_catalyst` (`darwin_x86_64` + `darwin_arm64`) drives two configs.
         - **Mac Catalyst does not work through Bazel**: rules_apple/apple_support have no Catalyst platform, and `bazel_build_tflite_ios darwin_<arch>` (and so `bazel_build_mac_catalyst`) actually produce **iOS Simulator** objects (`LC_BUILD_VERSION` platform 7, not Mac Catalyst's 6), which a Catalyst app can't link. Use `platforms/ios/cmake_build_tflite_catalyst` instead (see Building).
       - `platforms/android/bazel_build_tflite_android <arch>` (`x86`, `x86_64`, `arm`, `arm64`) stages the same `litertextern/` sources into the **LiteRT-LM** workspace exactly as the macOS script does (labels rewritten to `@litert//...`, so `libLiteRt.so` comes from LiteRT-LM's pinned LiteRT) and, like macOS, builds tfliteextern linked dynamically against LiteRT's runtime: `//tfliteextern:litert_runtime_so` (`libLiteRt.so` from `//litert/c:litert_tflite_runtime_c_api_so_shim`, exporting `LiteRt*`/`TfLite*` via the staged `litert_exported_symbols_linux.lds` version script, with `-Wl,-soname,libLiteRt.so` — LiteRT's own `litert_tflite_runtime_c_api_so` sets no SONAME, which would make `libtfliteextern.so` record a Bazel output path as its `DT_NEEDED`) and `//tfliteextern:tfliteextern_so` (`libtfliteextern.so`, `cc_shared_library` with `dynamic_deps`, sharing the `:tfliteextern_capi_lib` wrapper library with macOS). Both are copied to `lib/android/<abi>/` (matching what `Emgu.LiteRT.Runtime/Maui/Android`'s `.csproj` packages; it also packages `libLiteRt.so` when present). `libLiteRt.so` contains the TFLite C API, XNNPACK and the NNAPI delegate (C API - `:litert_runtime_so` lists `//tflite/delegates/nnapi:nnapi_delegate` and `:nnapi_delegate_no_nnapi_implementation` as Android deps itself, since LiteRT's runtime stopped pulling it in after the LiteRT-LM v0.17.1 commit, which made the v0.18.0 Android link fail with undefined `TfLiteNnapiDelegateCreate`) but not the TFLite GPU delegate V2 — LiteRT does GPU through its separate accelerator plugin — and that delegate needs TFLite internals `libLiteRt.so` doesn't export, so `:tfliteextern_capi_lib` defines `WITHOUT_GPU_DELEGATE` on Android. Each `.so` links its own static libc++ (most of `libtfliteextern.so`'s ~0.9 MB stripped size); only C APIs cross between them. The script strips both with the NDK's `llvm-strip --strip-unneeded` (found under `$ANDROID_NDK_HOME/toolchains/llvm/prebuilt/*/bin`, so it works from a Linux or macOS host): debug info otherwise roughly triples their size, and the dynamic symbol tables are unchanged (verified). Stripped sizes: `libLiteRt.so` 3.8–8.8 MB, `libtfliteextern.so` 0.6–0.9 MB depending on the ABI. Verified on an arm64 API 35 emulator: the MAUI demo loads both libraries and calls into `libLiteRt.so`. For `arm64` and `x86_64` it also copies LiteRT-LM's prebuilt GPU (OpenCL) accelerator `libLiteRtOpenClAccelerator.so`, and builds LiteRT-LM's `//c:litert-lm` with `--define=litert_runtime_link_mode=dynamic --platform_suffix=-litert_lm_dynamic` (as on macOS) and copies `liblitert-lm.so` (stripped; `DT_NEEDED` `libLiteRt.so`, `RUNPATH $ORIGIN`) plus LiteRT-LM's prebuilt `libGemmaModelConstraintProvider.so` to `lib/android/<abi>/`; that prebuilt only exists for those two ABIs, so `armeabi-v7a`/`x86` get no LiteRT-LM. Its 43 `LiteRt*` imports carry the `VERS_1.0` symbol version, which our `libLiteRt.so` (`litert_exported_symbols_linux.lds`) defines too — verified that every import of `liblitert-lm.so` and `libtfliteextern.so` resolves. On a Linux host with clang installed, the script adds `--repo_env=CC=clang --repo_env=CXX=clang++` so the host-side build tools (Bazel's `[for tool]` actions; Android code itself uses the NDK) are compiled with clang: Ubuntu 26.04's GCC 15 rejects Abseil's `raw_hash_set.cc` ("Never use <bmi2intrin.h> directly"). On a macOS host the script adds `--host_linkopt=-Wl,-undefined,dynamic_lookup`: LiteRT-LM's `build:android` sets `--noenable_platform_specific_config`, so its `build:macos` host link option doesn't apply, and without it the host Rust proc-macro dylibs its build tools need come out unloadable by dyld ("mis-aligned LINKEDIT string pool"), failing with rustc `E0463 can't find crate`. Verified on the arm64 API 35 emulator: the MAUI demo loads `libtfliteextern.so`/`libLiteRt.so` built this way and creates the XNNPACK delegate. Two things needed fixing beyond staging the sources:
         - The statically linked `//tfliteextern:tfliteextern` (no longer what the script builds) still links the GPU delegate on Android: `litertextern/tfliteextern/bazel/BUILD`'s `_TFLITEEXTERN_DEPS` adds `//tflite/delegates/gpu:delegate` + `:delegate_options` (and NNAPI) behind a `select({"@org_tensorflow//tensorflow:android": [...], "//conditions:default": []})` — those targets need EGL and don't build on the other platforms.
         - Of litert's four `.bazelrc` `android_*` configs, only `android_arm64` sets `--incompatible_enable_cc_toolchain_resolution`/`--incompatible_enable_android_toolchain_resolution`; the other three fall back to a legacy `--crosstool_top=//external:android/crosstool` alias that isn't actually defined anywhere in this WORKSPACE (it silently resolves to the host `local_config_cc` toolchain instead, which doesn't have a toolchain for a non-host cpu, or produces `/bin/false`-stubbed compile actions). The build script passes both flags explicitly for every arch to force the same NDK-toolchain-via-platforms resolution arm64 already gets from its config.
       - `platforms/ubuntu/24.04/bazel_build_tflite` follows the same staging pattern, builds `//tfliteextern:tfliteextern` with `--config=linux` (`--config=linux_arm64` too on an aarch64 host), and copies the result to `lib/runtimes/ubuntu-x64/native/libtfliteextern.so` (or `ubuntu-arm64`), matching what `Emgu.LiteRT.Runtime/Ubuntu`'s `.projitems` expects. No GPU-delegate select() or toolchain-resolution override needed here — Linux isn't `__ANDROID__` and already resolves its host toolchain correctly.
   - `platforms/debian/{bookworm,trixie}/bazel_build_tflite` (identical files) build `//tfliteextern:litert_runtime_so` and `//tfliteextern:tfliteextern_so` on a native ARM Debian host (`--config=linux --config=linux_arm64` on 64-bit, plain `--config=linux` on armhf) with clang forced via `--repo_env=CC=/usr/bin/clang` (GCC >= 14 rejects LiteRT's `target("dotprod")` attribute), and copy `libLiteRt.so`/`libtfliteextern.so` to `lib/runtimes/linux-arm64/native/` (or `linux-arm`).
2. **P/Invoke layer** — `TfLiteInvoke` (in `Emgu.TF.Lite/`, namespace `Emgu.TF.Lite`) is a partial static class that exposes the native DLL entry points via `[DllImport]`.
3. **Managed wrappers** — `Interpreter`, `Tensor`, etc. inherit `UnmanagedObject` (from `Emgu.LiteRT.Util/`, namespace `Emgu.LiteRT.Util`, built into its own `Emgu.LiteRT.Util.dll`) and wrap native handles with proper lifetime management.
   - `Emgu.LiteRT/` is a separate managed wrapper (own `Emgu.LiteRT.dll`, namespace `Emgu.LiteRT`) over LiteRT's own `libLiteRt` C API — `Environment`, `Model`, `CompiledModel`, `TensorBuffer`, etc. — with no Emgu native layer.
   - `Emgu.LiteRT.LM/` (own `Emgu.LiteRT.LM.dll` and nuget package `Emgu.LiteRT.LM`, namespace `Emgu.LiteRT.LM`, depending on `Emgu.LiteRT.Util` only) wraps LiteRT-LM's C API (`LiteRT-LM/c/*.h`, the `litert_lm_*` functions exported by `liblitert-lm`) the same way, via `DllImport("liblitert-lm")` (`__Internal` on iOS): `EngineSettings`/`Engine` (load a `.litertlm` model; tokenize, start/stop tokens), `SessionConfig`/`SamplerParams`/`Session` (`GenerateContent`, `RunPrefill`/`RunDecode`, scoring, checkpoints), `InputData`, `Responses`, `ConversationConfig`/`ThinkingConfig`/`ConversationOptionalArgs`/`Conversation` (JSON messages in LiteRT-LM's format; `Conversation.CreateTextMessage` builds one), `LoadedFile` (model capabilities) and `BenchmarkInfo`, plus the embedding engine (`EmbeddingEngine.cs`: `EmbeddingEngineSettings` - model, backends, threads, cache folder, min/max input length, activation type - audio threads, vision tokens per image, NPU dispatch folders - `EmbeddingOptions` - `Normalize`, `InsertSpecialTokens`, `InputOverflowStrategy`, `OutputSize`, `VisionTokensPerImage` - and `EmbeddingEngine` with `ComputeEmbedding(text | InputData[])`, `ComputeEmbeddings(texts | InputData[][])` as one batch, and `CosineSimilarity`; it loads GPU plugins like `Engine`); the experimental header isn't wrapped yet. `Emgu.LiteRT.LM.Models`' `EmbeddingModel` (download + load like `LanguageModel`; `Embed`, `EmbedQuery`/`EmbedDocuments` with the model's prompt prefixes, normalized) and `EmbeddingGemma2` (`litert-community/embeddinggemma-2-text-270m-litert-lm`'s `embeddinggemma-2-text-270m.litertlm`, 165 MB, Apache 2.0, 768 values or 512/256/128, EmbeddingGemma's `task: search result | query: ` / `title: none | text: ` prefixes) wrap it; `TestEmbeddingGemma2`: on an M1's CPU it loads in ~6 s, embeds a query in ~66 ms, the batch equals single embeddings, and each of 5 questions finds the document that answers it (cosine ~0.8 vs <0.72 for the rest; ## Building

### Prerequisites
- .NET SDK
- Visual Studio 2022 or VS 2026 (detected automatically by `vswhere.exe`) — Windows
- CMake 3.16+
- Bazel (for the Bazel native builds; the version is pinned by `litert/.bazelversion`). The macOS and Android Bazel scripts set `HERMETIC_PYTHON_VERSION=3.12` when `python3.12` is on the `PATH`.
  - The macOS, iOS and Android Bazel scripts run `bazel --output_user_root=<repo>/bazel_output build ...`, so Bazel's output tree, install base and cache (several GB per platform) live in `bazel_output/` at the repo root — gitignored, outside the `litert/` workspace — instead of the default `/private/var/tmp/_bazel_$USER` (macOS) or `~/.cache/bazel` (Linux). Running `bazel` by hand in `litert/` needs the same startup flag (e.g. `bazel --output_user_root="$(cd .. && pwd)/bazel_output" build ...` — use an absolute path), otherwise Bazel starts a separate server with a cold cache in the default location. Deleting `bazel_output/` forces a full rebuild.
- Xcode — macOS/iOS. The macOS script handles an Xcode installed outside `/Applications` (e.g. on another volume) by passing `DEVELOPER_DIR` into Bazel's sandbox.
- Android SDK + NDK, and a JDK — Android (see below)
- TF Lite native library already built and placed under `lib/runtimes/` (or `lib/android/`, `lib/ios/`)

### Build native TF Lite (Windows x64)
```powershell
cd platforms/windows
.\cmake_build_litert.ps1 64 xnn
```
Or via Bazel (also produces `lib/runtimes/win-x64/native/tfliteextern.dll`):
```powershell
cd platforms/windows
.\bazel_build_litert.ps1 64
```

Verified with LiteRT-LM v0.18.0 (`litert_windows_exports.def` unchanged: 652 live exports vs 652 listed; `TestGetVersion` passes). The scripts aren't signed, so from a shell with a restrictive execution policy run them as `powershell -NoProfile -ExecutionPolicy Bypass -File .\bazel_build_litert.ps1 64` (XNNPACK is on by default; `-DisableXnn` turns it off).

### Build the .NET solution (Windows)
```powershell
cd platforms/windows
.\build_emgu_litert.ps1
```
Optional args: `doc` (build docs), `nuget` (build NuGet packages), `package` (build zip packages).

Building `Emgu.LiteRT.Example/Maui.Lite/Maui.Demo.Lite.csproj` after pulling changes needs, in order: the native build above, `build_emgu_litert.ps1` (re-runs CMake, which generates the `Directory.Build.props` of any new project, e.g. `Emgu.LiteRT.LM.Extensions.AI` — otherwise NU1201 "does not support any target frameworks") and `build_emgu_litert.ps1 "" nuget` (the demo restores `Emgu.TF.Lite.runtime.windows` at the new version from `platforms/nuget/`; otherwise NU1102). If the demo build then fails with NETSDK1152 (duplicate `msvcp140.dll`/`vcruntime140.dll`/... publish outputs), remove those MSVC runtime DLLs from `lib/runtimes/win-x64/native/` — they duplicate the `Emgu.runtime.windows.msvc.rt.x64` package. Redeploying the packaged app with `Remove-AppxPackage` also deletes its `LocalApplicationData` (the downloaded LiteRT-LM models), so they are downloaded again.

### Build native TF Lite (macOS)
```bash
platforms/macos/bazel_build_tflite_macos_fat
```
Builds `arm64` and `x86_64` and writes the universal `lib/runtimes/osx/native/libtfliteextern.dylib` and `libLiteRt.dylib`, plus the arm64-only `liblitert-lm.dylib` and `libGemmaModelConstraintProvider.dylib` (needs `git -C LiteRT-LM lfs pull`) (plus the per-arch `*-darwin_arm64.dylib`/`*-darwin.dylib` they are `lipo`'d from).
```bash
platforms/macos/bazel_build_tflite_macos darwin_arm64   # or: darwin (x86_64, cross-compiled on Apple Silicon)
```
Alternative CMake build — host architecture only. After moving the `litert` submodule, the reused build folder (`litertextern/tfliteextern/build/`) can keep a stale KleidiAI download that the new XNNPACK doesn't match ("use of undeclared identifier 'kai_matmul_...'" in `xnnpack/src/reference/packing.cc`): delete `build/kleidiai*` and the `KLEIDIAI_SOURCE_DIR` entry in `build/CMakeCache.txt` (or start from an empty build folder). Like the Bazel build it produces both `libLiteRt.dylib` and a thin `libtfliteextern.dylib` linked against it (`@rpath` install names, `@loader_path` rpath, XNNPACK on); output goes to `lib/runtimes/osx/native/<arm64|x64>/`:
```bash
platforms/macos/cmake_build_tflite
```

### Build the .NET solution and packages (macOS)
```bash
platforms/macos/build_emgutf
```
Configures CMake in `build/` (Release) and runs `make package`: builds the managed projects, writes the NuGet packages (`Emgu.LiteRT`, `Emgu.TF.Lite`, `Emgu.LiteRT.Util`, `Emgu.TF.Lite.ImageIO`, `Emgu.LiteRT.Tflite.Models`, `Emgu.LiteRT.runtime.*`) to `platforms/nuget/`, and the CPack zip to `build/libemgulitert-ios-macos-<version>.zip`. The version's last component is derived from the git commit count, so it changes with every commit. Run the native build first: packages only include the native binaries already in `lib/`.

### Build native TF Lite (Mac Catalyst)
```bash
platforms/ios/cmake_build_tflite_catalyst arm64   # or: x86_64 (cross-compiled on Apple Silicon)
```
Writes `lib/ios/libtfliteextern_darwin_<arch>.a`, the self-contained static libraries `Emgu.LiteRT.Runtime/Maui/Mac`'s `.csproj` force-loads into a Catalyst app (`DllImport` resolves the `tfe*` symbols from the app binary, as on iOS). It configures `litertextern/tfliteextern`'s CMake project with clang's `-target <arch>-apple-ios15.0-macabi` (on the C/C++/Objective-C(++) compiler and linker flags), statically linking TFLite (`TFLITEEXTERN_LINK_LITERT=OFF`, XNNPACK off like the static iOS builds) into a build-only `libtfliteextern.dylib` — that link proves every symbol resolves for Catalyst and its `link.txt` lists exactly the static libraries needed, which the script merges with tfliteextern's objects via `libtool -static`. Build folders are `litertextern/tfliteextern/build_catalyst_<arch>/` (gitignored). Every object is Mac Catalyst (`LC_BUILD_VERSION` platform 6, minos 15.0). Catalyst is `CMAKE_SYSTEM_NAME` Darwin to CMake but `TARGET_OS_IOS` to the compiler, so `litertextern/tfliteextern/CMakeLists.txt` detects it (`TFLITEEXTERN_TARGET_MACCATALYST`) and adds `litert/tflite/profiling/signpost_profiler.mm` to `tensorflow-lite` itself — litert's CMake only compiles it for `CMAKE_SYSTEM_NAME` iOS, while `platform_profiler.cc` calls it whenever `TARGET_OS_IOS`; Objective-C++ must be enabled before litert's subdirectory is added, and `PROJECT(tfliteextern)` comes first in that file so the check can compile. Verified by running the MAUI demo as a Catalyst app on macOS 27 (the About page reads the TFLite version through the `tfe*` API). Building the demo for Catalyst needed:
- `net10.0-maccatalyst` in the MAUI UI runtime's target frameworks (`cmake/Emgu.LiteRT.runtime.maui.Directory.Build.props.in`, macOS/Windows hosts) — otherwise Catalyst apps resolve its `netstandard2.0` build, which never references the Mac runtime project, so no tfliteextern was linked at all.
- The UIScene life cycle: UIKit refuses to launch apps built with the macOS 27 SDK without it, so `Emgu.LiteRT.Example/Maui.Lite/Platforms/MacCatalyst/Info.plist` declares a `UIApplicationSceneManifest` using MAUI's default scene configuration with `SceneDelegate.cs` (a `MauiUISceneDelegate`).
- `-p:ValidateXcodeVersion=false` when the .NET MacCatalyst SDK pack doesn't match the installed Xcode exactly (e.g. pack 26.5 wants Xcode 26.6 while Xcode 27.0 is installed): `dotnet build Emgu.LiteRT.Example/Maui.Lite/Maui.Demo.Lite.csproj -f net10.0-maccatalyst -c Debug -p:ValidateXcodeVersion=false`. MAUI incremental builds may keep a stale bundled `Info.plist`; delete `bin/obj/Debug/net10.0-maccatalyst` after editing it.

### Build native TF Lite (Android, from Linux or macOS)
The Android binaries can be built on either a Linux or a macOS host, with the same script:
```bash
platforms/android/bazel_build_tflite_android arm64   # or: x86_64, arm, x86
```
Writes `lib/android/<abi>/libtfliteextern.so` and `libLiteRt.so` (`arm64-v8a`, `x86_64`, `armeabi-v7a`, `x86`), 16 KB page-aligned and stripped of debug info, plus `liblitert-lm.so` and `libGemmaModelConstraintProvider.so` for `arm64-v8a`/`x86_64` only (needs `git -C LiteRT-LM lfs pull`). `libtfliteextern.so` links dynamically against `libLiteRt.so`, LiteRT's runtime, which `Emgu.LiteRT` also uses directly. NNAPI is supported; the TFLite GPU delegate isn't (`tfeGpuDelegateV2Create` returns null). Run once per ABI; extra arguments are passed to `bazel build`. The script reads the SDK from `ANDROID_HOME` and the NDK from `ANDROID_NDK_HOME`, else the newest version under `$ANDROID_HOME/ndk`:
- **Linux**: `ANDROID_HOME` defaults to `/usr/lib/android-sdk` (the build image layout) when unset.
- **macOS**: set `ANDROID_HOME` to the Android Studio SDK, usually `~/Library/Android/sdk` (no default — the Linux path doesn't exist there). Verified with NDK 28.0.12916984 for all four ABIs.

### Build and run the MAUI demo (Mac Catalyst, iOS, Android)
Step-by-step instructions are in `Emgu.LiteRT.Example/Maui.Lite/README.md`. In short: build the platform's natives (Mac Catalyst: `cmake_build_tflite_catalyst arm64` plus `bazel_build_tflite_macos_fat` for the LiteRT-LM dylibs; iOS: `bazel_build_xcframework` and `bazel_build_litert_lm_ios`; Android: `bazel_build_tflite_android <abi>` with `ANDROID_HOME` set), generate the projects' `Directory.Build.props` (`platforms/macos/build_emgutf` or `cmake .` in `build/` - again after pulling a new project, otherwise NU1201), then `dotnet build Emgu.LiteRT.Example/Maui.Lite/Maui.Demo.Lite.csproj -f net10.0-<platform>`. Pitfalls: `-p:ValidateXcodeVersion=false` when the .NET Apple SDK pack doesn't match Xcode; `-p:RuntimeIdentifier=iossimulator-arm64` / `android-arm64` to build one architecture; `-p:AdbTarget="-s <serial>"` with several adb devices; `Emgu.LiteRT.Example/Maui.Lite/tools/deploy_android [serial ...]` builds/installs/starts the Debug app on Android devices and copies the models the Mac already has (`~/Documents/LiteRT-LM`, `~/Library/Application Support/LiteRT-LM`) into the app's private `files/LiteRT-LM` via `adb exec-in run-as <id> sh -c 'cat > ...'` - `exec-in` returns before the device has written everything, so the script waits for the full size - with the original's modification time (`touch -d @<sec.ns>`; .NET's ticks then match) and `.sha256ok` marker, so the app neither downloads nor hashes it (verified on the Pixel 8 emulator: the app's `LastWriteTimeUtc.Ticks` equalled the marker's); it uses `/usr/bin/stat` since a GNU `stat` may come first on the PATH; delete `bin`/`obj` for the platform after editing an `Info.plist`; the Catalyst `.app` is `bin/Debug/net10.0-maccatalyst/maccatalyst-arm64/Emgu LiteRT.app` (the `ApplicationTitle`, renamed from "Emgu TF Lite Maui Demo"; the `ApplicationId` is `com.emgu.litert`, changed from `com.emgu.tf.lite.maui.demo` - Android and iOS install it as a new app, without the old one's downloaded models and saved chats; on Mac Catalyst those live in `~/Documents/LiteRT-LM` and `~/Library/chats` and carry over, Preferences and SecureStorage don't). A clean Mac Catalyst build of the demo used to fail in the SDK's `_InstallNameTool` step, hidden by incremental builds: `bazel_build_tflite_macos` left the dylibs in `lib/runtimes/osx/native/` read-only (`chmod u-w`, like bazel-bin), so the SDK's writable copy wasn't ("Permission denied" on `liblitert-lm.dylib.tmp`) - the script now leaves them writable - and the Metal add-on references the LiteRT-LM add-on, which the demo references too, so `liblitert-lm`/`libLiteRt`/`libGemmaModelConstraintProvider` were in `_FileNativeReference` twice and the two `install_name_tool` runs on each raced ("cannot rename ... .tmp") - the demo's `EmguRemoveDuplicateNativeReferences` target removes the duplicates first. (opening it with `open` makes macOS ask for microphone access for the app rather than the terminal). Testing without UI automation: a temporary `[ModuleInitializer]` file in the demo that drives `LiteRtLmChatPage` through reflection (gated by `EMGU_LM_SELFTEST=1` on Mac Catalyst / via `SIMCTL_CHILD_EMGU_LM_SELFTEST=1 xcrun simctl launch --console-pty` on iOS; Android can't pass an environment variable, so it must run unconditionally there - reinstall a clean build afterwards), with screenshots from `screencapture -l <window id>` (Catalyst) or `adb exec-out screencap -p -d <display id>` (Android; a foldable has one display per screen). UI freezes ("isn't responding"): Debug builds run `UiStallWatchdog` (started in `App`), which logs stalls of the UI thread over 1 s with the breadcrumbs pages leave via `UiStallWatchdog.Mark` and, on Android, the main thread's Java stack, to logcat (`UISTALL`) and the app data folder's `ui_stalls.log` (`adb shell run-as com.emgu.litert cat files/ui_stalls.log`); a Pixel Fold ANR at 20:17 on 2026-10-10 is still unexplained - streaming, model downloads and TTS voice listing were measured and ruled out. A phone over Wi-Fi: Wireless debugging, `adb mdns services`, `adb pair <ip>:<pairing port> <code>` once, then `adb connect <ip>:<connect port>` (also works over Tailscale).

## Running Tests

Tests use either NUnit or MSTest (selected at compile-time via the `VS_TEST` preprocessor symbol).

### TF Lite — run all tests
```bash
dotnet test Emgu.LiteRT.Test/Emgu.TF.Lite.Test/Emgu.TF.Lite.Test.Net/Emgu.TF.Lite.Test.Net.csproj
```

### Model-free tests in CI
`.github/workflows/tests.yml` runs the suite on Ubuntu without models or this repo's native libraries: `cmake -S . -B build` (generates the `Directory.Build.props`), then `dotnet test ... --filter "TestCategory!=Native"` (111 tests, ~4 s). Test classes that load `tfliteextern`/`libLiteRt` are in the `Native` category (`[Category("Native")]`, `[TestCategory]` under `VS_TEST`) - put new native-dependent test classes there too, or CI fails with `DllNotFoundException`.

`.github/workflows/native.yml`'s `ios` job builds the four iOS xcframeworks (`bazel_build_tflite_ios_frameworks`, `bazel_build_litert_lm_ios`), then the MAUI demo for the iOS simulator (`-f net10.0-ios -p:RuntimeIdentifier=iossimulator-arm64 -p:ValidateXcodeVersion=false`, no signing needed), and checks that the `.app`'s `Frameworks` folder holds all four as simulator binaries, with every `@rpath/*.framework` each one links also embedded. Its `windows` job runs `bazel_build_litert.ps1 64` on `windows-latest` (its own Bazelisk, passed to the script as `BAZEL_COMMAND`, which runs LiteRT-LM's `.bazelversion` - the runner's `bazel.exe` ran 9.x regardless of `USE_BAZEL_VERSION` - Python 3.12, `BAZEL_SH` = MSYS2's bash, from a `subst` drive letter to keep the LiteRT-LM build's paths under 260 characters), checks that all four DLLs were written - the script carries on past a failed Bazel build - and runs the whole test suite, `Native` tests included.

### Run a single test
```bash
dotnet test <project.csproj> --filter "FullyQualifiedName~TestGetVersion"
```

Test assets (e.g., `grace_hopper.jpg`) must be present in the working directory when tests run.

The LiteRT-LM tests (`UnitTestLiteRtLm.cs`) download large models on the first run (Qwen3-0.6B ~500 MB, Gemma 4 E2B ~2.6 GB, E4B ~3.7 GB), so they are ignored by default, the same way as Emgu CV's model tests: opt in with `dotnet test <project.csproj> -p:TestModels=true`, which defines `TEST_MODELS` (each test has an `#if !TEST_MODELS` `[Ignore]` block).

Like Emgu CV, the app and test projects target the .NET version of the `dotnet` CMake runs: `cmake/modules/FindCSharp.cmake` sets `DOTNET_VERSION_MAJOR` from `dotnet --version`, and per-project `Directory.Build.props` generated from `cmake/*.Directory.Build.props.in` set `<TargetFramework>net${DOTNET_VERSION_MAJOR}.0</TargetFramework>` (`-windows` for `CVInterop.Lite`, `-android`/`-ios`/`-maccatalyst` for the MAUI projects); the csproj files name no version (a `TargetFramework` in a csproj would override the generated props, which are imported first). Re-run CMake (`build_emgutf`, or `cmake .` in `build/`) after switching .NET SDKs. So `Emgu.TF.Lite.Test.Net` needs the CMake-generated `Directory.Build.props` files (run the platform's `build_emgutf` once), and on macOS it copies `libtfliteextern.dylib`/`libLiteRt.dylib` from `lib/runtimes/osx/native/` via `Emgu.LiteRT.Runtime/Mac`'s `.projitems`.

## Key Conventions

- **Extern library name**: `tfliteextern`. On iOS it is `@rpath/tfliteextern.framework/tfliteextern`; on Mac Catalyst and Unity iOS (static libraries) `__Internal`.
- **`UnmanagedObject`** (in `Emgu.LiteRT.Util/`): base class for all objects wrapping a native pointer; handles `Dispose`/finalizer pattern.
- **Calling convention**: `CallingConvention.Cdecl` throughout.
- **Boolean marshaling**: `UnmanagedType.U1` for `bool`, `UnmanagedType.Bool` for `int`-as-bool.
- **Error handling**: native errors are redirected via a callback delegate (`TfLiteErrorCallback`) and thrown as managed exceptions.
- There is no `tensorflow/` submodule — it was removed once the Windows CMake path was proven to work without it (LiteRT downloads the TF source it needs itself). The overall package version (`CPACK_PACKAGE_VERSION_*` in the top-level `CMakeLists.txt`, and `litertextern/tfliteextern/CMakeLists.txt`'s own version) is read from `litert/litert/version.bzl` (`LITERT_EXPERIMENTAL_VERSION`) via `cmake/modules/LitertVersion.cmake`, plus the git commit count. Exception: the TFLite-versioned packages (`Emgu.TF.Lite`, `Emgu.LiteRT.Tflite.Models`, `Emgu.TF.Lite.runtime.windows`) use the TFLite version, i.e. TensorFlow's `TF_VERSION` (`EMGU_TFLITE_PACKAGE_VERSION` = `<TF_VERSION>.<commit count>`, e.g. 2.22.0.N). Every native build writes a `tflite_version.txt` next to its libraries (the Bazel scripts from `$(bazel info output_base)/external/org_tensorflow/tensorflow/tf_version.bzl`, the CMake build from the TensorFlow it downloads), the same way as `tflite_with_xnnpack.txt`; the top-level `CMakeLists.txt` reads all of them under `lib/` (highest wins, with a warning if they differ - e.g. a CMake-built 2.21.0 next to Bazel-built 2.22.0) and falls back to the LiteRT version when there are none. The root `Directory.Build.props` (from `cmake/Directory.Build.props.in`, imported at the end of each project's own props) only sets `Version` when the project hasn't, so the Tflite projects' version isn't overridden. The MAUI runtime's `PackageReference` to `Emgu.TF.Lite.runtime.windows` uses that version too; `ProjectReference`s to the Tflite projects pick it up automatically.
- The `litert/` directory is a submodule of `google-ai-edge/LiteRT`, pinned to commit `26895c9f` (`v2.2.0-643`): the LiteRT commit the `LiteRT-LM` submodule pins as its `@litert` repository (`LITERT_REF` in `LiteRT-LM/WORKSPACE`; LiteRT-LM v0.18.0). Do not modify files inside it directly.
  - **The `litert` submodule must match LiteRT-LM's LiteRT version.** The Bazel builds use LiteRT-LM's `@litert` (downloaded by Bazel), while the CMake builds (`litertextern/tfliteextern/CMakeLists.txt`) use this submodule; keeping them on the same commit means every `libLiteRt` is built from the same LiteRT source, so it is compatible with `liblitert-lm` (which links against it) and all platforms ship the same TFLite/LiteRT version. When updating the `LiteRT-LM` submodule, check its `LiteRT-LM/WORKSPACE` `LITERT_REF` and move `litert` to that commit too (`git -C litert checkout <LITERT_REF>`, then `git -C litert submodule update` for its nested `third_party/tensorflow`), and re-check the CMake builds. Then check whether the new `LITERT_REF` contains LiteRT commit `dd3db3123` ("Make the WeightLoader interface ABI-stable across the accelerator boundary"; `git -C litert merge-base --is-ancestor dd3db3123 HEAD`): if it does, the embedding models' GPU crash should be gone (see `Emgu.LiteRT.LM.Models`' `EmbeddingModel` above) - after rebuilding the natives, remove the "gpu" check from `EmbeddingModel.Init`, run `EmbeddingGemma2Multimodal` with `backend: "gpu"` and `VisionBackend = "gpu"` on the Mac (Metal) and the Pixel Fold (OpenCL), compare its embeddings with the CPU's (cosine > 0.99) and the text/image/audio searches, add a GPU test (skipped without the accelerator plugin, like `TestLiteRtMobilenetGpu`) and record the results. (Before following LiteRT-LM, `litert` was pinned to `v2.2.0`, not `main`: the bleeding-edge commit this was originally added at hit a WORKSPACE bug under Bazel; see `litertextern/tfliteextern/bazel/BUILD`'s comments.)
- `litertextern/` holds the Emgu-authored native wrapper (`tfliteextern`, `imgproc`) that both Windows build paths use — this is the one place native wrapper source changes should be made for that platform going forward. `litertextern/tfliteextern/bazel/{BUILD,tfliteextern.def}` is the Bazel-specific counterpart to `litertextern/tfliteextern/CMakeLists.txt`, staged into `LiteRT-LM/tfliteextern/` at build time (see above) since it can't live there in git.
