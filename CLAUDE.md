# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

Emgu TF Lite is a cross-platform .NET wrapper for the Google TensorFlow Lite library, enabling TF Lite functions to be called from C#, VB, VC++, and IronPython. It loads and runs TensorFlow Lite models on Windows, macOS, Linux, Android, and iOS.

The native C++ layer is exposed through P/Invoke via the `tfliteextern` extern library.

## Architecture

### Layer structure
1. **Native layer** — C/C++ wrapper DLL (`tfliteextern`) built with CMake or Bazel; must be present in `lib/runtimes/<rid>/native/` before building .NET code.
   - **Windows x64 (both CMake and Bazel)**, **macOS (Bazel)**, **iOS/Mac Catalyst (Bazel)**, **Android (Bazel)**, **Ubuntu (Bazel)**, and **Debian ARM (Bazel)** build against `litert/tflite` (the `google-ai-edge/LiteRT` submodule). There is no `tensorflow/` submodule in this repo.
     - CMake (Windows and macOS) builds directly from `litertextern/tfliteextern/`; `litert/tflite`'s own CMake project downloads the extra TF source it needs (e.g. MLIR/compiler files) itself via `FetchContent` at configure time. `litertextern/tfliteextern/CMakeLists.txt`'s `APPLE` branch picks its output subfolder (`runtimes/osx/native/arm64` or `.../x64`) via the same self-detected `IS_ARM64` (`check_symbol_exists("__aarch64__", ...)`) the `WIN32`/Linux branches already used — it used to check `EMGUCV_ARCH`, an Emgu.CV-only convention nothing in this repo ever sets, so it silently always fell into the x64 branch. `litert/tflite`'s own `profiling/proto`, `tools/benchmark/proto` (and transitively `model_runtime_info_proto`) CMake targets pass `protoc` a `--proto_path=${TENSORFLOW_SOURCE_DIR}` that doesn't encompass their actual `.proto` files (which live under `litert/tflite/`, not the separate FetchContent-downloaded TF tree `TENSORFLOW_SOURCE_DIR` points at) — breaking a plain `cmake --build .`, even though `tfliteextern` itself doesn't depend on any of them and builds fine alone. Since litert is a pristine submodule we don't patch upstream, `litertextern/tfliteextern/CMakeLists.txt` marks `profiling_info_proto`/`model_runtime_info_proto`/`benchmark_result_proto` `EXCLUDE_FROM_ALL` after the `ADD_SUBDIRECTORY` call instead, fixing `cmake --build .` generally; `platforms/macos/cmake_build_tflite` still targets `tfliteextern` specifically anyway, to skip litert's unrelated benchmark/example targets entirely. On macOS, `TFLITEEXTERN_LINK_LITERT` (an option in `litertextern/tfliteextern/CMakeLists.txt`, on by default for macOS only) makes the project `ADD_SUBDIRECTORY` LiteRT's own CMake project (`litert/litert`, which adds `litert/tflite` itself) instead of `litert/tflite` alone, and link `tfliteextern` against its `litert_runtime_c_api_shared_lib` (`libLiteRt.dylib`) — the same split as the Bazel build. On Apple, LiteRT's CMake links `libLiteRt` with `-all_load` and no export list, so it exports the `TfLite*` C API tfliteextern needs (and ~10k symbols in all — 14.9 MB for arm64 vs 6.8 MB from Bazel), and links Metal itself. `platforms/macos/cmake_build_tflite` configures with `CMAKE_BUILD_TYPE=Release` (the Makefile generator ignores `--config`) and `CMAKE_POLICY_VERSION_MINIMUM=3.5` (as LiteRT's presets do, for CMake 4). The CMake build's TFLite reports TensorFlow 2.21.0-rc0 (the `GIT_TAG` litert/tflite's CMake downloads; `litertextern/tfliteextern/CMakeLists.txt` defines `TF_MAJOR_VERSION` etc. from it before adding LiteRT's directories - LiteRT's CMake doesn't, so `version.h` otherwise falls back to a stale 2.19.0) vs 2.22.0-dev0 from Bazel (LiteRT-LM's `TENSORFLOW_REF`). Windows/Linux CMake builds keep the statically linked tfliteextern. Only single-arch (host) builds are supported from CMake — setting `CMAKE_OSX_ARCHITECTURES` to build a universal arm64+x86_64 binary in one pass breaks that same `check_symbol_exists()` detection, since it only compiles for one architecture at a time; a fat binary would need separate per-arch builds `lipo`'d together, as the Bazel path already does.
     - Bazel needs the wrapper package to live *inside* a LiteRT(-LM) workspace (a pristine submodule we don't patch upstream), so `bazel_build_litert.ps1` (Windows), `bazel_build_tflite_macos` (macOS), `bazel_build_tflite_ios` (iOS/Mac Catalyst), `platforms/android/bazel_build_tflite_android`, and the Ubuntu and Debian (`platforms/{ubuntu/*,debian/{bookworm,trixie}}/bazel_build_tflite`) scripts each copy `litertextern/tfliteextern/bazel/{BUILD,tfliteextern.def}` plus the shared `litertextern/tfliteextern/*.cc/.h` and `litertextern/imgproc/*.cc/.h` sources into a fresh `tfliteextern/` package inside that workspace on every run, then build from there. All of them stage into `LiteRT-LM/tfliteextern/` and build in the **LiteRT-LM** submodule's workspace, with the `BUILD` file's `//tflite`/`//litert` labels rewritten to `@litert//...` (LiteRT-LM's `WORKSPACE` fetches LiteRT as the external repository `@litert`, pinned to the same commit as the `litert` submodule — see the macOS bullet below). Bazel always fetches its own pinned TF archive (no local-submodule-reuse option — see the copied `BUILD`'s comments for why). The `BUILD` file's `.def`/`/DEF:` export-list trick is Windows-only (via `select()`); other platforms export every non-static symbol by default, verified by inspecting each build's symbol table. Switching Windows from `litert` to `LiteRT-LM` needed no change to the checked-in `litert_windows_exports.def` — verified by rebuilding `//tfliteextern:libLiteRt` against the newer commit and comparing `dumpbin /exports` (653 live exports vs. 652 listed) and by re-running `Emgu.TF.Lite.Test.Net`'s `TestGetVersion` against the resulting `tfliteextern.dll`.
       - `tfliteextern.cc` uses only the TensorFlow Lite **C API** (`tflite/c/c_api.h`, `c_api_experimental.h`, `common.h`, plus `tflite/schema/schema_generated.h` for model introspection). The `tfe*` entry points the C# side P/Invokes are unchanged, but their opaque handles are now tfliteextern's own small wrapper structs (`TfeModel`, `TfeInterpreter`, ...) around the C API objects. Gaps vs. the old C++-API wrapper: `TensorSize`/`NodeSize` come from the model's primary subgraph (excluding tensors/nodes delegates add); the C API fixes the thread count at creation, so `SetNumThreads` before `AllocateTensors` re-creates the interpreter (re-applying delegates) and after it is ignored with a stderr warning; `DynamicBuffer` (string tensors) is reimplemented on top of the exported `TfLiteTensorReset`. Errors reported through `tfeRedirectError`'s callback are thrown as exceptions by the C# handler, which .NET can't unwind through native frames on macOS/Linux — so new non-fatal diagnostics go to stderr instead. On Android, NNAPI uses its C API (`TfLiteNnapiDelegateCreate`, part of `libLiteRt.so`); the TFLite GPU delegate V2 is C++, Android-only, and compiled out (`WITHOUT_GPU_DELEGATE`, `tfeGpuDelegateV2Create` returns null) in the dynamically linked Android build.
       - `//tfliteextern:tfliteextern` (a `cc_binary`, `linkshared`) is the shared-library form used by Windows (and the static-link fallback elsewhere), statically linking the TFLite C API. **macOS** instead builds `//tfliteextern:tfliteextern_dylib`, a `cc_shared_library` with `dynamic_deps = [":litert_runtime"]`: `:litert_runtime` builds `libLiteRt.dylib` from LiteRT's `//litert/c:litert_tflite_runtime_c_api_so_shim` (LiteRT's runtime, exporting both the `LiteRt*` and `TfLite*` C APIs via the staged `litert_exported_symbols_darwin.lds`), with the install name set and `-framework Metal` linked — LiteRT's own `litert_tflite_runtime_c_api_so` sets neither, and its `.bazelrc` builds macOS with `-undefined dynamic_lookup`, so its `MTLCreateSystemDefaultDevice` reference would otherwise only resolve if something else loaded Metal. `exports_filter` lets `tfliteextern_dylib` take every TFLite library from `libLiteRt.dylib`, so `libtfliteextern.dylib` is only the wrapper (~80 KB per arch vs ~7–9 MB when statically linked) and depends on `@rpath/libLiteRt.dylib` with an `@loader_path` rpath. `bazel_build_tflite_macos` builds these in the `LiteRT-LM/` submodule's Bazel workspace (Bazel 7.6.1 per its `.bazelversion`), against the LiteRT commit LiteRT-LM's `WORKSPACE` fetches as the external repository `@litert` (`9fe5be45` for LiteRT-LM v0.17.1, the same commit the `litert` submodule is pinned to), so `libLiteRt.dylib` comes from the same LiteRT source as LiteRT-LM's own `liblitert-lm.dylib` (built with `--define=litert_runtime_link_mode=dynamic`, it depends on `@rpath/libLiteRt.dylib`, and ours exports every `LiteRt*` function it calls). While staging, the script rewrites our `BUILD` file's `"//tflite`/`"//litert` labels to `"@litert//...`; that LiteRT has no `tflite/ios/ios.bzl`, so `BUILD` defines the iOS minimum version itself. `.gitmodules` sets `ignore = dirty` on both submodules, so the staged `tfliteextern/` packages don't show as changes. For `darwin_arm64` the script also builds LiteRT-LM's `//c:litert-lm` that way, as a separate Bazel invocation with `--platform_suffix=-litert_lm_dynamic` (the define can't apply to our targets — in dynamic mode LiteRT's C API libraries resolve to headers only — and isn't part of Bazel's output folder name, so without the suffix the two builds would overwrite each other's outputs), and copies it to `lib/runtimes/osx/native/liblitert-lm{-darwin_arm64,}.dylib` (install name fixed to `@rpath/liblitert-lm.dylib`) together with LiteRT-LM's prebuilt `libGemmaModelConstraintProvider.dylib`, which it depends on and which is checked to be a real Mach-O file, not a Git LFS pointer. LiteRT-LM doesn't support Intel Macs (that prebuilt only exists for macOS arm64), so `liblitert-lm.dylib` is arm64 only, while `libLiteRt.dylib`/`libtfliteextern.dylib` stay universal; TFLite's kernels and XNNPACK remain inside `liblitert-lm.dylib` (~30 MB), since its embedding code uses TFLite's C++ API. Verified: loading `liblitert-lm.dylib` and `libtfliteextern.dylib` in one process maps a single `libLiteRt.dylib`. `bazel_build_tflite_macos <cpu>` builds both targets, copies them to `lib/runtimes/osx/native/{libtfliteextern,libLiteRt}-<cpu>.dylib` (dropping Bazel's extra `_solib`/runfiles rpaths, then re-signing ad hoc since `install_name_tool` invalidates the arm64 signature), and `lipo`s each into the universal `libtfliteextern.dylib`/`libLiteRt.dylib`; `bazel_build_tflite_macos_fat` drives `darwin_arm64` and `darwin`.
       - `libLiteRt.dylib` is also what the `Emgu.LiteRT` C# classes (`Emgu.LiteRT/`, built by `Emgu.LiteRT/NetStandard/Emgu.LiteRT.csproj` into its own `Emgu.LiteRT.dll`, configured from `cmake/Emgu.LiteRT.*.in`) P/Invoke directly via `DllImport("libLiteRt")` — one runtime serves both the `Emgu.TF.Lite` (Interpreter) and `Emgu.LiteRT` (CompiledModel) APIs. GPU/NPU accelerators are optional plugin dylibs (`libLiteRtMetalAccelerator.dylib` etc.) it tries to load at runtime; without them it logs a warning and uses the built-in XNNPACK CPU accelerator. XNNPACK is part of `libLiteRt`, so on macOS the Interpreter API also uses it by default (the static builds still compile tfliteextern with `-DWITHOUT_XNNPACK`). When `lib/runtimes/osx/native/libLiteRt.dylib` exists, the top-level `CMakeLists.txt` adds it to the `Emgu.LiteRT.runtime.macos` nuspec next to `libtfliteextern.dylib`, and `Emgu.LiteRT.Runtime/Mac`'s `.projitems` copies it to the build output; the CPack zip already picks it up via its `*.dylib` install pattern.
       - `//tfliteextern:tfliteextern_ios_framework` (a `cc_library` wrapped in `ios_static_framework`, no `hdrs` — the umbrella header rules_apple would generate collides with our own `tfliteextern.h`) is the static-library form for iOS device/simulator and Mac Catalyst, where `DllImport("tfliteextern")` resolves to `__Internal` and the tfe* symbols just need to be present in the final app binary. `bazel_build_tflite_ios <config>` (configs: `ios_arm64`, `ios_sim_arm64`, `ios_x86_64`, `ios_armv7`, `darwin_x86_64`/`darwin_arm64` for Catalyst) unzips the resulting `tfliteextern.framework`, extracts the raw archive, and names it `lib/ios/libtfliteextern_<config>.a`; `bazel_build_xcframework` (`ios_x86_64` + `ios_arm64` + `ios_sim_arm64`) and `bazel_build_mac_catalyst` (`darwin_x86_64` + `darwin_arm64`) drive multiple configs and `lipo`/`xcodebuild -create-xcframework` them together, matching what `Emgu.LiteRT.Runtime/Maui/iOS`'s `.csproj` expects (`lib/ios/libtfliteextern_ios.xcframework` or `libtfliteextern.a`).
         - **Mac Catalyst does not work through Bazel**: rules_apple/apple_support have no Catalyst platform, and `bazel_build_tflite_ios darwin_<arch>` (and so `bazel_build_mac_catalyst`) actually produce **iOS Simulator** objects (`LC_BUILD_VERSION` platform 7, not Mac Catalyst's 6), which a Catalyst app can't link. Use `platforms/ios/cmake_build_tflite_catalyst` instead (see Building).
       - `platforms/android/bazel_build_tflite_android <arch>` (`x86`, `x86_64`, `arm`, `arm64`) stages the same `litertextern/` sources into the **LiteRT-LM** workspace exactly as the macOS script does (labels rewritten to `@litert//...`, so `libLiteRt.so` comes from LiteRT-LM's pinned LiteRT) and, like macOS, builds tfliteextern linked dynamically against LiteRT's runtime: `//tfliteextern:litert_runtime_so` (`libLiteRt.so` from `//litert/c:litert_tflite_runtime_c_api_so_shim`, exporting `LiteRt*`/`TfLite*` via the staged `litert_exported_symbols_linux.lds` version script, with `-Wl,-soname,libLiteRt.so` — LiteRT's own `litert_tflite_runtime_c_api_so` sets no SONAME, which would make `libtfliteextern.so` record a Bazel output path as its `DT_NEEDED`) and `//tfliteextern:tfliteextern_so` (`libtfliteextern.so`, `cc_shared_library` with `dynamic_deps`, sharing the `:tfliteextern_capi_lib` wrapper library with macOS). Both are copied to `lib/android/<abi>/` (matching what `Emgu.LiteRT.Runtime/Maui/Android`'s `.csproj` packages; it also packages `libLiteRt.so` when present). `libLiteRt.so` contains the TFLite C API, XNNPACK and the NNAPI delegate (C API) but not the TFLite GPU delegate V2 — LiteRT does GPU through its separate accelerator plugin — and that delegate needs TFLite internals `libLiteRt.so` doesn't export, so `:tfliteextern_capi_lib` defines `WITHOUT_GPU_DELEGATE` on Android. Each `.so` links its own static libc++ (most of `libtfliteextern.so`'s ~0.9 MB stripped size); only C APIs cross between them. The script strips both with the NDK's `llvm-strip --strip-unneeded` (found under `$ANDROID_NDK_HOME/toolchains/llvm/prebuilt/*/bin`, so it works from a Linux or macOS host): debug info otherwise roughly triples their size, and the dynamic symbol tables are unchanged (verified). Stripped sizes: `libLiteRt.so` 3.8–8.8 MB, `libtfliteextern.so` 0.6–0.9 MB depending on the ABI. Verified on an arm64 API 35 emulator: the MAUI demo loads both libraries and calls into `libLiteRt.so`. For `arm64` and `x86_64` it also builds LiteRT-LM's `//c:litert-lm` with `--define=litert_runtime_link_mode=dynamic --platform_suffix=-litert_lm_dynamic` (as on macOS) and copies `liblitert-lm.so` (stripped; `DT_NEEDED` `libLiteRt.so`, `RUNPATH $ORIGIN`) plus LiteRT-LM's prebuilt `libGemmaModelConstraintProvider.so` to `lib/android/<abi>/`; that prebuilt only exists for those two ABIs, so `armeabi-v7a`/`x86` get no LiteRT-LM. Its 43 `LiteRt*` imports carry the `VERS_1.0` symbol version, which our `libLiteRt.so` (`litert_exported_symbols_linux.lds`) defines too — verified that every import of `liblitert-lm.so` and `libtfliteextern.so` resolves. On a Linux host with clang installed, the script adds `--repo_env=CC=clang --repo_env=CXX=clang++` so the host-side build tools (Bazel's `[for tool]` actions; Android code itself uses the NDK) are compiled with clang: Ubuntu 26.04's GCC 15 rejects Abseil's `raw_hash_set.cc` ("Never use <bmi2intrin.h> directly"). On a macOS host the script adds `--host_linkopt=-Wl,-undefined,dynamic_lookup`: LiteRT-LM's `build:android` sets `--noenable_platform_specific_config`, so its `build:macos` host link option doesn't apply, and without it the host Rust proc-macro dylibs its build tools need come out unloadable by dyld ("mis-aligned LINKEDIT string pool"), failing with rustc `E0463 can't find crate`. Verified on the arm64 API 35 emulator: the MAUI demo loads `libtfliteextern.so`/`libLiteRt.so` built this way and creates the XNNPACK delegate. Two things needed fixing beyond staging the sources:
         - The statically linked `//tfliteextern:tfliteextern` (no longer what the script builds) still links the GPU delegate on Android: `litertextern/tfliteextern/bazel/BUILD`'s `_TFLITEEXTERN_DEPS` adds `//tflite/delegates/gpu:delegate` + `:delegate_options` (and NNAPI) behind a `select({"@org_tensorflow//tensorflow:android": [...], "//conditions:default": []})` — those targets need EGL and don't build on the other platforms.
         - Of litert's four `.bazelrc` `android_*` configs, only `android_arm64` sets `--incompatible_enable_cc_toolchain_resolution`/`--incompatible_enable_android_toolchain_resolution`; the other three fall back to a legacy `--crosstool_top=//external:android/crosstool` alias that isn't actually defined anywhere in this WORKSPACE (it silently resolves to the host `local_config_cc` toolchain instead, which doesn't have a toolchain for a non-host cpu, or produces `/bin/false`-stubbed compile actions). The build script passes both flags explicitly for every arch to force the same NDK-toolchain-via-platforms resolution arm64 already gets from its config.
       - `platforms/ubuntu/24.04/bazel_build_tflite` follows the same staging pattern, builds `//tfliteextern:tfliteextern` with `--config=linux` (`--config=linux_arm64` too on an aarch64 host), and copies the result to `lib/runtimes/ubuntu-x64/native/libtfliteextern.so` (or `ubuntu-arm64`), matching what `Emgu.LiteRT.Runtime/Ubuntu`'s `.projitems` expects. No GPU-delegate select() or toolchain-resolution override needed here — Linux isn't `__ANDROID__` and already resolves its host toolchain correctly.
   - `platforms/debian/{bookworm,trixie}/bazel_build_tflite` (identical files) build `//tfliteextern:litert_runtime_so` and `//tfliteextern:tfliteextern_so` on a native ARM Debian host (`--config=linux --config=linux_arm64` on 64-bit, plain `--config=linux` on armhf) with clang forced via `--repo_env=CC=/usr/bin/clang` (GCC >= 14 rejects LiteRT's `target("dotprod")` attribute), and copy `libLiteRt.so`/`libtfliteextern.so` to `lib/runtimes/linux-arm64/native/` (or `linux-arm`).
2. **P/Invoke layer** — `TfLiteInvoke` (in `Emgu.TF.Lite/`, namespace `Emgu.TF.Lite`) is a partial static class that exposes the native DLL entry points via `[DllImport]`.
3. **Managed wrappers** — `Interpreter`, `Tensor`, etc. inherit `UnmanagedObject` (from `Emgu.LiteRT.Util/`, namespace `Emgu.LiteRT.Util`, built into its own `Emgu.LiteRT.Util.dll`) and wrap native handles with proper lifetime management.
   - `Emgu.LiteRT/` is a separate managed wrapper (own `Emgu.LiteRT.dll`, namespace `Emgu.LiteRT`) over LiteRT's own `libLiteRt` C API — `Environment`, `Model`, `CompiledModel`, `TensorBuffer`, etc. — with no Emgu native layer.
   - `Emgu.LiteRT.LM/` (own `Emgu.LiteRT.LM.dll` and nuget package `Emgu.LiteRT.LM`, namespace `Emgu.LiteRT.LM`, depending on `Emgu.LiteRT.Util` only) wraps LiteRT-LM's C API (`LiteRT-LM/c/*.h`, the `litert_lm_*` functions exported by `liblitert-lm`) the same way, via `DllImport("liblitert-lm")` (`__Internal` on iOS): `EngineSettings`/`Engine` (load a `.litertlm` model; tokenize, start/stop tokens), `SessionConfig`/`SamplerParams`/`Session` (`GenerateContent`, `RunPrefill`/`RunDecode`, scoring, checkpoints), `InputData`, `Responses`, `ConversationConfig`/`ThinkingConfig`/`ConversationOptionalArgs`/`Conversation` (JSON messages in LiteRT-LM's format; `Conversation.CreateTextMessage` builds one), `LoadedFile` (model capabilities) and `BenchmarkInfo`; the embedding-engine and experimental headers aren't wrapped yet. Notes: strings cross as null-terminated UTF-8 `byte[]` / `PtrToStringUtf8` (not `LPStr`, which is ANSI on Windows); the C API reports failures only as NULL / non-zero (details in the native log), surfaced as `LiteRtLmException`; it has no getters, so config properties cache the last value set; every setter and the stream functions copy their arguments. Streaming (`Session.GenerateContentStreamAsync`/`RunDecodeAsync`, `Conversation.SendMessageStreamAsync`, whose chunks are partial JSON messages) goes through `StreamOperation`: one static `LiteRtLmStreamCallback` delegate, a `GCHandle` as `callback_data`, a `TaskCompletionSource` with `RunContinuationsAsynchronously` (user code never resumes on LiteRT-LM's thread), no exception ever unwinding into native frames, native cancel issued from a thread-pool thread (cancelling from inside a callback could deadlock on LiteRT-LM's execution-manager locks), and the task completing only on the final chunk, so the session is idle once it completes (an `onChunk` exception cancels and then faults the task). LiteRT-LM doesn't support reusing a session/conversation after `Cancel`. On **iOS**, LiteRT-LM's C API comes from `platforms/ios/bazel_build_litert_lm_ios`, which builds LiteRT-LM's own `//swift:CLiteRTLM` (`apple_xcframework` in `LiteRT-LM/swift/BUILD`) in the LiteRT-LM workspace into `lib/ios/CLiteRTLM.xcframework`: a **dynamic** framework (device arm64 + simulator arm64, iOS 15) with its own statically linked LiteRT/TFLite, exporting only the C API - it must stay dynamic, since the iOS `tfliteextern` is a static library with its own TFLite and both statically in one app would duplicate those symbols. CLiteRTLM links LiteRT-LM's prebuilt `prebuilt/ios_{arm64,sim_arm64}/libGemmaModelConstraintProvider.dylib` (Git LFS), a loose dylib an app bundle can't contain, so the script wraps each slice into `GemmaModelConstraintProvider.framework` (`lib/ios/GemmaModelConstraintProvider.xcframework`), rewrites CLiteRTLM's load command to it with `install_name_tool -change` and re-signs ad hoc. Google builds that prebuilt for iOS 26.4+, so LiteRT-LM needs iOS 26.4 at run time. `Emgu.LiteRT.Runtime/Maui/iOS`'s `.csproj` embeds both xcframeworks (`NativeReference Kind=Framework`, when present), and `Emgu.LiteRT.LM`'s iOS `DllImport("__Internal")` resolves against the linked framework - verified in an iOS 27 simulator: the MAUI demo downloaded and ran Qwen3, streaming and multi-turn. The MAUI demo's `LiteRtLmChatPage` (and its `Emgu.LiteRT.LM`/`.LM.Models` references) is enabled for Windows and iOS; like Mac Catalyst, the iOS app needs the UIScene life cycle (`Platforms/iOS/Info.plist` `UIApplicationSceneManifest` + `SceneDelegate.cs`) or UIKit kills it at launch when built with the iOS 27 SDK, and building it with Xcode 27 needs `-p:ValidateXcodeVersion=false`. `liblitert-lm` (+ `libGemmaModelConstraintProvider`) is packaged, when present, in `Emgu.LiteRT.runtime.macos` (top-level `CMakeLists.txt`), `Emgu.LiteRT.Runtime/Mac`'s `.projitems`, the MAUI Android runtime (`arm64-v8a`/`x86_64`), and - on Windows, where it's built separately by `bazel_build_litert.ps1` rather than bundled with `libLiteRt.dll`/`tfliteextern.dll` - its own `Emgu.LiteRT.LM.runtime.windows` nuget package (depending on `Emgu.LiteRT.runtime.windows` for `libLiteRt.dll`), built only when `lib/runtimes/win-x64/native/liblitert-lm.dll` exists (`HAVE_WINDOWS_LITERT_LM`). Tests: `Emgu.LiteRT.Test/Emgu.TF.Lite.Test/UnitTestLiteRtLm.cs` (Qwen3-0.6B from `litert-community/Qwen3-0.6B`, downloaded via `DownloadableFile`; skipped where `liblitert-lm` can't be loaded).
   - `Emgu.LiteRT.LM.Models/` (own `Emgu.LiteRT.LM.Models.dll` and nuget package, namespace `Emgu.LiteRT.LM.Models`, depending on `Emgu.LiteRT.LM`, `Emgu.LiteRT.Util` and, for netstandard2.0 only, `System.Text.Json`) holds ready-to-use language models, the LiteRT-LM counterpart of `Emgu.LiteRT.Tflite.Models`: `LanguageModel` (base: `Init(modelFile, backend, configureSettings)` downloads the `.litertlm` via `FileDownloadManager` and creates the `Engine` on a thread-pool thread, with the compiled-model cache next to the model), `Qwen3` (Qwen3-0.6B, `litert-community/Qwen3-0.6B`'s `qwen3_0_6b_mixed_int4.litertlm` — the repo's `Qwen3-0.6B.litertlm` fails to load its tokenizer with LiteRT-LM v0.17.1; `EnableThinking`) and `Chat` (`Send`/`SendAsync` with streaming, `History`, `SystemMessage`, `MaxOutputTokens`, `EnableThinking`), with `ChatMessage` (JSON in LiteRT-LM's message format via `Utf8JsonWriter`/`JsonDocument`) and `ChatReply` (splits a leading `<think>...</think>` block into `Thinking`/`Text`). `Gemma4E2B` (Gemma 4 E2B, `litert-community/gemma-4-E2B-it-litert-lm`'s `gemma-4-E2B-it.litertlm`, 2.6 GB). How `Chat` uses LiteRT-LM conversations depends on `LanguageModel.SupportsMultiTurnConversation`: LiteRT-LM v0.17.1 renders a conversation incrementally and refuses a second message when the chat template re-renders earlier turns differently (Qwen3 drops the previous answer's empty `<think></think>`), so for such models (the default, e.g. `Qwen3`) `Chat` sends each message through a new `Conversation` whose initial messages are the history; models that override it to true (`Gemma4E2B`, verified multi-turn in one conversation, as is Qwen2.5-1.5B-Instruct) keep one `Conversation` open, so each message only processes the new tokens. `Chat` is `IDisposable` (releases the open conversation), rebuilds the open conversation from its history when `SystemMessage`/`MaxOutputTokens`/`EnableThinking` change or after a failed/cancelled send (LiteRT-LM doesn't support reusing a conversation after cancel), and `LanguageModel` keeps weak references to the chats that opened conversations and closes them before disposing or replacing its engine. Add new models as further `LanguageModel` subclasses. Tested by `TestQwen3Chat`/`TestQwen3Thinking`/`TestGemma4E2BChat` in `UnitTestLiteRtLm.cs`.
   - **Packaging**: `Emgu.LiteRT`, `Emgu.TF.Lite` (csproj, `AssemblyName`, nuget `PackageId` and C# namespace all `Emgu.TF.Lite` — they briefly diverged, with the folder and then the csproj/AssemblyName/PackageId each renamed to `Emgu.LiteRT.Tflite` and later moved back) and `Emgu.LiteRT.Util` each produce their own nuget package (`IsPackable=True`/`GeneratePackageOnBuild=True` in their CMake-generated `Directory.Build.props`) — they used to ship bundled into a single `Emgu.LiteRT` package (via `PrivateAssets="all"` ProjectReferences plus an `IncludeReferencedProjectsInPackage` target), but were split so each can be installed independently. `Emgu.TF.Lite` and `Emgu.LiteRT` both `ProjectReference` `Emgu.LiteRT.Util.csproj` with no `PrivateAssets` (their `UnmanagedObject`-derived types need it to compile), which NuGet turns into a normal package dependency on `Emgu.LiteRT.Util` when packing since the referenced project is itself packable; `Emgu.LiteRT` has no reference to `Emgu.TF.Lite` at all, since its code never used it — that was only ever packaging-bundling, not a real dependency. Every package ID except `Emgu.TF.Lite`'s, `Emgu.TF.Lite.ImageIO`'s and `Emgu.TF.Lite.runtime.windows`'s (each a literal string, not derived from the `Emgu.LiteRT` root) comes from `EMGU_LITERT_NUGET_ID` (`Emgu.LiteRT`) in the top-level `CMakeLists.txt` — `Emgu.LiteRT.Util`, `Emgu.LiteRT.Tflite.Models`, `Emgu.LiteRT.runtime.{macos,windows,ubuntu,debian-*,maui.*}` — and their underlying projects mostly keep `Emgu.TF.Lite.*` names or namespaces too (e.g. `Emgu.TF.Lite.Models/NetStandard/Emgu.TF.Lite.Models.csproj`), same as `Emgu.TF.Lite/NetStandard/Emgu.TF.Lite.csproj` itself (no longer an exception now that its csproj/AssemblyName/PackageId moved back off `Emgu.LiteRT.Tflite`). Projects that use `Emgu.TF.Lite`/`Emgu.LiteRT.Util` types (`Emgu.TF.Lite.Models`, the MAUI runtime projects) now `ProjectReference` all three with no `PrivateAssets`, so their own packages correctly depend on all three. `Emgu.TF.Lite/Toolbox.cs`'s tfliteextern image helpers (`Pixel32ToPixelFloat` etc.) are in `Emgu.TF.Lite.Toolbox`, not `Emgu.LiteRT.Util.Toolbox` — a partial class can't span the two assemblies.
4. **Models layer** — `Emgu.TF.Lite.Models/` (nuget `PackageId` still `Emgu.LiteRT.Tflite.Models`) provides high-level pre-built model helpers (MobileNet, COCO SSD, etc.) that download weights and run inference, built on the TFLite Interpreter API (`Emgu.TF.Lite`), not LiteRT's own CompiledModel API. `Emgu.TF.Lite.ImageIO/` (folder, csproj, `AssemblyName`, nuget `PackageId` and C# namespace all `Emgu.TF.Lite.ImageIO` — renamed from `Emgu.Models/`, then briefly `Emgu.LiteRT.ImageIO/`) is its own project and nuget package, providing `NativeImageIO`/`JpegData` - these couldn't move into `Emgu.LiteRT.Util` the way `Annotation`/`DownloadableFile`/`FileDownloadManager` did, because `NativeImageIO` calls `Emgu.TF.Lite.Toolbox`'s native pixel-conversion P/Invokes, which live in `Emgu.TF.Lite`; `Emgu.TF.Lite` itself depends on `Emgu.LiteRT.Util`, so putting `NativeImageIO` there too would create a circular project reference. `Emgu.TF.Lite.ImageIO.csproj` instead `ProjectReference`s both `Emgu.LiteRT.Util` (for `Annotation`, which `NativeImageIO`'s platform variants take as a parameter) and `Emgu.TF.Lite` (for `Toolbox`) directly, and depends on both as nuget dependencies when packed. `Android/AndroidFileAsset.cs` lives in this folder too but was already namespaced `Emgu.LiteRT.Util` (pre-existing, left as-is) rather than `Emgu.Models`/`Emgu.TF.Lite.ImageIO`.
5. **Platform runtime packages** — `Emgu.LiteRT.Runtime/` contains shared project items (`.shproj`/`.projitems`) that pull in the correct native binaries for each platform (Windows, macOS, Debian, Ubuntu, Maui).
6. **Unity integration** — `Emgu.TF.Lite.Unity/` is a Unity project that mirrors the managed API for use in game engines.

### Shared projects
`Emgu.TF.Lite.Shared.shproj`, `Emgu.LiteRT.Util.Shared.shproj`, etc. share source files across multiple target frameworks (NetStandard, Android, iOS, Unity). The `.projitems` files define which `.cs` files are included.

## Building

### Prerequisites
- .NET SDK
- Visual Studio 2022 or VS 2026 (detected automatically by `vswhere.exe`) — Windows
- CMake 3.16+
- Bazel (for the Bazel native builds; the version is pinned by `litert/.bazelversion`). The macOS and Android Bazel scripts set `HERMETIC_PYTHON_VERSION=3.12` when `python3.12` is on the `PATH`.
  - The macOS, iOS and Android Bazel scripts run `bazel --output_user_root=<repo>/bazel_output build ...`, so Bazel's output tree, install base and cache (several GB per platform) live in `bazel_output/` at the repo root — gitignored, outside the `litert/` workspace — instead of the default `/private/var/tmp/_bazel_$USER` (macOS) or `~/.cache/bazel` (Linux). Running `bazel` by hand in `litert/` needs the same startup flag (e.g. `bazel --output_user_root="$(cd .. && pwd)/bazel_output" build ...` — use an absolute path), otherwise Bazel starts a separate server with a cold cache in the default location. Deleting `bazel_output/` forces a full rebuild.
- Xcode — macOS/iOS. The macOS script handles an Xcode installed outside `/Applications` (e.g. on another volume) by passing `DEVELOPER_DIR` into Bazel's sandbox.
- Android SDK + NDK, and a JDK — Android (see below)
- TF Lite native library already built and placed under `lib/runtimes/` (or `lib/android/`, `lib/ios/`)

### Build native TF Lite (Windows x64)
```powershell
cd platforms/windows
.\cmake_build_litert.ps1 64 xnn
```
Or via Bazel (also produces `lib/runtimes/win-x64/native/tfliteextern.dll`):
```powershell
cd platforms/windows
.\bazel_build_litert.ps1 64 xnn
```

### Build the .NET solution (Windows)
```powershell
cd platforms/windows
.\build_emgu_litert.ps1
```
Optional args: `doc` (build docs), `nuget` (build NuGet packages), `package` (build zip packages).

### Build native TF Lite (macOS)
```bash
platforms/macos/bazel_build_tflite_macos_fat
```
Builds `arm64` and `x86_64` and writes the universal `lib/runtimes/osx/native/libtfliteextern.dylib` and `libLiteRt.dylib`, plus the arm64-only `liblitert-lm.dylib` and `libGemmaModelConstraintProvider.dylib` (needs `git -C LiteRT-LM lfs pull`) (plus the per-arch `*-darwin_arm64.dylib`/`*-darwin.dylib` they are `lipo`'d from). To build one architecture only (the universal files then contain just that one):
```bash
platforms/macos/bazel_build_tflite_macos darwin_arm64   # or: darwin (x86_64, cross-compiled on Apple Silicon)
```
Alternative CMake build — host architecture only. Like the Bazel build it produces both `libLiteRt.dylib` and a thin `libtfliteextern.dylib` linked against it (`@rpath` install names, `@loader_path` rpath, XNNPACK on); output goes to `lib/runtimes/osx/native/<arm64|x64>/`:
```bash
platforms/macos/cmake_build_tflite
```

### Build the .NET solution and packages (macOS)
```bash
platforms/macos/build_emgutf
```
Configures CMake in `build/` (Release) and runs `make package`: builds the managed projects, writes the NuGet packages (`Emgu.LiteRT`, `Emgu.TF.Lite`, `Emgu.LiteRT.Util`, `Emgu.TF.Lite.ImageIO`, `Emgu.LiteRT.Tflite.Models`, `Emgu.LiteRT.runtime.*`) to `platforms/nuget/`, and the CPack zip to `build/libemgulitert-ios-macos-<version>.zip`. The version's last component is derived from the git commit count, so it changes with every commit. Run the native build first: packages only include the native binaries already in `lib/`.

### Build native TF Lite (Mac Catalyst)
```bash
platforms/ios/cmake_build_tflite_catalyst arm64   # or: x86_64 (cross-compiled on Apple Silicon)
```
Writes `lib/ios/libtfliteextern_darwin_<arch>.a`, the self-contained static libraries `Emgu.LiteRT.Runtime/Maui/Mac`'s `.csproj` force-loads into a Catalyst app (`DllImport` resolves the `tfe*` symbols from the app binary, as on iOS). It configures `litertextern/tfliteextern`'s CMake project with clang's `-target <arch>-apple-ios15.0-macabi` (on the C/C++/Objective-C(++) compiler and linker flags), statically linking TFLite (`TFLITEEXTERN_LINK_LITERT=OFF`, XNNPACK off like the static iOS builds) into a build-only `libtfliteextern.dylib` — that link proves every symbol resolves for Catalyst and its `link.txt` lists exactly the static libraries needed, which the script merges with tfliteextern's objects via `libtool -static`. Build folders are `litertextern/tfliteextern/build_catalyst_<arch>/` (gitignored). Every object is Mac Catalyst (`LC_BUILD_VERSION` platform 6, minos 15.0). Catalyst is `CMAKE_SYSTEM_NAME` Darwin to CMake but `TARGET_OS_IOS` to the compiler, so `litertextern/tfliteextern/CMakeLists.txt` detects it (`TFLITEEXTERN_TARGET_MACCATALYST`) and adds `litert/tflite/profiling/signpost_profiler.mm` to `tensorflow-lite` itself — litert's CMake only compiles it for `CMAKE_SYSTEM_NAME` iOS, while `platform_profiler.cc` calls it whenever `TARGET_OS_IOS`; Objective-C++ must be enabled before litert's subdirectory is added, and `PROJECT(tfliteextern)` comes first in that file so the check can compile. Verified by running the MAUI demo as a Catalyst app on macOS 27 (the About page reads the TFLite version through the `tfe*` API). Building the demo for Catalyst needed:
- `net10.0-maccatalyst` in the MAUI UI runtime's target frameworks (`cmake/Emgu.LiteRT.runtime.maui.Directory.Build.props.in`, macOS/Windows hosts) — otherwise Catalyst apps resolve its `netstandard2.0` build, which never references the Mac runtime project, so no tfliteextern was linked at all.
- The UIScene life cycle: UIKit refuses to launch apps built with the macOS 27 SDK without it, so `Emgu.LiteRT.Example/Maui.Lite/Platforms/MacCatalyst/Info.plist` declares a `UIApplicationSceneManifest` using MAUI's default scene configuration with `SceneDelegate.cs` (a `MauiUISceneDelegate`).
- `-p:ValidateXcodeVersion=false` when the .NET MacCatalyst SDK pack doesn't match the installed Xcode exactly (e.g. pack 26.5 wants Xcode 26.6 while Xcode 27.0 is installed): `dotnet build Emgu.LiteRT.Example/Maui.Lite/Maui.Demo.Lite.csproj -f net10.0-maccatalyst -c Debug -p:ValidateXcodeVersion=false`. MAUI incremental builds may keep a stale bundled `Info.plist`; delete `bin/obj/Debug/net10.0-maccatalyst` after editing it.

### Build native TF Lite (Android, from Linux or macOS)
The Android binaries can be built on either a Linux or a macOS host, with the same script:
```bash
platforms/android/bazel_build_tflite_android arm64   # or: x86_64, arm, x86
```
Writes `lib/android/<abi>/libtfliteextern.so` and `libLiteRt.so` (`arm64-v8a`, `x86_64`, `armeabi-v7a`, `x86`), 16 KB page-aligned and stripped of debug info, plus `liblitert-lm.so` and `libGemmaModelConstraintProvider.so` for `arm64-v8a`/`x86_64` only (needs `git -C LiteRT-LM lfs pull`). `libtfliteextern.so` links dynamically against `libLiteRt.so`, LiteRT's runtime, which `Emgu.LiteRT` also uses directly. NNAPI is supported; the TFLite GPU delegate isn't (`tfeGpuDelegateV2Create` returns null). Run once per ABI; extra arguments are passed to `bazel build`. The script reads the SDK from `ANDROID_HOME` and the NDK from `ANDROID_NDK_HOME`, else the newest version under `$ANDROID_HOME/ndk`:
- **Linux**: `ANDROID_HOME` defaults to `/usr/lib/android-sdk` (the build image layout) when unset.
- **macOS**: set `ANDROID_HOME` to the Android Studio SDK, usually `~/Library/Android/sdk` (no default — the Linux path doesn't exist there). Verified with NDK 28.0.12916984 for all four ABIs.

### Build with CMake (cross-platform)
```bash
mkdir build && cd build
cmake <PATH_TO_EMGUTF_ROOT>
cmake --build . --config Release
```

## Running Tests

Tests use either NUnit or MSTest (selected at compile-time via the `VS_TEST` preprocessor symbol).

### TF Lite — run all tests
```bash
dotnet test Emgu.LiteRT.Test/Emgu.TF.Lite.Test/Emgu.TF.Lite.Test.Net/Emgu.TF.Lite.Test.Net.csproj
```

### Run a single test
```bash
dotnet test <project.csproj> --filter "FullyQualifiedName~TestGetVersion"
```

Test assets (e.g., `grace_hopper.jpg`) must be present in the working directory when tests run.

The LiteRT-LM tests (`UnitTestLiteRtLm.cs`) download large models on the first run (Qwen3-0.6B ~500 MB, Gemma 4 E2B ~2.6 GB), so they are ignored by default, the same way as Emgu CV's model tests: opt in with `dotnet test <project.csproj> -p:TestModels=true`, which defines `TEST_MODELS` (each test has an `#if !TEST_MODELS` `[Ignore]` block).

Like Emgu CV, the app and test projects target the .NET version of the `dotnet` CMake runs: `cmake/modules/FindCSharp.cmake` sets `DOTNET_VERSION_MAJOR` from `dotnet --version`, and per-project `Directory.Build.props` generated from `cmake/*.Directory.Build.props.in` set `<TargetFramework>net${DOTNET_VERSION_MAJOR}.0</TargetFramework>` (`-windows` for `CVInterop.Lite`, `-android`/`-ios`/`-maccatalyst` for the MAUI projects); the csproj files name no version (a `TargetFramework` in a csproj would override the generated props, which are imported first). Re-run CMake (`build_emgutf`, or `cmake .` in `build/`) after switching .NET SDKs. So `Emgu.TF.Lite.Test.Net` needs the CMake-generated `Directory.Build.props` files (run the platform's `build_emgutf` once), and on macOS it copies `libtfliteextern.dylib`/`libLiteRt.dylib` from `lib/runtimes/osx/native/` via `Emgu.LiteRT.Runtime/Mac`'s `.projitems`.

## Key Conventions

- **Extern library name**: `tfliteextern`. On iOS/Unity this resolves to `__Internal`.
- **`UnmanagedObject`** (in `Emgu.LiteRT.Util/`): base class for all objects wrapping a native pointer; handles `Dispose`/finalizer pattern.
- **Calling convention**: `CallingConvention.Cdecl` throughout.
- **Boolean marshaling**: `UnmanagedType.U1` for `bool`, `UnmanagedType.Bool` for `int`-as-bool.
- **Error handling**: native errors are redirected via a callback delegate (`TfLiteErrorCallback`) and thrown as managed exceptions.
- There is no `tensorflow/` submodule — it was removed once the Windows CMake path was proven to work without it (LiteRT downloads the TF source it needs itself). The overall package version (`CPACK_PACKAGE_VERSION_*` in the top-level `CMakeLists.txt`, and `litertextern/tfliteextern/CMakeLists.txt`'s own version) is read from `litert/litert/version.bzl` (`LITERT_EXPERIMENTAL_VERSION`) via `cmake/modules/LitertVersion.cmake`, plus the git commit count. Exception: the TFLite-versioned packages (`Emgu.TF.Lite`, `Emgu.LiteRT.Tflite.Models`, `Emgu.TF.Lite.runtime.windows`) use the TFLite version, i.e. TensorFlow's `TF_VERSION` (`EMGU_TFLITE_PACKAGE_VERSION` = `<TF_VERSION>.<commit count>`, e.g. 2.22.0.N). Every native build writes a `tflite_version.txt` next to its libraries (the Bazel scripts from `$(bazel info output_base)/external/org_tensorflow/tensorflow/tf_version.bzl`, the CMake build from the TensorFlow it downloads), the same way as `tflite_with_xnnpack.txt`; the top-level `CMakeLists.txt` reads all of them under `lib/` (highest wins, with a warning if they differ - e.g. a CMake-built 2.21.0 next to Bazel-built 2.22.0) and falls back to the LiteRT version when there are none. The root `Directory.Build.props` (from `cmake/Directory.Build.props.in`, imported at the end of each project's own props) only sets `Version` when the project hasn't, so the Tflite projects' version isn't overridden. The MAUI runtime's `PackageReference` to `Emgu.TF.Lite.runtime.windows` uses that version too; `ProjectReference`s to the Tflite projects pick it up automatically.
- The `litert/` directory is a submodule of `google-ai-edge/LiteRT`, pinned to commit `9fe5be45` (`v2.2.0-265`, 2026-08-27): the LiteRT commit the `LiteRT-LM` submodule pins as its `@litert` repository (`LITERT_REF` in `LiteRT-LM/WORKSPACE`; LiteRT-LM v0.17.1). Do not modify files inside it directly.
  - **The `litert` submodule must match LiteRT-LM's LiteRT version.** The Bazel builds use LiteRT-LM's `@litert` (downloaded by Bazel), while the CMake builds (`litertextern/tfliteextern/CMakeLists.txt`) use this submodule; keeping them on the same commit means every `libLiteRt` is built from the same LiteRT source, so it is compatible with `liblitert-lm` (which links against it) and all platforms ship the same TFLite/LiteRT version. When updating the `LiteRT-LM` submodule, check its `LiteRT-LM/WORKSPACE` `LITERT_REF` and move `litert` to that commit too (`git -C litert checkout <LITERT_REF>`, then `git -C litert submodule update` for its nested `third_party/tensorflow`), and re-check the CMake builds. (Before following LiteRT-LM, `litert` was pinned to `v2.2.0`, not `main`: the bleeding-edge commit this was originally added at hit a WORKSPACE bug under Bazel; see `litertextern/tfliteextern/bazel/BUILD`'s comments.)
- `litertextern/` holds the Emgu-authored native wrapper (`tfliteextern`, `imgproc`) that both Windows build paths use — this is the one place native wrapper source changes should be made for that platform going forward. `litertextern/tfliteextern/bazel/{BUILD,tfliteextern.def}` is the Bazel-specific counterpart to `litertextern/tfliteextern/CMakeLists.txt`, staged into `LiteRT-LM/tfliteextern/` at build time (see above) since it can't live there in git.
